## Concrete problem and finite change

`formats/markdown/export.go` accumulates a complete HTML string, repeatedly
materializes escaped whole code/quote/raw/table fragments, and worker `render`
then converts it to a byte slice. The64MiB check happens after that work. The
existing exact8MiB ampersand-fence regression produces about40MiB HTML, making
these temporary copies material even with a bounded input.

Add an additive byte-returning export API with a caller-supplied nonnegative
limit and a distinct output-limit error. The worker passes the existing64MiB
protocol cap and returns those owned bytes directly. Keep existing string API
callers compatible and keep successful HTML/warnings/order/ranges identical.
No partial result may be returned on limit failure; worker sends a coherent
`output-limit` response with zero payload. Partial-document refusal remains.

Preferred minimal approach: one shared renderer writing through an internal
sink, with a bounded byte sink for the worker. Every append checks the remaining
budget before growing/copying, and capacity growth must not exceed the limit.
Escape the five HTML characters incrementally, emitting literal runs/entities;
do not call whole-fragment html.EscapeString and concatenate large strings first.
Preserve exact entity spellings (`&amp;`, `&#39;`, `&lt;`, `&gt;`, `&#34;`) and
traverse early-out after failure. Audit code, quote, raw HTML/doc-block fallback,
table fallback/cells, plain gaps, inline text and href. Heading anchors already
have a256-byte base cap. Existing string convenience APIs may collect strings;
avoid duplicating format rules. Owner may propose a simpler equivalent approach
at the API checkpoint, but no protocol change, unsafe alias, spool files, parser
rewrite, new library or alternate application export path.

Bounds are on accepted/generated bytes and owned result-buffer capacity, not
whole-process RSS. Buffer growth can transiently retain previous allocations;
source/AST/Go allocator/host result copies remain. Do not promise a hard peak
memory cap or zero-copy across processes.
