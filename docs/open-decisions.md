**本阶段修掉的三处真实缺陷**（不是重构，是 bug）：

1. `core/editor/registry.ts` 的 `registerAdapter` 用 `unshift` 插入，
   实际优先级与注释**相反**。只有一个内核时看不出来；接上第二个认得 `.md` 的内核后，
   备胎会抢在正主前面把所有 `.md` 吃掉。已改为「原地替换 + push」并补了说明。
2. **查找替换在 Markdown 内核上会静默丢数据**：替换不经过键盘事件，
   原先的「变更上报」判定把它当成程序写入而不上报，外壳持有的内容停留在替换前，
   用户按保存时写回磁盘的是旧内容。已加 `USER_EDIT_META`。
3. **图片的写入路径与回读路径不是同一个字符串**（M6 暴露）：
   Markdown 里的地址必须是正斜杠，Windows 上的文档路径是反斜杠 ——
   `joinPath` 只拼接、不统一，于是写入时算出 `…\a.assets\image-x.png`、
   回读时算出 `…\a.assets/image-x.png`。文件系统两种都认，所以**只在按字符串
   比较的地方出问题**（缓存键、去重、相等判断），表现为「图写进去了但显示不出来」。
   已让 `joinPath` 统一分隔符风格（只换风格，不折叠重复分隔符、不解析 `..`），
   并补了一条「写读路径逐字符相同」的用例。

   > 这一条**在单元测试里看不到**：内核那一层拿到的「读文件」是测试自己给的假函数，
   > 返回什么都是测试说了算。只有端到端（真写盘 → 真回读）才把它照出来 ——
   > 这也是「接缝必须单独测」的一个具体例子。

| 事项 | 为什么推迟 | 风险 / 何时该做 |
|---|---|---|
| **切标签页会重建编辑器内核** | 正确性优先：让内核跟着标签页走比在同一个面板里换内核安全得多（ADR 0010） | 中。代价是撤销栈、光标、滚动位置在切换时丢失。改法（全部挂载 + CSS 隐藏）需要先实测内存占用，尤其是一份 10 万字文档 |
| **切视图也会重建内核** | 同一个理由（ADR 0014）。两种视图共用 `doc.text` 一份权威副本，所以**内容**无损；丢的是撤销栈、光标与滚动位置 | 中。horseMD 明确把「切源码模式保留滚动位置」当卖点，所以这一条迟早要补。难点是**坐标翻译**：源码偏移 → ProseMirror 位置需要序列化器的逆映射，而它一旦不精确就会「跳到错的地方」——按本项目一贯的取舍（跳错比不跳更伤人），**宁可不做也不做错**。廉价的近似（按滚动比例）可以后续单独评估 |
| **i18n** | 现在只有中文，做 i18n 骨架需要先确定文案的组织方式 | **中高。这件事越晚做越贵** —— 每加一个功能就多一批散落的字符串。建议在 P3-B 的第 17 项做「骨架」而不是「翻译」 |
| **选中浮层点到编辑器之外不会自己收起来** | 刻意为之：点浮层按钮必然先让编辑器失焦，一失焦就藏，按钮会在 `click` 到达之前消失（ADR 0015）。**不做，而不是没做** | 低。只会让浮层多留一会儿，不涉及数据。改法是监听 `.editor-area` 的 `blur` 并在 `relatedTarget` 落在浮层内部时放过 —— 但这个判断在 jsdom 里验证不了，容易写成「真机上偶发点不动」，所以等有人真的抱怨再说 |
| **浮层的屏幕几何只有人眼能验** | `coordsAtPos()` 依赖布局引擎，jsdom 返回全 0（`src/test/jsdom-gaps.ts` 只能补成空矩形）。测试钉住的是「空选区返回 null」「不抛错」 | 低（但确实没验）。要在 `npm run desktop` 里目视确认：浮层摆在哪、会不会压住文字、贴边时有没有翻到下方。与 V3 同类 —— 测试环境的结论不能替代真机结论 |
| **空段落套进容器后会序列化成 `<br />`** | Milkdown 的 `remarkPreserveEmptyLinePlugin` 把空段落序列化成一个 `<br />` 的 html 节点当**空行占位符**：mdast 里空段落序列化出来什么都没有，没有占位符的话「一个空引用」存盘再打开就消失了。**往返稳定**（`> <br />` → `> <br />`），只影响「插入了但一个字没打就保存」，打字（`> 甲`）之后占位符就没了 | 低。**不是 M4 引入的** —— 手敲 `> ` 触发输入规则就能造出同样产物。两条改法都有真实损失（关掉插件 = 放弃空行保留；只省掉纯占位符容器 = 空引用存盘后消失），所以现在不动。详见 [ADR 0016](./decisions/0016-slash-menu.md) 代价 2 |
| **主包体积**（886 kB → 现在更大） | 桌面端从本地磁盘加载，与网页端性质不同 | 低。拆分方案已明确：`React.lazy` 加载内核，外壳首屏目标 < 200 kB |

| **图片没有尺寸调整与右键菜单** | 拖动改宽高、`width` 属性、复制路径、在文件管理器里打开 —— 这些都是纯交互层的增量，不需要新的内核能力。M6 先把「能粘进来、存得住、看得见」这条主干打通 | 低。等有人真的需要在文档里控制图片大小时再做。难点在「改了尺寸之后怎么存」—— 要么写进 Markdown 的 HTML 形式（会牺牲可移植性），要么只在预览里生效（那就不算功能） |
| **图片的显示观感与灯箱只有人眼能验** | 同 M3–M5：jsdom 没有布局引擎，也不解码图片 | 低（但确实没验）。要在 `npm run desktop` 里确认：占位的虚线框大小、加载中那块底色的位置、灯箱在大图 / 长图上的表现、深底与浅色主题的对比度 |
| **图片走 `data:` URI 而非 `asset:` 协议** | `asset:` 要打开 `app.security.assetProtocol` 并配一份路径白名单 —— 那是一块需要长期维护的安全面。`data:` 走已有的 `read_binary_file`，权限收口在同一个地方。代价（base64 大 1/3、常驻 DOM）由上游 24 MB 的单文件上限兜住 | 低到中。**重审条件**：一份文档里几十张大图、打开明显变慢时，重新评估 —— 届时要一并给出白名单方案，而不是只把开关打开。见 [ADR 0018](./decisions/0018-m6-images.md) |

| **设置页的版式与长列表滚动只有人眼能验** | 同 M3–M6：jsdom 没有布局引擎，`getBoundingClientRect()` 全是 0，也**没有滚动**。测试钉住的是「工具栏能开、Esc / 点遮罩能关、点内部不关、快捷键表由注册表派生、改主题立即生效且落盘、版本号来自构建期常量」——全是**行为**，不是**观感** | 低（但确实没验）。要在 `npm run desktop` 里目视确认：四段分组的分隔是否清楚、开关的选中态在深浅两套主题下都看得见、快捷键表在窗口变窄时会不会溢出、以及**清除位置记忆**那个按钮的破坏性提示是否足够显眼。见 [ADR 0021](./decisions/0021-m9-position-memory-and-settings.md) |
| **位置记忆的实际手感只有人眼能验** | 位置（光标偏移 + 滚动比例）的**往返**在单测里钉得很死（三个内核各一条 + `position.test.ts` 10 条 + `positions.test.ts` 21 条），但「**回到哪儿才算对**」是个观感问题：`textLength` 对不上时只恢复滚动、不对齐光标，这在实际文档上落点是否符合直觉，只有真机能判断 | 低到中。要在 `npm run desktop` 里确认三件事：① 长文档读到一半切走再切回，落点是否就是刚才那一段；② 在**源码模式**与富文本之间来回切，滚动比例是否稳定（两边 `textLength` 口径不同，只在同一视图内保证）；③ 编辑完立刻关窗（`beforeunload` 兜底那一次写盘）再打开，位置有没有丢。与 V3 同类 —— **测试环境的结论不能替代真机结论** |

### V3 怎么跑（2026-09-30：材料与探针已备齐）

**为什么不能自动化（限定版）。** jsdom 没有布局引擎、没有真实绘制与计时，项目里也没有 benchmark 脚手架。
**合成事件**也插不进字符 —— ProseMirror 不监听 `keydown`，它靠 `beforeinput` + `MutationObserver` 派发事务，
所以 `dispatchEvent(new KeyboardEvent('keydown'))` 走不到那条链。
（**但「自动化打字」并非绝对不通**：Playwright 的 `keyboard.type()` 走的是 CDP 的 `Input.dispatchKeyEvent`，
那是浏览器眼中的**可信输入**，会完整走一遍输入管线。代价是要装一份 Chromium，且无头模式下的绘制读数不可信。
本项目目前走的是「材料与读数自动、敲键盘手动」。）

**材料** —— `node scripts/make-v3-longdoc.mjs`（产出在 `docs/samples/`，已进 `.gitignore`）：

| 文件 | 内容 |
|---|---|
| `v3-longdoc.md` | 15426 字 / 765 行 / 23419 字符，含 11 个代码块（8 种语言）、5 个 mermaid、公式与表格 |
| `v3-longdoc-nocode.md` | 对照组：**节数与字符数与上者对齐**（同为 33 节，字符数差 2.7%），只差「有没有 `code_block`」 |

两份构成一次干净的 A/B，差值就是 `codeHighlightPlugin` 每次改文档**整篇重跑 highlight.js** 的净成本。
（A/B 的方向别做反：把代码块的语言名删掉**不是**去掉高亮 —— `highlightCode()` 对无语言输入会走
`hljs.highlightAuto()`，那是**更贵**的一条路。要归因就得让 `code_block` 节点本身消失。）

**自动化（2026-09-30 补齐）** —— `node scripts/v3-run.mjs --file <文档> --mode rich|source|split --at start|middle|end`
（还有 `--provider desktop|browser`、`--keys`、`--interval`、`--fresh`、`--out`）。
它用 CDP 驱动真实 Chromium：`Input.dispatchKeyEvent`（带 `text`）就是 Playwright `keyboard.type()` 走的那条路，
是**浏览器眼中的可信输入**，会完整走一遍 `beforeinput` → `MutationObserver` → `input` 管线；
探针整份 `Runtime.evaluate` 进去，**不需要人粘贴**。汇总用 `node scripts/v3-summary.mjs`。

一次场景 = 一条命令。这是必要的：V3 是「视图 × 落点 × 文档」的笛卡尔积，改一次内核就要重跑一遍，
而手工流程每次都要重新对齐姿势 —— **姿势不一致，读数就不可比**。

**两条路，一个校验锚点。**

- `--provider desktop`：真 WebView2。需要给窗口配置 `additionalBrowserArgs` 带上 `--remote-debugging-port=9222`
  （`scripts/v3-dev.conf.json` 是覆盖式配置）。**`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` 环境变量没有用** ——
  `wry` 无条件调用 `options.set_additional_browser_arguments(...)`（没给就填默认值），
  而 WebView2 的约定是「宿主显式设了这个属性就忽略环境变量」。
- `--provider browser`：`npm run dev` + 真实 Edge。**同一个 Chromium 引擎、同一套布局与绘制**，
  差的只是宿主外壳；文档来源换成浏览器预览的内存虚拟盘，用 CDP 的文件选择拦截喂文件
  （顺带证明了「打开文件」那条链路是通的）。
  **必须关掉 Windows 的原生遮挡检测**：`--disable-features=CalculateNativeWinOcclusion,msEdgeSidebarV2`
  `--disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling`。
  少了这几条，窗口被别的窗口盖住时 Chromium 会**挂起渲染管线**，`paint` 会窜到 1144ms / 1408ms ——
  而那**不像 0 那样一眼可疑**，只会被读成「这一档特别慢」。
- **校验锚点**：人工在真 WebView2 上跑的第一轮，`paint` p50 = **32ms**；Edge 这条路跑出来也是 **32ms**，
  刷新率同为 120Hz、长任务同为 0。**两条路对得上，才说明这条路可信。**

**主判据（2026-09-30 修正）：`beforeinput` → 出字那一帧。**

| 读数 | 含义 | 误差 |
|---|---|---|
| `输入延迟` | **主判据**。`beforeinput` 的 Event Timing 条目：从事件到**字上屏**的那一帧 | **无** |
| `sync` | `beforeinput` → `input`：浏览器完成原生插入 + 内核在这一段里同步跑掉的成本 | **无** |
| `paint` | `input` → 它之后的下一次绘制 | **无** |
| `longtasks` | 主线程上 > 50ms 的独立任务 | **无** |

**为什么改判据**：初版拿 `paint`（`input` → 下次绘制）当判据，那是**低估** ——
`input` 事件在 `beforeinput` 之后才发，于是「浏览器插入 + 内核同步响应」那一整段被漏在了外面
（富文本档实测 **34ms**，占总量一半以上）。改用 `beforeinput` 自己的 Event Timing 条目，
它的 `duration` 定义就是「beforeinput → 处理完之后的下一次绘制」，正好是要的那个数。

**`sync` 与 `paint` 不能相加。** 它们量的是**不同的那次绘制**：`beforeinput` 的条目量到「字上屏」那一帧，
`input` 的条目量到它**之后**的下一次绘制（内核把原生插入的文本改写回自己的模型之后）。
实测 `sync 34 + paint 40 = 74ms`，而同一批数据的 `输入延迟` 只有 **48ms** —— 差的那 26ms 是内核的收尾工作，
**用户在 48ms 时已经看见字了**。

**主判据被独立验证过**：拿「实测按键间隔 − 间隔设定值」去对 `输入延迟`，六档全部吻合在 1–8ms 内
（49/48、80/72、49/48、18/16、18/16、18/16）。这是一条与 Event Timing 完全无关的旁证。

**两个必须知道的读数性质：**

- Chromium 把 Event Timing 的 `duration` **粗化到 8ms 的整数倍**（实测取值只有 16/24/32/40/64/88…），
  所以**「≤ 50ms」实际等价于「≤ 48ms」**，而且 p50 与 p95 常常是同一个数（24/24、40/40）——
  百分位在这个粒度上不总是有分辨力，读数要连着看。
- **量程下限是 16ms**：另开一个 `durationThreshold: 16` 的观察器，收到的条目数与 `0` 的**完全相同**，
  说明 Chromium 把 `durationThreshold` 钳到了最小 16（规范里就写的 16）。
  于是源码 / 分屏档报出来的 16ms 是**顶到量程**，真实值 **≤ 16ms**，不能读成「正好 16ms」。

**绝对读数随机器负载整体漂移 —— 判据必须写明测量环境。**
同一份文档、同一个视图、同一台机器，隔了二十分钟再跑：`sync` 从 18.3 变成 34、源码档从 4.1 变成 7.3 ——
**两个完全不同的内核按同一个比例（约 1.8×）一起变慢**，说明漂的是环境不是代码
（这台机器上同时跑着几套语言服务和一个前端 dev server）。
这对 V3 是要害：判据是「≤ 50ms」，而读数能整体翻倍 —— **判定会随负载翻面**。所以：

1. **同批次内部**的横向比较（视图之间、落点之间）可信；
2. 跨批次比绝对值必须按**校准基准**归一化（`v3-run.mjs` 每轮前后各跑一次页面内固定 CPU 负载）；
3. 记录结论时**必须写上当时的校准基准**，否则这个数字没有意义。

报告里还有一行**自动归因**，因为两个方向要改的地方完全不同：

| 现象 | 说明瓶颈在 |
|---|---|
| `sync` 达标、`输入延迟` 不达标 | 样式 / 布局 / 绘制（或掉帧）—— **不是 JS** |
| 两者都不达标 | 才轮到 `plugin.ts` 里那几条 O(n) |

报告里同时给出**刷新率**：它决定「掉一帧」值多少毫秒（同样掉 4 帧，60Hz 是 67ms、144Hz 只有 28ms）。

> **踩过的坑（2026-09-30，第一次实测照出来的）**：探针初版用**双 `requestAnimationFrame`**
> 估「画完了没有」，注释里还写着「偏差 0–16.7ms」—— **那句话是错的**。rAF 回调跑在绘制**之前**，
> 所以「双 rAF」意味着至少等到第 2 帧，读数是 `实际耗时 + 1~2 帧`（60Hz 下是 **+16.7~33.3ms 的固定底噪**）。
> 第一次实测拿到 `paint.p50 = 35.5ms`，而同批数据 `sync.p50` 只有 17.2ms、83 次输入只产生 4 条长任务 ——
> 35.5 几乎就是底噪本身，一份实际几毫秒的输入被报成了「超出 50ms 判据」。
> 已改用 Event Timing API（`durationThreshold` **必须显式设成 0**，默认 104ms 只报慢的），双 rAF 降为回退路径。
> 教训：**测量工具的误差必须被量化，否则它会把结论带偏，而且偏的方向看起来「很合理」**。
>
> 同类的第二例：**判据本身选错了**。`paint` 是真实读数、没有误差，但它量的是**半条链路**。
> 一个「没有误差」的读数仍然可能是**错的指标** —— 这是比测量误差更难发现的一类错误。

**归因矩阵**（「过不过」只是第一问，「**是谁慢**」才决定改哪儿）：

| 对照 | 隔离出的成本 |
|---|---|
| 文档**开头**打字 vs **中部/结尾**打字 | `cursorReporterPlugin.positionOf` 的 `textBetween(0, safe)` —— 成本与光标位置成正比 |
| `v3-longdoc.md` vs `v3-longdoc-nocode.md` | `buildDecorations` 里那次整篇重跑 highlight.js |
| 富文本 vs 源码模式 | 整条 Milkdown 链路（源码侧是 CodeMirror，理论上无这项成本） |
| 开头与结尾一样慢、且去掉代码块还是慢 | 嫌疑落到 `markdownEmitPlugin` 的整篇 `serialize` |
| 分屏 vs 富文本 | 右栏整篇重解析（`PREVIEW_SYNC_DELAY_MS` 防抖之后的那一次） |

**`v3-run.mjs` 自己会挡住三种「假绿」**，都不会给你一份能误读的数据：

1. **输入没进去** —— 装探针之前先挂一个独立的 `beforeinput` 计数器，敲一个字符读计数，为 0 就报错退出
   （此时读数会全是 0，而 **0 看起来像「性能极好」**）；
2. **测量期间页面被隐藏/遮挡** —— 全程跟踪 `visibilitychange`，丢过前台就判失败、**不落盘**
   （此时 `paint` 会变成上千毫秒，而那种数字**不像 0 那样可疑**）；
3. **点击没落进编辑器** —— 滚动后取「内容矩形 ∩ 可见矩形」的中心再点（第一版取的是**内容矩形的中心**，
   而一份 2 万字文档的内容高约 4.7 万像素，`--at start` 算出来的 y ≈ 23500px 在视口外，点击落空、焦点丢失），
   并断言点击后 `document.activeElement` 在编辑器内。

**一并测原文保真。** 这正是 horseMD 最值钱的差异点，我们从未测过。做法：打开一份真实 md →
**不动任何内容** → 保存 → `git diff` 那份文件。已知会被改写的有 setext→ATX、行尾空白收敛、
`~~~`→```、`___`→`***`、硬换行两空格→反斜杠（见 `plugin.ts` 的注释），
**以及清单里没写的两条：无序列表 `-` → `*`、表格分隔行被按列宽重排**（后者有测试，
见 `markdown-core.test.ts` 的「序列化器的规范化行为」；前者两处都没写）。
实测一份 15426 字的真实文档在「打开即序列化」这一步被改写 **402 个字符（1.7%）**。

### V3 实测记录（2026-09-30，第一轮）

**条件**：`v3-longdoc-nocode.md`（对照组，22788 字符 / 480 行，**不含代码块**）、**富文本**视图、
光标在**中部**、120Hz 显示器（一帧 8.3ms）、91 次真实输入。

| 读数 | p50 | p95 | max |
|---|---|---|---|
| `sync`（内核 JS：序列化 + 插件遍历 + setState） | **14.7** | 16.7 | 20 |
| `paint`（事件 → 下一次绘制） | **32** | **64** | 88 |

- **长任务 0 条** —— 主线程上 >50ms 的任务一条都没有。
- 第一轮报出来的 `paint.p95 = 104ms` 是**探针自己的假信号**（5 条配不到 `input` 标记的
  Event Timing 条目），已剔除，见文末「探针的两处误差」。

**结论：`sync` 明确达标；`paint` 落在判据的边界上，取决于口径。**

**判据口径待定 —— 这是要拍板的第一件事。** ADR 0004 只写了「输入延迟 ≤ 50ms」，**没写百分位**：

| 口径 | 读数 | 判定 |
|---|---|---|
| p50 ≤ 50ms（「多数输入跟手」） | 32ms | ✅ 通过 |
| p95 ≤ 50ms（「95% 的输入跟手」） | 64ms | ❌ 不通过 |

建议**以 p50 为主判据、p95 作尖峰监控**：50ms 说的是「敲下去字就出来」的常态手感；
p95 里混着系统抖动（GC、OS 调度、别的标签页），而 120Hz 的流水线**本身**就要 1–2 帧
（8.3–16.7ms）—— 那是任何编辑器都躲不掉的物理下界。**因为 5% 的输入超过 50ms
就去掉即时渲染、换成分栏预览，是用一个确定变差的体验去换一个更小的尾巴。**

> **但这是产品决策，不是技术结论。** 定下来之后要回填 ADR 0004 的状态行。

**已排除的嫌疑**（都做了量化）：

| 嫌疑 | 实测 | 结论 |
|---|---|---|
| `DocumentPane` 的 `stats`：每次按键 `analyze(全文)`（`for...of` 全码点遍历 + 一次全局正则） | **0.53ms**（22788 字符；其中遍历 0.37、正则 0.04） | **不是瓶颈**，与 `sync` 差 30 倍 |
| 高亮重建（`buildDecorations` 整篇重跑 highlight.js） | 本轮文档**不含代码块**，这条根本没跑 | **未验** —— 要用完整版再测一轮 |

**顺带量出来的两个数字**（不在每次按键的路径上，但都是用户能感觉到的停顿）：

| 操作 | 耗时（jsdom，22788 字符） | 出现在哪 |
|---|---|---|
| `setMarkdown(全文)` = 解析 + 事务派发 + 序列化 | **118.6ms** | 切视图、**分屏的内容同步**、重新加载 |
| 首次创建编辑器 | **717ms** | 打开一份 2 万字文档 |

> `setMarkdown` 那条要特别注意：分屏的 `PREVIEW_SYNC_DELAY_MS = 160ms` 防抖之后，
> 右栏走的正是 `setValue` → `setMarkdown`。也就是**停止打字约 280ms 后会有一次 118ms 的卡顿**。
> 它不影响打字本身（不在按键路径上），但会在每次停顿处顿一下。
> 这是 **jsdom** 的数字，量级可参考、绝对值不能直接当浏览器里的。

**探针的两处误差（都踩过，都已修）**：

1. **双 `requestAnimationFrame` 估「画完了没有」** —— rAF 回调跑在绘制**之前**，
   「双 rAF」= 至少等到第 2 帧，读数含 **1~2 帧的固定底噪**（60Hz 下 +16.7~33.3ms）。
   第一轮把 `paint.p50` 报成 35.5ms，几乎就是底噪本身。**已改用 Event Timing API**
   （`entry.duration` 的定义就是「事件 → 下一次绘制」，无帧对齐误差）。
2. **`buffered: true` 捞进来的历史条目 / 配不到标记的 entry** —— 上一版把它们当样本收下
   （`inputType: 'unknown'`、`gap: 0`），于是**躲过了冷启动过滤**，把 `paint.p95` 从 64ms 污染成 104ms。
   它们的 `sync.n` 是 0，本该一眼看出不对。**已改成丢弃并计数**（报告里的「丢弃的无关条目」）。

**下一步（按优先级）**：

1. **源码视图**跑同一套 —— 这是「分栏预览方案」的**输入侧成本**，是判据的另一半，现在完全没有数。
2. **完整版**（含代码块）跑同一套 —— 与对照组之差就是高亮重建的净成本。
3. **文档开头 vs 中部** —— 隔离 `cursorReporterPlugin.positionOf` 的 `textBetween(0, safe)`（成本与光标位置成正比）。

**测完写回哪里**：本表 V3 行 + ADR 0004 的「重审条件」与状态行（部分待定 → 已定）。
**命中后怎么办**：ADR 0004 的原文是「换成分栏预览方案，而不是硬优化」——
而 **M10 刚做的分屏正是这个方案的雏形**（ADR 0022），不是从零开始。

### V3 实测记录（2026-09-30，第二轮 —— 主判据修正后的完整八档 + 五个归因变体）

**条件**：`v3-longdoc.md`（15426 字 / 765 行 / 23419 字符，含 8 个高亮代码块 + 5 个 mermaid 围栏）
与对照组 `v3-longdoc-nocode.md`；真实 Edge（Chromium 151）+ `npm run dev`；120Hz（一帧 8.3ms）；
每档敲 60 键、间隔 60ms；**13 档在同一个批次内跑完**；**校准基准 30.2–33.5ms（离散 11%）**；
全程 `visibilityState = visible`、无可见性中断；每档敲入 60 键、`beforeinput` 计数均为 60（**输入一个没丢**）。

| 视图 | 落点 | 文档 | 输入延迟 p50/p95/max | sync p50 | paint p50 | >50ms | 长任务 | 判定 |
|---|---|---|---|---|---|---|---|---|
| rich | start | 完整版 | **72 / 88 / 88** | 63.4 | 72 | 60 / 60 | 56 条（最长 82） | ❌ |
| rich | middle | 完整版 | **48 / 56 / 64** | 34.2 | 40 | 6 / 60 | 1 条（55） | ❌ |
| rich | end | 完整版 | **48 / 56 / 64** | 35.4 | 48 | 13 / 60 | 3 条（52） | ❌ |
| rich | middle | 对照组 | **40 / 64 / 64** | 34.1 | 40 | 10 / 60 | 5 条（53） | ❌ |
| rich | start | 对照组 | **48 / 64 / 80** | 38.1 | 48 | 16 / 60 | 3 条（68） | ❌ |
| source | start | 完整版 | **16 / 16 / 32** | 6.8 | 16 | 0 / 51 | 0 条 | ✅ |
| source | middle | 完整版 | **16 / 24 / 32** | 7.0 | 16 | 0 / 57 | 0 条 | ✅ |
| source | end | 完整版 | **16 / 16 / 24** | 6.6 | 16 | 0 / 49 | 0 条 | ✅ |
| split | middle | 完整版 | **16 / 24 / 24** | 7.3 | 16 | 0 / 57 | 1 条（91） | ✅ |

**结论一：富文本档没有余量，源码 / 分屏档有 3 倍余量。**

富文本档 `输入延迟` p50 落在 **48ms**，判据线是 50ms（有效 48ms，因为读数被粗化到 8ms 的整数倍）——
**它正好压在线上**。而源码 / 分屏档是 **16ms，且是顶到 16ms 量程下限**（真实值 ≤ 16ms），
即「比测量能力还快」。

**这一档的判定会随机器负载翻面。** 上一批次（负载轻，见「第二轮之前的中间批次」）里同一个场景
`rich / middle / 完整版` 的 `sync` 是 18.3ms、`paint` 是 24ms；本批次是 34.2 / 40 —— 差 **1.8 倍**，
而两个内核按同一比例一起变慢，说明漂的是环境。按这个比例折算，**轻载下富文本档的 `输入延迟`
约 27ms，是达标的**。所以「富文本档达标了吗」这个问题，**在没有写明测量环境时无解**。

**结论二：落点影响很大 —— 文档开头比中部/结尾贵 1.5 倍。**
富文本档 `rich / start` 是 **72ms p50、88ms p95，60 次输入里 60 次超过 50ms、56 条长任务** ——
这是唯一一档**明显**不合格的。中部与结尾都是 48ms。

**结论三：代码块的净成本约 8ms（中部）/ 24ms（开头）。**
完整版 vs 对照组：`middle` 48 vs 40、`start` 72 vs 48。
（对照组并非「没有 `code_block`」—— 它的 5 个 mermaid 围栏两边都有，换掉的只是 8 个高亮代码块。
这一点 `make-v3-longdoc.mjs` 的注释写成了「只差有没有 `code_block`」，**不准确**，待修。）

**结论四：分屏几乎等于源码（16 / 16）。**
左栏是 CodeMirror、右栏是只读预览，`PREVIEW_SYNC_DELAY_MS = 160ms` 防抖之后右栏整篇重解析 ——
**这些都没有出现在按键路径上**：长任务 1 条（91ms）、其余全绿。
上一轮记的「分屏停顿 118ms」是 **jsdom** 里 `setMarkdown(全文)` 的数字，真机上的表现远好于它。

**结论五（未定位）：首块是 H1 时明显更贵，机制不明。**
五个变体（只改文档里的一处，其余字节完全一致；都是把 `v3-longdoc.md` 改一处生成到 `.v3-out/`，
不进版本库 —— 改法就是下表第二列，逐字可复现）：

| 变体 | 改了什么 | 本批次 输入延迟 p50 | 轻载批次 sync p50 |
|---|---|---|---|
| `probe-para-first.md` | 第 1 行的 `# ` 去掉（首块由 H1 变段落） | **56** | 18.6 |
| `probe-h2-first.md` | 第 1 行改成 `## `（首块由 H1 变 H2） | **56** | 27.6 |
| `v3-longdoc.md`（原样） | 首块是 H1 | **72** | 28.5 |
| `probe-heading-mid.md` | 中部落点由列表项改成 H2 | 48 | 18.5 |
| `probe-h1-mid.md` | 中部落点由列表项改成 H1 | 40 | 18.7 |

**中部放 H1/H2 都不慢**（40–48，与列表项、表格行同档），所以不是「标题节点本身贵」。
两批次都指向「**首块是 H1 时最慢**」，但「首块是 H2」在两批次里不一致（本批次与段落同速、轻载批次与 H1 同速）——
**机制未定位**。已排除的：标题没有特殊 CSS（无 `text-wrap` 之类）、外壳没有面包屑、
`OutlinePanel` 按 `text` 变化重算、与落点无关。**这条不阻塞 V3 的结论**（最慢的那一档是 72ms，
把首块换成段落也只是降到 56ms，仍然超出），但值得单独查。

**判据口径：现在这个问题变小了。** 第一轮争的是「p50 还是 p95」（当时 p50 32 达标、p95 64 不达标）。
现在两档读数的 p50 与 p95 往往只差一档（48/56、16/24）—— 因为读数被粗化到 8ms 粒度，
**百分位在这个粒度上本来就没有多少分辨力**。真正决定判定的是**测量环境**，不是百分位。

**下一步（按优先级）**：

1. **查「首块是 H1 更贵」** —— 唯一一条未定位的成本，也是唯一一档明显不合格的场景。
2. **压富文本档的 `sync`（34ms）** —— 它在判据里占一半以上。已知的整篇级工作：
   `markdownEmitPlugin` 的整篇 `serialize`、`buildDecorations` 的整篇重跑 highlight.js、
   `cursorReporterPlugin.positionOf` 的 `textBetween(0, safe)`。逐条量化即可定位。
3. **原文保真**（仍未做）。
4. **V1 / V2**（仍未跑）。

**测完写回哪里**：本表 V3 行 + ADR 0004 的「重审条件」与状态行。
**命中后怎么办**：ADR 0004 的原文是「换成分栏预览方案，而不是硬优化」——
而 **M10 刚做的分屏正是这个方案的雏形**（ADR 0022），不是从零开始。
**而且这一轮给了一个新的、更硬的数字**：源码内核（CodeMirror）比富文本内核（Milkdown）
**快 3 倍（16ms vs 48ms）**，这与 horseMD 正在评估的「源码优先 Live Preview」方向一致 ——
它不再是「感觉上更轻」，而是有实测支撑。**但换架构是大动作，不构成充分理由**：
还要看原文保真（源码优先天然解决 serializer 改写未编辑源码的问题）与 V1 / V2 的结论。

### V3 实测记录（2026-09-30，第二轮之前的中间批次）

第一轮之后、主判据修正之前，用旧的 `paint` 口径跑过一次完整的 13 档。它的价值是**留下了负载漂移的证据**：

|---|---|---|---|
| rich / middle / 完整版 | 18.3 | 34.2 | 1.87× |
| rich / start / 完整版 | 28.5 | 72.0（输入延迟） | — |
| source / middle / 完整版 | 4.1 | 7.0 | 1.71× |

两个完全不同的内核按同一个比例变慢 —— **这是「漂的是环境」的直接证据**，

### V4 的结论（2026-09-29，M5 落地时得出）

**结论：成本可接受，自研；不评估 Crepe。**

M5 已经把表格的可视化编辑做出来了（加行加列、删行删列、设对齐、插入最小表格），
实现是「一个纯函数 `describeTable()` + 一个 React 工具条 + 装饰层」，
**没有引入任何新依赖**。也就是说 V4 原本担心的「成本明显超出预算」并没有发生 ——
真正的成本不在 UI，而在**读懂 Milkdown 的表格 schema**（见下）。

同时，「改用 `@milkdown/crepe`」这个备选分支**被 ADR 0017 关闭了**：
Crepe 开箱的表格 UI 正是建立在 `@milkdown/components` 上的，而那是 Vue 3。
采纳它等于采纳 ADR 0017 已经否掉的那条路（第二套 UI 框架 + 高亮管线分叉）。

三条在实现过程中**实测**到的、读文档读不出来的约束（已写进 ADR 0017）：

1. 最小表格是 **2 行**（表头行 + 至少一个正文行）；**空表头行会在序列化时被静默丢掉**；
2. 对齐是**按列、且由表头决定**的 —— 设对齐必须**写整列**，只写光标所在格会在存盘时丢；
3. `TableRole` 里**没有 `header_row`**，表头行与正文行共用 `row`。

**仍未做、且属于 V4 范围的剩余部分**：鼠标拖拽改列宽、表格悬浮 `+` 按钮、
单元格内快捷导航（Tab 跳格是 ProseMirror 自带，跨行插入未做）。
这些**不需要新的内核能力**，是纯交互层的增量，可以随时补 —— 所以不再挂着一个待验证项。
