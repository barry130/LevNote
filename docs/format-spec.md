# 轻笺 · 格式与互操作规范 v0

状态：**草案（v0）** · 实现对应 `packages/interop-spec` · 最后更新见 git

---

## 0. 这份规范要解决什么

轻笺把四类文档放在同一个工作区里：Markdown、代码/文本、思维导图、draw.io 图表。
它们 **不是四种「视图」，而是四类一等公民**：每一类都能独立新建、编辑、保存成自己的原生格式。

剩下的问题是：**它们怎么互相引用、互相嵌入、互相转换**。
本规范只定义这件事。它不定义编辑器界面、不定义渲染效果。

一条贯穿全文的原则：

> **文件在轻笺之外也必须活得下去。**
> 任何一份轻笺写出的文件，用记事本打开应该是可读的；
> 用别的 Markdown 渲染器打开，内容应该还在，而不是变成一堆乱码或空白。

## 1. 三个互操作层级

| 层级 | 名称 | 语义 | 存的是什么 | v0 状态 |
|---|---|---|---|---|
| L1 | 引用 reference | 文档里放一个「指针」，真实内容在旁边的独立文件里 | 路径 + 元数据 | ✅ 采纳为默认 |
| L2 | 就地编辑 inline-edit | 在主文档里直接编辑被引用文档，保存回原文件 | 路径，无副本 | ✅ 采纳 |
| L3 | 结构变换 transform | 把一个 Markdown 片段提升成独立的 `.md` 文件，或反向拉平 | 无（一次性操作） | ⏳ P4 |

**L1 是默认形态，L3 是例外。** 一个 20 行的时序图不值得单独开一个文件，
但一个 300 节点的思维导图塞进 Markdown 里会毁掉可读性与 diff 可读性。
所以例外要存在，但不能变成常态 —— 出现频率是设计的约束条件。

## 2. `doc-block` 语法

### 2.1 为什么是围栏代码块

语法载体是一个 **普通围栏代码块**，信息串固定为 `doc-block`：

````text
```doc-block
id: arch
kind: diagram
mode: reference
src: diagrams/arch.drawio
title: 整体架构
---
```
````

选它的理由是**降级不崩**：任何不认得 `doc-block` 的 Markdown 渲染器，
都会把它当成一个普通代码块渲染出来。用户看到的是元数据，
而不是一片空白或半截 HTML。这在「把文件发给别人」时至关重要 ——
而轻笺是纯桌面应用、没有分享链接，文件外发是唯一的协作方式。

### 2.2 结构

```
<围栏>doc-block <换行>
<属性区：若干 key: value 行> <换行>
---            <属性区结束标记>
<载荷区（仅 mode: inline 时非空）>
<结束围栏>
```

- **围栏**：≥3 个反引号。载荷里若出现「整行都是反引号」，围栏自动加长到比它多 1 个。
- **属性区**：`key: value`，键为小写 ASCII，可用连字符。空行忽略。
- **结束标记**：一整行恰好是 `---`。**必须存在**，即使载荷为空 —— 无歧义比省一行重要。
- **载荷区**：`---` 之后直到结束围栏之间的一切，**逐字节原样**。

### 2.3 属性参考

| 键 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `id` | ✅ | `[A-Za-z0-9][A-Za-z0-9_-]{0,63}` | 文档内唯一。用于交叉引用与去重 |
| `kind` | ✅ | `markdown` \| `code` \| `mindmap` \| `diagram` \| `image` \| `text` | 决定用哪套内核打开 |
| `mode` | ✅ | `reference` \| `inline` | 默认语义是 `reference` |
| `src` | `reference` 时 ✅ | 相对路径 | 一律正斜杠，相对于**当前文档所在目录** |
| `title` | ❌ | 任意单行文本 | 展示用标题 |
| 其它 | ❌ | 任意单行文本 | **原样保留**，见 §5 |

`kind: text` 是兜底：遇到不认识的 `kind` 时按它处理，内容一个字不丢。

### 2.4 内联示例（载荷里含围栏）

````text
````doc-block
id: snippet-1
kind: code
mode: inline
---
```python
print("hello")
```
````
````

外层用了 4 个反引号，因此内层的 3 个反引号不会提前结束块。
这跟 CommonMark 处理嵌套围栏的规则一致，用户无需学新东西。

## 3. 解析规则（可实现的精确版本）

1. 逐行扫描。一行若匹配 `^(`{3,})\s*doc-block\s*$`，视为块开始，记下围栏长度 `N`。
2. 向后找属性区结束行：一整行 trim 后等于 `---`。
   - 若中途遇到「反引号数 ≥ `N` 且整行只有反引号」的行 → 判定 `MISSING_TERMINATOR`。
3. 从结束标记之后继续找结束围栏：整行只有反引号且数量 ≥ `N`。
   - 找不到 → 判定 `UNTERMINATED_FENCE`，块延伸到文末。
4. 载荷 = 结束标记行尾 到 结束围栏行首 之间的**原文切片**，不做任何规范化。
5. 块的 `range` 右端取**结束围栏这一行的内容末尾**，不含其后的换行。
   块与块之间的空行不属于任何块，归调用方所有。

第 5 条是 `spliceBlocks` 能原样还原整篇文本的前提，不要"顺手"改成包含换行。

## 4. 序列化规则

- **未改动的块**：直接回填 `raw`，不要重新生成。这是「打开文件不产生 diff」的保证。
- 属性输出顺序固定：`id` → `kind` → `mode` → `src` → `title` → 其余键按字典序。
  顺序固定是刻意的：同一份内容永远产出同样的文本，git diff 才有意义。
- 值含首尾空白或引号时自动加双引号，避免被 `trim` 吃掉。
- **行尾**：默认输出 `\n`；调用方可用 `lineEnding` 指定目标行尾。
  序列化器不自己猜 —— 行尾是**文件属性**，由知道目标文件的文档模型传入。
- 序列化前把载荷统一压成 `\n` 再整体替换，否则载荷里既有的 `\r\n` 会被二次转义成 `\r\r\n`。

## 5. 向前兼容

**更高版本写的键，低版本必须原样保留。** 解析时落到 `attrs.extra`，
序列化时照原样写回，同时给一条 `UNKNOWN_KEY` 提示（可能是拼写错误，也可能是新特性）。

这条规则的实际意义：用户在两台机器上装了不同版本的轻笺，文件来回拷不会掉信息。
**没有这条，任何新增属性都是一次单向的数据损失。**

## 6. 校验规则

校验是纯函数，只做静态检查，不碰文件系统。

| 码 | 级别 | 触发条件 |
|---|---|---|
| `MISSING_ID` / `BAD_ID` | error | id 缺失或不合法 |
| `DUPLICATE_ID` | error | 同一文档内 id 重复 |
| `UNKNOWN_KIND` | error | `kind` 不认识（按 `text` 兜底处理，内容不丢） |
| `UNKNOWN_MODE` | error | `mode` 不认识（按 `reference` 处理） |
| `MISSING_SRC` / `EMPTY_SRC` | error | reference 模式缺 `src` |
| `ABSOLUTE_SRC` | error | `src` 是绝对路径 —— 换台机器或发给别人必失效 |
| `BACKSLASH_IN_SRC` | warning | `src` 用了反斜杠 |
| `PATH_ESCAPES_ROOT` | warning | `src` 向上跳出了文档目录，分享时容易漏文件 |
| `MISSING_TERMINATOR` | error | 缺 `---`，无法分辨属性与内容 |
| `UNTERMINATED_FENCE` | error | 缺结束围栏，可能吞掉后面的正文 |
| `HEADER_LINE_IGNORED` | warning | 属性区里有非 `key: value` 行 |
| `UNKNOWN_KEY` | warning | 见 §5 |
| `PAYLOAD_IN_REFERENCE` | warning | reference 模式下还写了载荷 |
| `EMPTY_PAYLOAD_IN_INLINE` | warning | inline 模式但载荷为空 |
| `IMAGE_MUST_REFERENCE` | warning | 图片被内联 —— 别把二进制塞进 Markdown |

**error 与 warning 的区别**：error 表示「照这样写下去，内容会丢或会失效」；
warning 表示「能工作，但你大概不是这个意思」。UI 上 error 必须显眼，warning 可以安静。

## 7. 四类文档的原生格式

| 类型 | 扩展名 | 格式 | 说明 |
|---|---|---|---|
| Markdown | `.md` `.markdown` | CommonMark + GFM 子集 | 上游用 Milkdown；`doc-block` 作为扩展语法 |
| 代码/文本 | 按语言 | 纯文本 | 不做格式化，不做自动换行改写 |
| 思维导图 | `.mindmap` | JSON，见 §7.1 | 与 `doc-block` 同目录，互为引用 |
| draw.io 图表 | `.drawio` | draw.io 原生 XML | **逐字节透传**，见 §7.2 |

### 7.1 `.mindmap`（文件格式 `version` = 1）

> **一处口径统一（2026-10-02）**：本节标题原写「(v0)」，而下面的示例写的是 `"version": 1`，
> §9 又讲「v0 → v1 的兼容承诺」—— 三处说法互斥，实现只能挑一个。
> **定死为：文件里的 `version` 字段当前是 `1`**（示例是会被直接抄走的东西，以它为准），
> 标题里原来的「v0」是**这份规范草案自己的版本号**，与文件字段不是一回事。
> 代码里的对应常量是 `src/core/mindmap/types.ts` 的 `MINDMAP_VERSION`。
> 下面那份骨架**没有改动** —— 它本来就是对的。

```json
{
  "format": "levnote.mindmap",
  "version": 1,
  "layout": "logicalStructure",
  "root": {
    "id": "n1",
    "topic": "根主题",
    "note": "",
    "collapsed": false,
    "style": {},
    "children": [
      { "id": "n2", "topic": "分支", "children": [] }
    ]
  }
}
```

设计取舍：**结构自持，不绑定具体内核**。`id` / `topic` / `children` 是三家内核（mind-elixir、
simple-mind-map、自研）都有的最小公因式，`style` / `layout` / `note` / `icons` / `image` / `hyperLink` / `tags`
是可选增强（`icons` 2026-10-12 由 ADR 0053 从 extra 透传桶升格为正字段：存**显示字形本身**，
与 `topic` 存显示文本同理 —— 不发明语义 id，不绑定某家的标记词表；`image` 同日由 ADR 0054
升格：`{ url, width, height, fit? }` 三键齐才有效，`url` 存**文件 src**（相对路径或 data:），
尺寸存**显示尺寸** —— 尺寸即内容，不存它下次打开就是内核的默认猜值）。
`hyperLink` 与 `tags` 同日由 ADR 0055 升格：`hyperLink` 是一个**非空字符串** —— 内核对假值
不渲染，`""` 是画不出来的链接；`tags` 是「文字或带样式的文字」的数组，**文字即内容**
（与 `icons` 存字形同理），空数组照写。两者的取值形状照内核的渲染合同，不发明中间表示。
具体用哪个内核仍未定（见 `docs/decisions/` 的待决项），因此本节刻意只固定最小骨架 ——
一旦绑定某家的完整 schema，换内核就等于让用户的文件失效。

**内核已定（ADR 0007：mind-elixir，精确锁定 `5.15.1`），但骨架不变** ——
`id` / `topic` / `children` 恰好就是 mind-elixir 的字段名（这是当初选它的理由之一，
见 ADR 0007 第 3 条）。两处已知的对齐损耗由**适配层**吸收，不改格式：
`expanded` ↔ `collapsed` 是**改名**（不是两个语义），`layout` 官方侧只固定
`logicalStructure` 一个值。见 `docs/open-decisions.md` 的「V2 实测记录」。

#### 7.1.1 实现上的三条（2026-10-02 落地，`src/core/mindmap/`）

1. **未知键的透传桶就是 §5 那个 `extra`**，顶层与每个节点**各一个**。
   没有它，任何一次「未来版本新增字段」都会变成单向的数据损失。
2. **`extra` 不能跟着内核数据走。** mind-elixir 的 `getData()` 一次往返会丢 40 处字段
   （V2 实测），所以适配层的契约是「**带旧信封进去，拿新信封出来**」，
   而不是「把内核 data 转成文档」。见 `src/core/mindmap/types.ts` 的模块注释。
3. **认出来的字段类型不对时，值转进 `extra` 而不是丢掉**（`BAD_FIELD` 提示）。
   于是 `"note": 42` 这种文件**读得进来也写得出去**，一个字节都不少。
   真正防的是**重复的 JSON 键**：同一个键不许既在已知字段、又在 `extra` 里。

#### 7.1.2 与 mind-elixir 的字段对应（2026-10-02 接入内核时定下）

**骨架只固定「最小公因式」，不等于「只许有这些」。** 下面这张表说明每个键去哪：

| 我们的键 | 内核的键 | 说明 |
|---|---|---|
| `layout` | `direction` | **四个取值，不是四个方向各写一个字段**：`logicalStructureLeft`(0) / `logicalStructureRight`(1) / `logicalStructure`(2，默认) / `orgChart`(3)。用户按 `Ctrl + 方向键` 就能换，只认一个值等于丢掉这个动作 |
| `collapsed` | `expanded` | **改名，不是两个语义**（互为反义）。**只有一个方向写值**：`expanded === false` → `collapsed: true`。反过来不写 —— 内核的默认就是展开，写出来是噪声，还会给「打开 → 保存」平白加一次 diff |
| `id` / `topic` / `children` / `note` / `style` | 同名 | 直通。`note` 与 `style` 为空时不写（空串 / 空对象与「没有」等价） |
| `icons` | 同名 | **正字段（ADR 0053 升格，2026-10-12）**。`string[]`，存标记的显示字形本身（`"1️⃣"`、`"⭐"` …），不存语义 id。空数组 `[]` **照写** —— 那是「全清过」的如实记录，不是「没有」。类型不对时整值转 `extra`（§7.1.1 第 3 条） |
| `image` | 同名 | **正字段（ADR 0054 升格，2026-10-12）**。`{ url, width, height, fit? }`：`url` 是**文件里的 src**（相对路径或 data:，内核上屏前经外壳 `resolveImageUrl` 解析），`width` / `height` 是显示尺寸（正有限数，粘贴时按最长边 320 缩好），`fit` 可省（`fill` / `contain` / `cover`）。**整对象照收**：`image` 里我们不认识的子键原样跟着走 —— 尺寸之外我们不解释别人的内容。类型不对（不是对象、`url` 非非空字符串、尺寸非正数、`fit` 不在枚举里）时**整值转 `extra`** |
| `hyperLink` | 同名 | **正字段（ADR 0055 升格，2026-10-12）**。**非空字符串**（`""` 整值转 `extra` —— 内核对假值不渲染，空串是画不出来的链接）。原文**不 trim 不解码**；分类与打开归外壳 `classifyLink`（http(s) / mailto / 文件路径，文件路径可指向工作区里的另一份文档）。**内核零 UI**：菜单里的 link 项是节点连线不是它 —— 编辑弹层与 🔗 的点击拦截是我们自己的代码 |
| `tags` | 同名 | **正字段（ADR 0055 升格，2026-10-12）**。`(string \| { text, className?, style? })[]` —— **文字即内容**（与 `icons` 存字形同理）。对象元素我们不认识的子键**原样照收**；混入一个坏形状**整条**转 `extra`，不逐项过滤 —— 防「悄悄只留好的一半」。空数组 `[]` 照写：那是「全清过」的如实记录 |
| `branchColor` | 同名 | **正字段（ADR 0060 升格，2026-11-07）**。**非空字符串**（`""` 整值转 `extra` —— 内核对假值 `\|\|` 回落默认轮转色，空串是画不出来的颜色）：分支连线的颜色，hex 值即内容，**不限定词表**（词表外的色值照读照写，只是调色盘里没有格子代表它）。内核**子树继承**（子节点的线从父色起步、自己有值才盖过），**根没有连线**（`linkDiv` 只画 `me-main` 里子节点的线）—— 手写在根上的值照存不丢，但没有任何视觉效果。编辑入口是样式弹层第五行「连线」；摘掉 = 回到默认轮转色表 |
| 节点的其它键 | 同名 | 走该节点的 `extra`。`metadata` / `dangerouslySetInnerHTML` … 我们**一个都不解释，也一个都不丢** |
| 顶层的 `arrows` / `summaries` / `meta` | 同名 | 走顶层 `extra`。少了这一步，用户画的箭头与摘要是「存得住但看不见」 |
| 顶层的其它键 | — | 走顶层 `extra`（§5）。**注意顶层与节点不同**：内核的 `getData()` 返回的是一个写死的字段列表，我们展开到它上面的自定义顶层键会原样消失，所以顶层必须从上一份信封继承 |

三条**刻意不参与渲染**的：

1. **`theme` 与 `compact`**：保留在 `extra` 里（不丢），但**两个方向都不与内核交换**。
   它们是**视图偏好**，由轻笺的设置页统一管（ADR 0021）。文件里再存一份会让
   「深色主题下打开一张图突然变亮」；而如果反过来把内核的主题写进文件，
   又会覆盖用户原本手写的那一份。**保留但不读**是唯一同时满足两边的做法。
2. **节点上的 `direction`**：它是内核 `layout()` 的**产物**
   （按左右计数均分，同一棵树永远分配出同样的结果），不是用户写进文件的东西。
   我们让它走 `extra` 往返 —— 于是**用户的左右分布能存下来**，
   但内核每次都重算，所以它既不是格式的一部分，也不会被我们解释。
3. **`parent`**：内核自己维护的父引用（循环引用），**双向都排除**。
   一旦漏进 `extra`，`JSON.stringify` 会直接抛错。

> **一条实现上的顺序要求**：「没改过就不写」的基准必须取**内核跑完第一次布局之后**的那一份，
> 不能取刚解析出来的那一份 —— 否则内核补上的 `direction` 会被当成「用户改了东西」。
> 见 `src/modules/mindmap/MindmapEditor.tsx` 的 `settled`。

### 7.2 `.drawio` 往返的硬要求

这是本规范里最不能出错的一块，验收标准逐条列：

1. **未知元素必须透传**：认不出的节点类型、自定义 shape、第三方样式，原样保留。
2. **压缩变体要支持**：draw.io 的 `<diagram>` 内容可能是 raw deflate + base64。
   读进来解压后编辑，写出去**必须按原变体压回去**，否则某些 draw.io 版本读不了。
3. **多页必须保留**：一个 `.drawio` 可以有多张图，编辑第 2 页不能弄丢第 1 页。
4. **不做「顺手美化」**：不重排属性顺序、不重新缩进、不补默认值。
   往返一次之后，除了用户真正改的部分，其他地方应逐字节不变。

第 4 条尤其容易被忽视：XML 序列化器很乐意替你「整理」一下，
而这一整理就会让用户的下一次 `git diff` 变成一整页红色的噪音。

#### 7.2.1 变体表（2026-10-02 实测确认，不是推测）

下面这张表是 V1 实测出来的（**判据在查看器源码 `Editor.parseDiagramNode` 里，不是猜的**）。
实现 `.drawio` 读写时按这张表来，**不要发明表外的形式**。

| `<diagram>` 的内容 | 是否合法 | 说明 |
|---|---|---|
| `<mxGraphModel>` 作为**子元素** | ✅ | draw.io 关掉压缩后的写法 |
| `base64(deflateRaw(encodeURIComponent(xml)))` | ✅ | draw.io 的**默认**保存格式。**必须是 raw deflate**，带 zlib 头的读不了 |
| **空**（什么都没有） | ✅ | 真实存在（新建页没画东西）。读的时候会被补一个空模型，**写回时不要丢页** |
| **没有 `<mxfile>` 外壳**，根直接是 `<mxGraphModel>` | ✅ | 能读能画，但**页集合为 0** —— 读写都不能假设「页」存在 |
| `<mxGraphModel>` **转义成文本**（`&lt;mxGraphModel …&gt;`） | ❌ | **不是合法变体**，见下 |

**为什么最后一条不合法**（这条写下来是为了避免有人再发明一遍）：
`Editor.parseDiagramNode` 对 `<diagram>` 的**任何非空文本内容**都**无条件**调用
`Graph.decompress`，而它第一句是 `Graph.stringToArrayBuffer(atob(b))` —— **没有保护**，
也没有「这段文本是不是已经是裸 XML」的分支。所以转义文本进 `atob` 必抛
`InvalidCharacterError`。反向也证过：`viewer.min.js` 里**没有任何路径会把转义文本写进
`<diagram>`**。

> 转义形式**真实存在**，但不在 `.drawio` 文件里 —— 它在 HTML 的 `data-mxgraph` 属性、
> SVG 的 `content` 属性、PNG 的 `zTXt` 块里，那些走另外的抽取函数。
> **`.drawio.png` / `.drawio.svg` 是另外的扩展名**，不属于本节的范围。

**压缩变体的一条实现细节**：`Graph.compress` 的第二个参数决定 `deflate` 还是 `deflateRaw`，
而读取侧传的是 `null` → **只有 `deflateRaw` 能被读回**。所以写回时也必须用 raw。

## 8. 编码与行尾（红线）

**绝不静默转码。**

1. 打开：探测编码（BOM 优先，其次字符集统计猜测），用它解码。
   探测失败或出现非法字节时**如实标记 `lossy`**，让 UI 提示用户手动指定。
2. 保存：写回**原编码**。若目标编码无法表示文本中的某些字符，
   **报错并取消写入** —— 不许用 `&#NNNN;` 之类的数字实体偷偷替换。
   实现上除了检查编码库的 `had_errors`，还要做一次「编码 → 回读 → 比对」的双保险。
3. BOM 与行尾是**文件属性**，原样保留。混排行尾的文件不会被一次保存擅自统一。
4. 写入一律**原子替换**：同目录临时文件 → `fsync` → `rename`。
   写到一半崩溃不会把用户的文件变成半截。

## 9. 版本演进

- **`version` 字段的口径见 §7.1 的口径统一块：当前是 `1`。**（本节原先写的
  「v0 → v1」指的是**这份规范草案**的第 0 版到第 1 版，与文件里的字段混了名，已改写。）
- 版本 1 → 版本 2 的兼容承诺：**版本 1 写出的文件，版本 2 必须能读且不丢内容**。
  依赖的就是 §5 的「未知键原样保留」。
- **`version` 只在「新增了低版本完全无法解释的结构」时才动。**
  新增一个可选键**不算** —— §5 的透传桶已经兜住了，动版本号只会让低版本
  无谓地拒绝打开它本来能读的文件。
- 破坏性变更走新 `kind` 或新属性键，不改变既有键的含义。
- 属性区**不引入嵌套结构**。用 YAML 的好处是表达力，坏处是用户手改时更容易写错，
  且解析器要吃掉整个 YAML 的复杂度。要表达复杂配置时，正解是 `src` 指一个独立文件。
