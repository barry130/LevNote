# 轻墨 ↔ horseMD 差距分析与技术路线

状态：**已评估** · 评估日期 2026-09-29 · 对标对象 [`BND-1/horseMD`](https://github.com/BND-1/horseMD) v0.13.224（2026-09-19）

本文是一次**对外部成熟项目的系统性对标**。目的不是「抄功能清单」，
而是回答三个问题：

1. 我们与它的差距在**哪几个维度**上，各自有多远；
2. 哪些差距是**必须补**的，哪些是**可以不补**的（因为我们的前提与它不同）；
3. 补完之后，我们在哪里可以**超过**它。

---

## 零、一句话结论

> **轻墨的「决策质量」高于 horseMD，但「执行率」和「产品面」明显落后。**
> 差距的主因不是技术能力，而是**验证项积压**（`open-decisions.md` 的 V1–V4 全部未执行）
> 与**工程基建缺位**（无 git、无 CI、无 lint、无对外文档）。
>
> 本次已经补上两处最关键的缺口：**多标签工作区**（产品形态）与
> **代码内核 CodeMirror 6**（内核覆盖 1/4 → 2/4），
> 并把工程基建补齐到可协作的水平。

### C 档 · 前提不同，**不建议**跟

| 功能 | 为什么不做 |
|---|---|
| **云同步（WebDAV / S3）** | ADR 0001 的核心理由是「本地优先、无服务端、数据 100% 在用户手里」。云同步会稀释这条定位，而且它是**独立工程**（冲突合并、凭据管理、限流）。 |
| **移动端（Capacitor）** | 移动端只能做只读（horseMD 自己也是），投入产出比低，且会拖累桌面端的迭代速度。 |
| **AI 功能** | horseMD 的 AI 还停在「Phase 0 契约、无 UI 无网络」。没有明确的用户诉求前不做。 |
| **Pandoc 转换（Word/EPUB/LaTeX）** | 依赖外部二进制，安装包与跨平台分发成本高。**如果要做，走「检测到 pandoc 才显示该功能」的路线**，而不是打包它。 |
| **图床（PicGo）** | 与「本地优先」冲突：图片一旦上传就走出了用户的文件系统。 |

## 三、架构面差距

### 3.1 我们领先的地方（要守住，不要为了对标而丢掉）

| 维度 | 轻墨 | horseMD |
|---|---|---|
| **平台抽象** | `DocumentProvider` 是唯一平台差异点，纯 `vite dev` 下能跑内存虚拟盘做界面开发 | Electron 的 IPC 直接散在渲染层 |
| **内核抽象** | `EditorAdapter` 契约 + 注册表 + 兜底内核；外壳不认识任何具体内核 | 编辑器与外壳耦合较紧（Crepe 的能力直接决定 UI 能做什么） |
| **编码纪律** | 「绝不静默转码」是红线：探测失败如实标记 `lossy`、写回原编码、不可表示时报错取消写入、BOM/行尾是文件属性 | 「原文保真」只覆盖「不擅自改 CRLF/BOM 与未触碰的 Markdown」 |
| **写入安全** | 原子替换（临时文件 → fsync → rename）+ mtime 乐观锁 + 冲突必须由用户决策 | 未在 README 中说明写入策略 |
| **互操作规范** | `docs/format-spec.md` + `packages/interop-spec`：四类文档的引用/嵌入/转换有正式规范与实现 | 无对等物 |
| **决策记录** | ADR 体系 + 每条都带「重审条件」 | `implementation-notes.md` 更偏 bug 记录，没有「什么条件下该推翻这个决策」 |
| **体积** | Tauri ≈ 3.2 MB | Electron ≈ 85 MB（README 自称「轻」，但 Electron 的基线摆在那里） |

**这一节的意义**：对标时最容易犯的错是「看到对方有什么就加什么」。
上面这些是轻墨的**结构性优势**，任何新增功能都不该以削弱它们为代价。
具体地说：

- 新增功能不得绕过 `DocumentProvider` 直接碰文件系统；
- 新增内核不得让外壳认识它的类型；
- 任何会改变磁盘字节的操作都不得静默进行。

### 3.2 我们落后的地方

| 维度 | 差距 | 影响 |
|---|---|---|
| **内核覆盖** | 1/4 → 本次 2/4（Markdown + 代码）；思维导图与 draw.io 仍是空壳 | 产品的核心承诺（四类文档一等公民）目前只兑现了一半 |
| **Markdown 编辑体验** | 轻墨手工组装 `@milkdown/kit`；斜杠菜单、表格可视化编辑、代码块语言选择器与行号都已自研补齐，**只剩块手柄**。horseMD 直接用 Crepe 白拿这些 | 原先是 ADR 0004 的 **V4 待验证项**，现已由 ADR 0017 给出结论（自研可行，且官方组件是 Vue 3、采纳它等于换掉高亮管线）。剩下的「像不像 Typora」主要是块手柄与拖拽改列宽这类**交互层的糖** |
| **Markdown 功能面** | 已补：字数统计（Word 口径）、源码模式切换（Ctrl+/）（ADR 0014）、**选中浮层工具条**（ADR 0015）、**斜杠菜单 `/` 插入块**（ADR 0016）、**表格可视化编辑 + 代码块语言选择器 / 行号**（ADR 0017）、**图片粘贴落盘 + 相对路径 + 灯箱**（ADR 0018）、**LaTeX 数学公式**（ADR 0019）、**Mermaid 图表**（ADR 0020）、**位置记忆 + 设置页**（ADR 0021）；仍缺：块手柄 | **前六条都没有引入任何新依赖**（M7 / M8 破了这条：`katex` + `remark-math`、`mermaid`，两者都走动态加载不进主包，见 ADR 0019 / 0020）—— 源码视图复用已有的代码内核，浮层与斜杠菜单用的是已挂载的 `commonmark` / `gfm` 预设里的命令，表格与代码块自研（官方那套是 Vue 3，见 ADR 0017），图片的显示与灯箱也是自己画的（显示走已有的 `read_binary_file` 命令，见 ADR 0018）。清单与顺序见 `ROADMAP.md` 的 P3.5 |
| **性能证据** | V1–V4 四项验证**全部未执行**；`open-decisions.md` 里 V3 明确写着「仍未测」 | **这是最值得警惕的一处** |
| **实时预览架构** | 无相关探索 | horseMD 已经在做 CM6 + Lezer 的 live-preview spike，实测 12.8 万汉字：解析 5.4ms、首屏 8ms、单键重解析 0.35ms，并明确写「确认 source-as-model 架构可行」 |
| **Rust 侧能力** | `watch` / `search` / `drawio` / `export` 四个模块都是返回 `NOT_SUPPORTED` 的占位 | 外部改动检测目前靠「窗口重新获得焦点时比对 mtime」，是权宜之计 |
| **工程基建** | 无 git、无 CI、无 lint、无对外文档 | 本次补齐 |

### 3.3 关于 3.2 里那两条「架构级」差距的深入判断

**（1）V1–V4 全部未执行，是比功能缺失更严重的问题。**

轻墨的 `open-decisions.md` 把「什么条件下该推翻决策」写得比 horseMD 清楚得多，
但**四项验证一项都没跑**。其中：

- **V3（Milkdown 长文档输入延迟 ≤ 50ms）** 被自己标注为「唯一一项推迟了但会反噬的验证」，
  它的结论要回填 ADR 0004，而 0004 至今挂着「部分待定」。
- 对比之下，horseMD 在 `spike/` 里真的跑了 CM6 + Lezer 的实测并公开了数字。

**这说明差距的本质不是「想得不够」，而是「想了没做」。**
轻墨的 ADR 体系如果不配上执行纪律，会退化成「看起来很专业」的文档。

> **本次的技术建议（最重要的一条）**：
> 在写下一行编辑器功能代码之前，先花半天把 V3 跑出来。
> 一份 1 万字的真实中文文档，在 `npm run desktop` 里手动输入，用浏览器性能面板看输入到渲染的耗时。
> 这件事没有替代方案 —— jsdom 的耗时与真实 WebView 无关，这是 `open-decisions.md` 自己写的。

**（2）horseMD 正在考虑**离开**Milkdown，这对我们是一个重要信号。**

它的 `spike/live-preview` 明确写着「Isolated CM6 + Lezer spike（not wired into the app）」，
并规划了 `docs/live-preview-migration-plan.md`。也就是说：
**一个已经把 Milkdown Crepe 用起来的项目，正在评估换成「源码即模型」的实时预览架构。**

这直接印证了 ADR 0004 的备选方案（「CodeMirror + 预览分栏（更保守，也更不像 Typora）」）
不是保守退路，而可能是**更可持续的架构**。V3 的实测结论应该把这一条也纳入判断。

### 关于 lint 这一格：一个「技术选型领先于生态」的代价

**接入成功了，但过程暴露了一个值得记住的教训。**

项目原先用 **TypeScript 7**，而 `typescript-eslint@8` 的 peer 范围是 `>=4.8.4 <6.1.0` ——
它在**模块导入时**就抛错（`typescript-eslint does not support TS 7.0`），
连只装 `@typescript-eslint/parser` 单独加载也不行。
跟踪 issue：[typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)。

采用的解法是官方给出的「并排跑两个大版本」：

```jsonc
"typescript":         "npm:@typescript/typescript6@^6.0.2",  // tsc 与 lint 都用它
"@typescript/native": "npm:typescript@^7.0.2"                // TS 7 仍在，需要时显式调用
```

**这是一个明确的取舍**：让 lint 工具链决定了编译器的默认大版本。
换到的是类型感知的规则 —— 尤其是 **`no-floating-promises`**，
它是这类应用最容易出真 bug 的一类（异步调用没接住 → 保存失败被吞掉 → 用户以为存上了）。
**这个取舍值得，但必须写清楚重审条件**（已写进 `eslint.config.js` 头部与 `ROADMAP.md`）。

**这件事本身是一个可复用的判断**：采用一个刚发布的大版本语言工具链，
代价会以「周边工具全部滞后」的形式出现。轻墨在语言层面选了最严格的配置
（`strict` + `noUncheckedIndexedAccess` + `verbatimModuleSyntax`），这是对的；
但**严格与「工具链可用」之间存在一个需要被跟踪的窗口期**。

**当前状态（2026-09-29 更新）**：ESLint 已**全绿并阻塞**。
首轮全量扫描 33 项，全部清零；`unbound-method` 也从「关掉」变成「修好写法后打开」，
**配置里不再有任何被关掉的规则**。`npm run check` 与 CI 都会因 lint 失败而失败。
每一条的去向记在 `ROADMAP.md` 第 20 项与 ADR 0013 末尾的表。

清零过程中还暴露了这套双编译器方案的一个**系统性代价**：lint 跑在 TS 6 上、
`tsc` 跑在 TS 7 上，两者对同一段代码可能给出不同的类型（实测到一次：
TS 6 得到 `never`、TS 7 得到 `number`）。也就是说**「`tsc` 通过」不蕴含
「lint 通过」**，两条命令都必须跑。已写进 ADR 0013 的「代价」一节。

**当初为什么不直接让它把 CI 变红**：一个新 linter 一上来就满屏红，
结果是所有人学会忽略红灯 —— 那比没有 lint 更糟。
所以「先非阻塞、清零后转正」是有意的两步走，不是拖延。

## 六、在同等水平之上，往哪里超越

差距补齐之后，轻墨有四个 horseMD 结构上做不到的方向。

### 6.1 四类文档的**块级互操作**（horseMD 完全没有对等物）

horseMD 只有 Markdown 一类文档。轻墨的 `docs/format-spec.md` 定义了
四类文档如何在同一个工作区里互相引用、就地编辑、结构变换，
而 `packages/interop-spec` 是这份规范的**可执行实现**（27 条测试钉住）。

这是**品类级的差异**：它不是「horseMD 的功能 + 1」，而是
「Markdown 编辑器」与「四类文档的工作区」之间的差别。
把思维导图与 draw.io 补上之后，这条差异才真正成立 —— 所以 V1/V2 是**战略级**的验证项。

### 6.2 数据安全的**可验证性**（horseMD 只做到一半）

轻墨的编码纪律（ADR 0003）可以做到一件 horseMD 做不到的事：
**承诺并验证「打开→保存」对未触碰内容的逐字节保真**。

现在缺的是把它变成**用户可见的证据**：
`open-decisions.md` 提到「往返保真度自检」因为噪音太大被降级成了测试保证。
正确的做法不是放弃，而是**把它做成一个可选的、显式的动作**：
「校验本文件的往返保真度」——跑一次，如实报告差异，不改文件。
这一条如果做出来，会是这个品类里少见的**可信度卖点**。

### 6.3 体积与冷启动（Tauri 的结构性优势）

3.2 MB vs 85 MB 不是「省一点硬盘」，而是**分发能力**的差异：
小到可以随邮件附件、可以放在内网共享盘、可以在任何一台旧机器上秒开。
配合第 18 项（主包拆分），冷启动可以做到 1 秒以内。
**这一条应该写进产品定位，而不只是当成一个技术参数。**

### 6.4 决策记录体系（把它变成对外资产）

轻墨的 ADR 带「重审条件」，这是 horseMD 的 `implementation-notes.md` 没有的。
但 ADR 现在是**内部文档**。把它整理成一份公开的
「我们为什么这样选、什么条件下会改」的文档，本身就是一种**技术品牌**：
它让外部贡献者能在十分钟内理解项目，而不是靠读代码猜。

**前提是 §3.3 那条纪律先立起来** —— 一份只写不执行的决策记录，
公开出去反而是负资产。
