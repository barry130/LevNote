# 0003 · 编码/行尾不静默转码，写入一律原子替换

日期：2026-09-28
状态：已采纳

## 背景

桌面编辑器直接操作用户的文件，而用户的文件来自四面八方：
Windows 记事本存的 GBK、旧项目里的 GB18030、Mac 上带 BOM 的 UTF-8、
从数据库导出的 UTF-16LE。一次错误的编码处理，轻则乱码，重则整份文件永久损坏。

## 决策

四条红线，实现位置在 `src-tauri/src/fs/codec.rs` 与 `atomic.rs`：

1. **打开时探测，不做转换。** BOM 优先；无 BOM 时用字符集统计猜测。
   探测不可靠时（解码出现非法字节）**如实标记**，由 UI 提示用户手动指定，
   而不是自作聪明地换一个编码再试。
2. **保存时写回原编码。** 若目标编码无法表示文本中的某些字符，**报错并取消写入**。
3. **BOM 与行尾是文件属性，原样保留。** 混排行尾的文件不会被一次保存擅自统一。
4. **写入原子化**：同目录临时文件 → `fsync` → `rename`。

## 理由

- 第 2 条的措辞是「报错」，不是「尽力而为」，这是刻意的。
  主流编码库（`encoding_rs` 亦然）在遇到不可表示字符时会**静默替换成数字实体**
  （`&#26085;`）。结果是保存成功、没有报错、文件看起来正常，
  但用户的原文已经被永久改写。这种失败无法被用户察觉，属于最危险的一类。
  因此除检查编码库的错误标志外，还额外做一次「编码 → 回读 → 与原文比对」的双保险。
- 第 3 条不是洁癖。若保存时统一成 LF，用户下一次 `git diff` 会看到整个文件全变了，
  真实的改动被淹没在噪音里 —— 对以 git 管理文档的用户，这等于毁掉了版本历史的价值。
- 第 4 条防的是断电与崩溃。直接 `File::create` + 写入，写到一半断电，
  文件就成了半截内容。临时文件必须在**同目录**，跨盘 `rename` 不是原子操作。

## 代价

- 用户想「把 GBK 文件转成 UTF-8」时，需要显式操作（状态栏切换编码再保存），而不是自动完成。
  这是可接受的：转码是一次**有意的**、用户知情的操作。
- 实现比「一律按 UTF-8 读写」复杂，且需要针对中文场景做真实编码样本的测试。

## 重审条件

- 无。这四条属于数据安全底线，不因产品需求变化而放宽。
- 唯一可能的演进：为「批量转码」提供显式的、带预览与备份的工具，但绝不做隐式转换。
