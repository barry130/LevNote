# 0031 · i18n 骨架：先抽文案，不急翻译

日期：2026-10-04
状态：已采纳（P3 第 17 项落地）
关联：0012（命令注册表 —— 首批文案的宿主）、`core/i18n/`、
`ROADMAP.md` 第 17 项（「越晚做越贵」是这项排进 P3 的理由）

## 背景

ROADMAP 把 i18n 定位成**骨架**：「先抽文案，不急翻译」。要回答的是：

- 骨架到底要立起什么（机制、约定、首批范围）；
- 什么**现在不做**（不引入 i18n 库、不在设置页放语言切换、不翻第二语言）。

## 决策

### 1. 机制：`core/i18n/` 三件套 —— 目录、查表、插值

- `messages.ts`：`zhCN` 目录（`as const`），`MessageKey = keyof typeof zhCN`
  —— **写错 key 是编译错误**，不是运行时空白。
- `index.ts`：`t(key, params?)` 查表 + `{name}` 插值；`setLocale` / `getLocale`
  管语言状态。回退链：**当前语言 → zh-CN（key 定义处）→ key 本身**。
  最后一级返回 key 而不是空串是有意的：目录漏了 key，屏幕上是可搜的标识，
  不是无声空白（硬约束 2 的 i18n 版）。
- 插值漏参的占位符**原样保留**，不悄悄删掉。

不引入 i18n 库：骨架只需要「查表 + 插值 + 回退」，四十行以内；i18next 的
复数规则、日期格式化、懒加载命名空间在只有一种语言时全是死重。

### 2. 首批文案：命令面（title + category）

23 条命令的标题与 6 个分组，全部收进目录（`command.<id>.title` /
`command.category.<域>`）。选命令面的理由：命令清单是**能力的唯一清单**
（ADR 0012），命令面板、活动栏提示、设置页快捷键表都从它派生 ——
一处抽完，所有派生 UI 自动跟上，且 `registry.test.ts` / `App.test.tsx`
钉住值不变（**抽文案不许顺手改文案**）。

### 3. 明确不做的

- **keywords 不进目录**：拼音助记（'baocun' 等）是 zh-CN 特有的检索辅助，
  不是显示文案；第二语言需要不同助记时再收。
- **语言偏好不进设置页**：只有一份目录的今天，放一个语言切换只会做出
  「切了没反应」的死设置 —— 那是另一种静默撒谎。设置页接入点留给第二份
  目录落地的那次改动（`registerBuiltInCommands` 在 App 启动 effect 里调用，
  在它之前 `setLocale` 即可，顺序是现成的）。
- **Rust 侧错误文案不动**：错误横幅出现在 UI 层时自然会被看到，届时按需
  收进目录；现在抽了也验证不了。

## 后果

- 加第二种语言的工作量变成：复制一份目录 → 逐 key 翻译 → `SupportedLocale`
  扩联合类型 → `CATALOGS` 加一行 → 设置页加偏好项。机制本身不用再动。
- `Command.title` 当时是**注册时求值**的字符串（不是惰性取值）：当前语言恒定
  所以无感；第二语言落地时如果运行中切换语言，命令标题要么重注册、要么
  title 改成惰性 —— 见重审条件。**这个分支 2026-10-09 走到了，见复评记录三**：
  「重注册」那条路是错的（重注册的是同一批已烤死的对象，一次都没生效过），
  最终按重审条件选了惰性取值。

## 重审条件

- **第二语言真的立项时**：评估 i18n 库（复数、日期、RTL 需求是真的才引入）；
  同时补「部分翻译目录的回退链」测试（现在的测试留了位置，见
  `i18n.test.ts` 的 locale 状态 describe）。
- **运行中切换语言**：~~若成为需求~~ **2026-10-09 已成需求并按此条落地**
  （`Command.title` / `category` 改为惰性取值）。结论见复评记录三 —— 其中
  「重审命令重注册的语义」这部分的结果是**把重注册整个删掉**。
- **命令 id 改名**：key 随 id 走（`command.<id>.title`），改名是跨两处的
  编译期可见改动 —— 这是刻意的，不要为省事把 key 与 id 解耦。

## 复评记录（2026-10-07，第二份目录落地）

en 目录接入设置页，运行中切换语言按「重审条件」的第二条执行了，结论：

- **`Command.title` 保持注册时求值，不改惰性**。App 在 `settings.locale`
  变化时对内置命令**原位重注册**（`register` 对同 id 覆盖并保留位置），
  命令面板的顺序不受影响。惰性 title 会把「查表」推迟到每一次绘制，
  换来的是每次渲染多一次函数调用 —— 而重注册只在切语言那一刻发生一次，
  成本模型明显更优。
- **回退链保留**：en 目录是 `Record<MessageKey, string>`（类型钉住全量对应），
  `PartialCatalog` 的回退语义留给将来的部分翻译语言。
- **覆盖范围分批**：本轮英文覆盖命令系统（菜单 / 命令面板 / 快捷键表），
  面板与提示文案仍在 zh-CN 且未抽出 —— 迁移是机械活，每迁一批那块界面
  就在两种语言下都成立；设置页的语言行标签刻意写成双语（「语言 / Language」），
  在完成前不假装它是全量的。
- 重审条件的剩余项不变：复数 / 日期 / RTL 需求为真时再评估 i18n 库。

## 复评记录二（2026-10-07，E2 批次：外壳界面文案全量迁移）

ui/ 目录 18 个组件（设置页 / 文件树 / 标签栏 / 大纲 / 检索 / 查找替换 /
四个浮层 / 状态栏 / 横幅 / 空态）约 180 条文案全部抽进目录，en 目录补齐同量
译文。落地时确认的三件事：

- **静态清单存 key、渲染时才 `t()`**（ViewSwitcher / BlockHandle / SlashMenu /
  SelectionToolbar / TableToolbar / CodeBlockPicker）：模块加载时求值会把语言
  钉死在启动那一刻。含 `useMemo` 的地方（块手柄菜单条目）同样只存 key ——
  memo 不会因切语言重跑，把译文存进去就会过期。**这条在 E3 批次又抓到两处
  违例**：`mermaid-render` / `drawio-render` 的空图表常量原来是模块级
  `const X = t(...)`，已改为在返回点现调 `t()`（常量只有同模块与测试在用，
  测试同样改为按 key 现查）。
- **zh 值逐字节不变**，测试按文字找元素的辅助函数与全部中文断言不用动。
  「目录无占位符」的旧测试前提作废（插值文案进目录了），改为钉
  「两份目录同 key 的占位符集合一致」—— 这是插值文案的翻译契约。
- **core 层的消息随后续三个批次全部迁完**（E3a 常驻消息 / E3b 动作消息 /
  E3c 渲染与导图解析 + 平台层）：保存结果 notice、检索与替换汇总、
  AppError 的 message、`.mindmap` 解析降级提示、Mermaid / draw.io 渲染失败
  原因、浏览器预览虚拟盘消息、原生对话框标题，连示例文档创建失败与
  「复制为 HTML」的通知。被 core 测试逐字钉着的文案随批次一起动
  （改为按 key 现查）；`interpolate` 是单趟替换，参数值里含 `{}` 不会被
  再扫描 —— 与原先模板字面量的行为一致。

## 复评记录三（2026-10-09，命令面运行中切语言：#TASK-I18N-CMD-LIVE-01）

门下在评审 #TASK-P0-GREEN-01 时探到：设置页切 English 后**菜单顶层名变了，
下拉项没变**，命令面板条目与快捷键表同理。中书令独立复核后立项，本轮修复。

**上一轮（复评记录）选错了路，且错得不易察觉。** 那份记录写的是
「`Command.title` 保持注册时求值，不改惰性；App 在 locale 变化时对内置命令原位
重注册」，理由是按「每次绘制多一次函数调用」对比「切语言那一刻重注册一次」的
成本模型。成本模型本身没错，**错在前提**：`BUILT_IN_COMMANDS` 是模块级常量，
`title: t('...')` 在模块加载那一刻（locale 还是默认 zh-CN）就求值烤进对象了。
所以那次重注册拿到的永远是**同一批已经烤死的对象** —— 它是一次无效动作，
一次都没生效过。这也解释了为什么缺陷能一直藏着：重注册的代码在、看着完全正常、
单测全绿（没有人测过「切完之后读到的是什么」）。

**本轮结论**：

- **`Command.title` / `category` 改为惰性取值**（重审条件的那条分支）。落地形状是
  `core/commands/definitions.ts` 的 `builtInCommand(spec)`：内置命令只声明
  `titleKey` / `categoryKey`，命令对象上这两个字段是**读的那一刻才查表**的 getter。
- **重注册整个删掉**（`App` 的 locale effect 现在只 `setLocale` + bump `localeTick`）。
  不再需要「谁来重新求值」—— 惰性取值下刷新文案只需要重渲染。
- **为什么是 getter 而不是把 `title` 改成函数**：`Command` 是外壳按契约消费的
  形状（菜单 / 命令面板 / 快捷键表三处读 `command.title` 当字符串）。改成函数
  等于让每个调用方各写一次 `title()`，漏一处屏幕上就是一行 `function () {...}`。
  getter 让「消费方零改动」与「求值时机正确」同时成立。
- **编译期拦住复发**：`BuiltInCommandSpec` **不接受**字面量 `title` / `category`
  —— 写了就是编译错误。那是这个缺陷的形状本身，不该靠人记得别写。
  数据类命令（最近打开的文件）走 `titleFrom: () => 文件名`，同一条惰性路径。
- **口径同步**：`docs/release-smoke.md` 的语言切换条在上一轮已订正成「分主语」
  写法，但其中「命令面板 / 快捷键表变英文」这句在机制修好之前与实测不符；
  本轮修好后才真正成立。`AGENTS.md` 与 `CHANGELOG.md` 0.3.27 里
  「命令标题是注册时求值的」同源断言一并订正。

**这一轮真正的教训**：「重注册一次」与「惰性取值」的成本模型争论是**在错误前提上
展开的** —— 两边都没先问一句「重注册拿到的对象，是新的吗？」。判断依据由此加一条：
**凡是「刷新某个派生值」的写法，先确认被刷新的东西本身是可变的**；
如果它是模块级常量，刷新动作只是给自己看的心安。

## 复评记录四（2026-10-10，快照型文案第二批：#TASK-I18N-SNAPSHOT-01）

门下在评审 #TASK-I18N-CMD-LIVE-01 时顺手扫了**同族的快照型文案**，登记了两处
**同类但不同源**的残留（在 `b4e13ef` 已存在，非那个 PR 引入）。中书令复核后立项，
本轮一次改齐。门下的要求原话是「别让它停在评论里」。

### 根因：同族缺陷的两种形态

复评记录三说的是「模块加载那一刻求值」（命令面）。这一批是**另外两种形态**，
而且都发生在**运行时**，所以不能再靠「模块级常量」那条判断依据兜住：

1. **副作用依赖漏了 locale**（`src/ui/App.tsx` 的窗口标题 effect）。
   `t()` 的**求值时机是对的**（就在 effect 体内现调），漏的是**触发时机** ——
   deps 只有 `activeTab`，切语言不会重跑它，屏幕上那个标题一直停在旧语言。
   **修法**：deps 补 `settings.locale`。不必额外同步手段：语言是**上一步**
   落地的（同一个 commit 里 `useLayoutEffect` 先跑 `setLocale`，而 layout effect
   一定早于 passive effect），本 effect 读到的已经是新语言。
2. **把 `t()` 的结果存进了 state**（`core/document/store.ts` 的 `notice`、
   `src/ui/FindBar.tsx` 的替换汇总）。这在动作发生的那一刻就把文案**烤成字符串**，
   之后切语言再也不会重算。**修法**：存 key + 参数，**渲染时才查表**。

第 2 条正是复评记录二为组件立下的「静态清单存 key、渲染时才 `t()`」那条纪律 ——
当时只把它应用到了「模块级常量」这一种形态，而 `t()` 的结果存进**运行期 state**
是同一条纪律的另一种违例。**判断依据由此收窄成一句**：
**凡是把 `t(...)` 的返回值放进任何会活过这一次求值的地方（模块常量、state、
`useRef`、store 字段），它就必须改成 key + 参数。** 唯一可接受「存译文」的位置
是**最终渲染出来的那一份 DOM / 字符串**。

### 落地的形状

- `StoreState.notice`：`string` → `Notice | null`。`Notice` 是**联合**：
  `{ key; params? }`（新写法，查表推迟到渲染）与 `{ text: string }`（只服务
  `images.ts` 的 `PasteImageFail.reason` —— 那个文件不在本轮改动范围内）。
  导出 `renderNotice()` 把两个变体收敛成一句话，状态栏与查找栏两处消费方共用 ——
  免得各写一份联合类型的分支（那是这类改动最容易分叉的地方）。
- **`clearNotice` 与「关闭文档」都归 `null` 而不是空串**：`null` 才是「没有」，
  空串会在渲染处诱出 `{notice && ...}` 这种「空串为假」的隐式判断 —— 类型换了
  之后那套判断就该一起消失。
- **`text` 变体是显式的技术债**，不是给新代码留的后门：它服务的那 6 条文案
  在 `core/document/images.ts` 里被烤成了字符串（`PasteImageFail.reason`），
  要彻底消掉得让那个模块也交回 key —— 与本轮白名单冲突，另立 follow-up。
  **新写的 notice 一律走 `key` 变体**。

### 为什么没有拆成「本轮只做标题、notice 单列」

R4 要求给成本依据。实测：`notice` 的**写入点 6 处**（`store.ts` 内，
全是 `this.commit({ notice: ... })` 一行）、**读取点 2 处**（`DocumentPane`
渲染、`FindBar` 无关 —— 它有自己的 state）。改动面**全部落在白名单内**，
且类型换掉之后**编译器会把每一个漏改的点报出来**（`Notice` 不是 `string`，
`string` 用不到 `renderNotice`）。一次改齐的成本低于「拆两轮 + 留一份带
`as` 的过渡类型」—— 后者会引入本单明令禁止的消音写法。故未拆。
