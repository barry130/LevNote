# 0014 · 源码模式：把「同一份文档的第二种视图」做成一等概念

日期：2026-09-29
状态：已采纳
关联：0004（内核选型）、0010（多标签工作区）、0011（降级到次优）、0012（命令注册表）

## 背景

对标项目 horseMD 的 Markdown 功能清单里有一条 **「源码模式切换（`Ctrl/Cmd+/`）」**：
一份 Markdown 文档可以在「渲染后的样子」和「原始 Markdown 源码」之间来回切。
它解决的是一个真实痛点 —— 富文本视图会把用户看不见的语法（`**`、表格的对齐行、
围栏代码块的语言标记）藏起来，偶尔需要在源码层面确认或直接改。

轻笺要补这一条，但补法不能是「在 Markdown 内核里加一个开关」。
原因是我们有一条不能破的边界（ADR 0004 / 0011）：

> **外壳不认识任何具体内核。** 它只知道 `EditorAdapter` 与 `EditorHandle`。

如果源码模式在 Markdown 内核内部实现（比如让 Milkdown 切到 `EditorView` 的
原始文本模式），那么：

- 外壳要判断「现在能不能切源码」就必须知道「这是个 Markdown 内核」——
  边界破了；
- 源码视图的语法着色要另写一套（CodeMirror 的 markdown 语言包已经在了，
  白扔）；
- 将来若换成自研的 Markdown 内核（ADR 0004 的重审条件之一），
  这套切换逻辑要跟着重写一遍。

而且「切视图」还牵动几处已经踩过坑的时序：内核是**异步**创建的（`session` 号、
`disposed` 检查、句柄失效那一整套），切视图会重建内核，等于把那条路径再走一遍。

## 决策

1. **源码视图是适配器的一个属性**：`EditorAdapter.sourceView?: EditorAdapter`。
   Markdown 适配器把它指向代码内核 —— 也就是说，
   **源码视图底下坐着的就是 CodeMirror**，语法着色、行号、折叠全部白拿。
2. **源码视图不注册进注册表。** 它只挂在适配器对象上，由外壳在
   `viewMode === 'source'` 时显式取用。
3. **视图模式（`ViewMode`）住在 `StoreState`，不住在 `OpenDocument`。**
4. **内核实例标识从 `session` 扩展成 `session:viewMode`**，
   句柄失效判定与内核启动失败的标记都用它。
5. **Markdown 扩展名名单收敛到 `core/path.ts` 的 `MARKDOWN_EXTENSIONS`。**
   在此之前这份名单抄在三处（Markdown 内核、代码内核、外壳的大纲判断），
   而源码视图是第四个需要它的地方。
6. **内核启动失败后允许重试**：显式切一次视图就重试目标内核，
   并且「新内核就绪」会撤掉上一个实例留下的错误横幅。

## 理由

### 为什么源码视图不注册进注册表

注册表按路径挑内核，而**同一个路径只能有一个答案**。
源码视图不是「另一个能处理 `.md` 的内核」，而是「同一个路径的第二种看法」。
把它注册进去，`resolveAdapter('a.md')` 就有了两个合法答案，
哪一个先被匹配到取决于注册顺序 —— 那是没法推理的行为
（ADR 0011 里刚修过一个「优先级与注释相反」的 bug，不想再制造一个）。

### 为什么 `ViewMode` 不进 `OpenDocument`

`OpenDocument` 描述的是**文件**（路径、编码、行尾、mtime），
视图模式描述的是**这次编辑会话**。混在一起的代价是两个具体的坑：

- `reload()` 会走 `toDocument()` 重建文档对象，稍不注意就把视图模式
  一起重置回富文本 —— 用户按了「从磁盘重新加载」，界面自己跳回富文本视图；
- `isDirty` 会被迫回答「视图模式算不算脏」，而这个问题本身就不该被提出。

放进 `StoreState` 之后，它天然是**每标签页**的（一个标签页一个 store，
见 ADR 0010），而且 `reload()` / `saveAs()` 这类只碰文档对象的操作碰不到它。
`store.test.ts` 的「视图模式」一组把这两条钉住了。

### 为什么把 `viewMode` 也算进内核实例标识

切视图**不改会话号**。而句柄失效判定（`handleKeyRef`）与失败标记（`failedKey`）
本来都只认 `session` —— 切视图时那一段异步窗口里，
`handleRef` 会被误认为「有效」，于是外壳可能把内容写到一个已经销毁的旧内核上。

把它扩展成 `session:viewMode` 之后，两个机制同时得到修正，
并且顺带换到一个副作用：**一次「富文本内核起不来」不再把用户永久锁在兜底内核上**，
他至少能切到源码视图，用代码内核把内容看全。

### 为什么名单必须收敛

源码视图让「`.mdown` / `.mkdn` 这些冷门后缀也要有 markdown 语法着色」变成需求，
于是第四个抄本出现了。抄多份的真实后果不是「维护麻烦」，而是**双重落空**：

> Markdown 内核认为「这不是 .md」（于是退位），代码内核也不认它（于是继续往下掉），
> 用户拿到一个白底 textarea —— 而两个内核的代码看上去都没写错。

`modules/wiring.test.ts` 用一条**跨模块**的断言把它钉住：
名单里的每一个扩展名，两个内核都必须认领，且都必须得到 `markdown` 语法包。

## 后果

- **Ctrl+/ 与工具栏开关都走同一条命令**（`view.toggleSource`，ADR 0012），
  所以不会出现「按钮和命令面板行为不一致」。命令在**不支持源码视图的文档上显示为禁用**
  而不是隐藏 —— 隐藏会让用户以为功能不存在。
- **状态栏在源码模式下显示「代码 / 文本 · Markdown 源码」。**
  只显示当前内核名的话，一份 `.md` 的状态栏写着「代码 / 文本」，用户会以为打开错了文件。
- 切视图会**重建内核**，因此撤销栈、光标位置、滚动位置都会重置
  （与切标签页的代价相同，见 `open-decisions.md` 的推迟项）。
  这是正确性优先的取舍：让内核跟着视图走，比在同一个实例里换模式安全得多。
  **这一条是当前最明显的体验欠账** —— horseMD 明确把「切源码模式保留滚动位置」
  当卖点。之所以没有顺手做，是因为它需要「源码偏移 ↔ ProseMirror 位置」的
  双向映射，而那个映射一旦不精确就会跳到错的地方；
  按本项目一贯的取舍（跳错比不跳更伤人），宁可不做也不做错。
- 前端主包 +1.7 kB（1,666.96 → 1,668.69 kB），因为全部复用已有依赖，
  **没有引入任何新包**。
- `OutlinePanel` 里那份手抄的 `StoreState` 字段表被删掉了
  （给 `StoreState` 加 `viewMode` 时它第一个炸），改为从 `store.ts` 的
  `emptyStoreState()` 同源取。

## 重审条件

- **若切视图时的「重建内核」代价在长文档上被实测为不可接受**
  （比如 10 万字文档切换要等一秒以上）→ 改为「两个内核都挂载、用 CSS 隐藏」。
  但那条路要先实测内存占用，而且隐藏的那个内核仍然在响应文档变更 ——
  撤销栈语义会变得难以解释，不是纯收益。与 V3（长文档输入延迟）一起评估。
- **若将来出现第三个需要源码视图的内核**（比如思维导图的 XML 源码）→
  `sourceView` 这个字段的设计就被验证了；若它只对 Markdown 有用、
  且第二个使用者迟迟不出现 → 考虑把它降级成 Markdown 模块内部的一个约定，
  而不是契约的一部分。**当前只有一个使用者，这一点必须承认。**
- **若 ADR 0004 的重审结论是「改用 CM6 + Lezer 的源码即模型」** →
  那时「富文本 / 源码」就不再是两种视图，而是一个连续谱，
  本 ADR 的整个模型需要重做。这是本决策最大的外部不确定性。
- 若源码视图与富文本视图出现**任何**内容不一致（切过去再切回来内容变了）→
  立即按最高优先级处理：两种视图共用 `doc.text` 这一份权威副本是本设计的前提，
  它一旦不成立，「无损切换」这个承诺就没了。
