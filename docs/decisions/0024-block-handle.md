# 0024 · M11 块手柄：悬停命中走 DOM 元素、目标块由内核记、清目标块的时机交给外壳

状态：**已采纳**

## 背景

M11 是 Markdown 这一类的最后一项，对标的是 Typora 那种「鼠标停在某一块左侧，
浮出一个握把，点开有块级菜单，还能直接拖着换位置」。

它比 M3–M10 都更贴外壳与内核的边界，因为有三件事在别的浮层里从没出现过：

1. **触发源是鼠标移动，不是选区。** 前面五个浮层（选中工具条 / 斜杠菜单 /
   表格工具条 / 语言面板 / 灯箱）都挂在「选区 / 文档 / storedMarks 变了」上，
   而鼠标移动**完全不碰 state** —— 那套上报骨架一辈子都不会被唤醒。
2. **手柄在编辑器外面。** 用户必须把鼠标从正文移到手柄上才能点它，
   而这一步必然让「指针还在编辑器里吗」这个问题的答案变成「不在」。
3. **手柄要记住「作用在哪一块上」，而外壳不知道那是文档里的第几块。**
   位置与文档坐标之间隔着一次布局，而硬约束 10 说外壳不许持有文档坐标。

## 决策

1. **块 = `doc` 的顶层子节点。** 整张列表算一块，一个引用算一块，一张表格算一块。
2. **悬停命中走 DOM 元素**（`event.target` → `posAtDOM` 向上找到第一个认得的元素 →
   `resolve(...).index(0)`），**不走 `posAtCoords`**。
3. **左侧留白里保住目标块**（`withinGutter`）：指针在当前这一块的包围盒
   往左扩 44px 的带子里，就继续算作还指着它。
4. **目标块由内核记**（`target.index`），**清它的时机交给外壳**：
   判据是「手柄彻底不可交互」，不是「菜单关了」。
5. **按住鼠标时冻住目标块**（`event.buttons !== 0` 就跳过），不新增契约。
6. **拖动不用 HTML5 拖放**，用指针事件自己实现；落点由内核算
   （`dropIndicatorAt` / `dropAt` 收视口坐标，返回一条横线）。
7. **「转为」复用 `formatting.toggleBlock`**，但先挡「已经是这个格式」。
8. **不做「复制为 Markdown」。** 它需要一条会静默失败的剪贴板路径。

## 理由

### 1. 为什么悬停命中不走 `posAtCoords`

两条独立的原因，任一条都足够：

- **它依赖 `document.elementFromPoint` / `caretRangeFromPoint`，而 jsdom 两个都没有**
  （实测都是 `undefined`，所以 `posAtCoords` 必抛）。走坐标等于把
  「上移 / 下移 / 复制 / 删除 / 转为」**全部命令**挡在测试之外 ——
  而它们恰恰是最需要测的部分。改走 DOM 之后，内核那半边在 jsdom 里跑得通，
  `block.test.ts` 的 45 条里有一大半是这么来的。
- **它算的是「最近的一个文本位置」，不是「指针压着哪个元素」。**
  指针停在块的内边距上时它会给出一个看似合理的答案，而我们要的恰恰是
  「指针真的压在这一块上吗」。

`posAtDOM` 只查 docView 树、不触发布局，代价比 `elementFromPoint` 更低
（后者会强制结算布局）。

### 2. 为什么留白那一条不能省

手柄贴在块左边缘**往左 26px**，而块左边缘的左边是编辑器自己的内边距。
用户从正文移向手柄，中途必然穿过那条留白。纯按元素命中算的话，
那几像素里「指针压着哪个块」的答案是**没有块** → 内核报 null →
外壳把整个手柄卸载 → 用户永远点不到它（`mouseenter` 都不会再发，
因为元素已经不在了）。

这条是**几何兜底**，在 jsdom 里验不了（没有布局引擎，包围盒全是 0），
所以真正的保证在 `withinGutter` 那组单测上，而不是集成用例。

### 3. 为什么清目标块的时机在外壳，而且不是「菜单关了」

内核与外壳各有各的状态，必须分清：

| 状态 | 住哪 | 什么时候变 |
|---|---|---|
| 「指针现在压着哪一块」 | 内核 → 上报给外壳 | 每次鼠标移动 / 滚动 / 文档变化 |
| 「手柄现在可交互吗」 | 外壳（React state） | 三个条件合起来 |
| 「菜单上的动作该作用在哪一块」 | **内核**（`target.index`） | 只在手柄彻底不可交互时清 |

第三项**不能**跟着第一项走：用户要把鼠标从正文移到手柄上才能点它，
一离开编辑器就清，菜单上的每个动作都会作用在「没有目标」上 —— 表现为
**点了没反应**，而且菜单画得好好的，完全看不出原因。

它也**不能**跟着「菜单关了」走：菜单关掉的那一刻指针还在手柄上，
用户随时会再点一次。清早了，第二次打开的菜单里每个动作都会失效。

所以判据是 `visible === false`（指针既不在任何一块上、也不在手柄上、
菜单也没开、也不在拖动），外加组件卸载。

### 4. 为什么「按住鼠标」这一条不能省

拖动重排期间 `mousemove` 照常发。不挡的话指针扫过哪一块、`target.index`
就变成哪一块 —— 用户拖的是第 1 块，松手却把第 3 块搬走了。

判据用 `event.buttons !== 0` 而不是加一条「开始拖动 / 结束拖动」的契约：
一次契约都不用加，而且顺带覆盖了「拖选正文时手柄乱跳」。

### 5. 为什么拖动必须用坐标，而悬停必须不用

这两个方向看着矛盾，其实是同一个问题的两个面：

- 拖动时指针下面压着的是**手柄自己**（它跟着块的位置，而指针从它身上出发），
  元素命中会命中手柄而不是正文。坐标命中问的是「这个位置在文档的哪里」，
  与压着谁无关 —— 正是拖动需要的语义。
- 悬停时问的恰恰是「指针压着谁」，而且不能被手柄挡住。

配套的两条保险：拖动期间手柄加 `pointer-events: none`（`posAtCoords` 内部
也走 `elementFromPoint`），落点指示线也 `pointer-events: none`。

### 6. 为什么「转为」要先挡同格式

`toggleBlock` 对同格式是**取消**语义（标题降回正文、列表脱出容器），
而「转为」的语义是「设成这个」。不挡这一下，用户点「转为 → 二级标题」
会把一个已经是 H2 的标题变成正文 —— 菜单上明明写着「转为二级标题」，
结果二级标题没了。

外壳把当前那一项显示成**禁用**是第一道，内核里 `isSameBlockFormat` 是第二道。
两道都要：外壳那道是体验（看得见为什么不能点），内核那道是正确性
（外壳的状态可能过期）。

### 7. 为什么不做「复制为 Markdown」

它是块菜单的常见项（Typora 有），但在这个项目里只能走
`navigator.clipboard.writeText` —— 而它在没有用户手势、没有权限、
或者 WebView 策略不允许时会**返回一个被拒绝的 Promise**，我们既没有通用提示通道
（`notice` 是 `DocumentStore` 专用的单槽位），也不该为它造一个。
「复制」这条路径上的失败是**用户以为复制到了、其实没有**，与硬约束 2 冲突。
等有了通用提示通道再说。

### 8. 为什么原子块如实给 `block: null`

表格 / 公式 / 分隔线不是「文本块的另一种形式」，转过去转不回来。
假装它们是段落的话，菜单会点亮「正文」，而用户点下去什么都发生不了 ——
更糟的是「转为正文」真做起来就是**把一张表格变成一段空文字**（硬约束 2 的红线）。
所以 `CONVERTIBLE` 是一张白名单，不是黑名单。

## 代价与已知偏离

- **几何量取在 jsdom 里验不了。** 包围盒、落点线、留白带宽都只有真机能验。
  这一条写在 `block.ts` 的文件头里，也在两个测试文件里各说了一次 ——
  目的是让下一个人不要以为「集成用例绿了 = 落点算得对」。
- **手柄只有「上移 / 下移 / 复制 / 删除 / 转为」五个动作**，没有「复制为 Markdown」
  （理由见上），也没有多选（Typora 的多选块要另造一套选区模型）。
- **「整张列表算一块」意味着不能只移动列表里的一项。** 只移动一项会让它脱离列表
  变成段落 —— 那几乎不是用户想要的。这与 Typora 一致。
- **拖动没有跨标签页 / 跨文件的能力**（把一个块拖到另一个标签页里）。
  那需要一套跨文档的剪贴板语义，属于 P6 的块级互操作。
- **主包 +11.4 kB**（1,756.20 → 1,767.56 kB）。手柄与菜单都是首屏就可能要画的，
  没有懒加载余地；`IconGrip` 是手写的（同 M10 的 `ui/icons.tsx`，不引图标库）。

## 重审条件

1. **手柄在真机上「点不到」或「闪一下就没」。** 那说明留白那条几何兜底
   在真实布局下不够宽（44px 是估的），或者 `nodeDOM` 拿到的包围盒
   与用户眼里的「块」不一致（例如列表的缩进算在 `ul` 还是 `li` 上）。
   判据是**真机上从正文移到手柄的成功率**，不是坐标对不对。
2. **`event.buttons !== 0` 在触控板 / 触摸屏上不成立。** 那说明这套
   「按住 = 拖动」的判定在那些设备上会失效，要改成显式的拖动状态。
3. **`posAtDOM` 的性能在大文档上不够。** 它在每次 `mousemove` 上跑一次，
   而 jsdom 里测不出真实开销。如果长文档上悬停发涩，就要把元素命中挪进帧调度
   （现在是当场的），或者改成「只在 `event.target` 变化时才重算」。
4. **`close()` 的时机再次出问题**（比如出现了「菜单里点了一项之后，
   再点开菜单没反应」）。那说明「外壳决定时机」这条分工不够 ——
   要考虑让内核自己带一个「目标块的有效期」。
5. **P4 / P5 落地之后**，思维导图与 draw.io 的块也需要手柄。
   那时要检查的是：`BlockHandleState` 里有没有 Markdown 特有的东西
   （`headingLevel` 是，但它是可空的），以及 `blockIndexFromElement`
   的「顶层子节点」这条假设在别的内核上成不成立。
