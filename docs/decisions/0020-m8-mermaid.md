# 0020 · M8 Mermaid 图表：图与源码是同一块的两种看法，导出时画成 SVG

状态：**已采纳**（M8）

## 背景

M8 的交付是「Markdown 里的 Mermaid 图表」：写一段 ```` ```mermaid ```` 代码块，
在编辑器里就能看到画出来的图，导出时它跟着进单文件 HTML。这是 `ROADMAP.md`
第 15 项，也是 Markdown 模块最后一块**渲染类**能力（只剩位置记忆 / 设置页 / 块手柄）。

它要一次定下五件事：

1. mermaid（12.7 MB 的模块图）怎么才能不进主包；
2. 「这是图」这件事在**哪一层**判定；
3. 图与源码在编辑器里怎么共存；
4. 谁来提供渲染用的容器（mermaid 默认往 `document.body` 挂临时节点）；
5. 导出的单文件里怎么让图**不依赖网络**。

## 决策

1. **`import('mermaid')` 动态加载**，缓存 Promise、**失败不缓存**（`core/mermaid-render.ts`）。
2. **「什么算图表块」单独成一个纯函数**（`core/mermaid.ts` 的 `isMermaidLanguage`），
   三处共用：NodeView、装饰判断、导出。
3. **图与源码是同一个块的两种看法**，由 `dom.dataset.mode` 决定谁显示；
   **光标在块里就是源码**。
4. **容器由我们提供**（`withMeasureContainer`），挪到屏幕外、**参与布局**；
   mermaid 的 `render` 第三参数永远传。
5. **导出时画成 SVG 内联进 HTML**，且**永远按浅色画**；渲染失败保留源码并上报。

## 理由

### 1. 为什么必须动态加载，以及代价

`mermaid.core.mjs` 本身只有 53 KB，但它一被加载就把几十个图种和各自的布局
算法一起拉进来（`node_modules/mermaid/dist` 里非 sourcemap 的部分是
12.7 MB / 271 个文件）。静态引入等于让**每一个**打开轻墨的人先付这笔钱，
哪怕这篇文档一张图都没有。

实测产物：

| | M7 之后 | M8 之后 |
|---|---|---|
| 主包 `index-*.js` | 1,724 kB | 1,734 kB（**+9.8 kB**） |
| `dist/` 总量 | 2.4 MB | 5.8 MB |

也就是说 mermaid 那 3.4 MB 全在**懒加载**的 chunk 里，主包只多了我们自己的代码
与 chunk 装载器。这与 M7 对 KaTeX 的做法是同一条约束。

**代价（必须写清楚）**：`dist/` 大了 3.4 MB，安装包跟着大。这是 mermaid 的固有体积，
它不提供「只要流程图」的可裁剪入口。重审条件见文末。

### 2. 为什么「这是图」要单独成一个函数

这个判定出现在**三处**，而且三处的运行环境完全不同：NodeView（画不画）、
导出（换不换）。三处各写一个 `language === 'mermaid'`，上游哪天多认一个别名
就会出现「编辑器画得出、导出不画」——而那不报错，只让发出去的文档少一张图。

判定里**刻意不认 `mmd` / `mermaidjs` 这类别名**：认了会造成**我们制造的分歧** ——
轻墨把那一块画成图，而别人打开这份文档时它只是一段代码。

### 3. 为什么「光标在不在块里」要插件推给视图

ProseMirror 给 NodeView 的只有两个钩子（`update` / `destroy`），
**都不是「选区变了」**。而图/源码的切换完全由选区决定。所以插件自己持有一份
活跃视图表，在 `PluginView.update()`（唯一每帧都跑的钩子）里逐个推。

这里有一个**只能靠实测发现**的顺序问题：一个事务里 ProseMirror **先**跑
`nodeView.update()`、**后**跑 `PluginView.update()`。所以「在块里打第一个字」时，
`update()` 看到的 `editing` 还是上一帧的（光标在块外面）—— 在那里判断要不要画图
会因为这一帧的滞后而多画一张没人看的图。修法是把图区的对齐**统一放在
`syncSelection` 里**，`update()` 只管节点本身。

### 4. 为什么容器不能省、且不能 `display: none`

`mermaid.render(id, text, container)` 的第三个参数省掉的话，mermaid 走另一条分支
（`mermaid.core.mjs` 的 `root = select("body")`），把量尺寸用的临时 `<div>`/`<svg>`
**挂到真实页面的 body 上**。编辑器里那是可见的污染；导出时更糟 ——
我们要的只是它返回的那段字符串。

容器还必须**真的参与布局**：mermaid 靠 `getBBox()` / `getComputedTextLength()`
量文字尺寸，这两个 API 只在元素真的被渲染时才给得出数字，`display: none`
或游离节点会得到全 0（Firefox 上直接抛错），画出来是一片挤在一起的框。
所以容器用 `position: fixed; left: -99999px` —— 在布局里，但看不见。

**同一个事实带来一个测试上的硬限制**：jsdom 没有布局引擎，`getBBox()` 一律返回 0，
**mermaid 在单测里画不出任何东西**。所以「渲染」这一层必须可注入 ——
M8 的编辑器与导出单测都用假渲染器，钉住的是我们这一层的契约
（谁被换掉、失败留下什么、主题传对了没有），而不是「图画得好不好看」。
后者只能人工看。

### 5. 为什么导出永远按浅色画

导出产物是一张**纸**：`core/export/document.ts` 的 `PAGE_STYLES` 把底色写死成浅色，
它没有深色模式。所以哪怕用户此刻用深色主题，图也必须按浅色画 ——
否则会出现「浅色的纸上一张深色底的图」。这与 `Lightbox.tsx` 那条「灯箱恒深」
是同一类判断：**容器决定配色，而不是应用当前的主题决定配色**。

编辑器里则相反：图的配色**跟随应用主题**（`theme: 'default' | 'dark'`），
换主题时靠一个盯根元素 `data-theme` 的 `MutationObserver` 触发重画 ——
换主题不会派发任何事务，插件收不到通知。

## 代价与已知问题

1. **配色只是明暗一致，不是同一套色号。** 用的是 mermaid 的内置主题
   （`default` / `dark`），不是轻墨的「宣纸 / 松烟」。要做到色号一致得走
   `theme: 'base'` + `themeVariables`，把我们的 CSS 变量读出来喂进去 ——
   那是一条真实存在的路，只是 M8 没做。重审条件见文末。
2. **`dist/` 里有**两份** KaTeX**（`katex-*.js` 各 259 kB）。不是打包器的问题：
   mermaid 依赖 `katex@^0.16.47`，而我们用 `katex@^0.18.9`，两者 semver 不重叠，
   npm 于是装了两份（`node_modules/mermaid/node_modules/katex`）。
   两份都是懒加载的，只有「同一会话里既看公式又看图」才会都下载。
   把我们的版本降到 0.16 能省掉它，但会丢掉 0.18 的修复 —— 不划算。
3. **`dist/` 大了 3.4 MB**（见上）。
4. **图表不能进表格**：`code_block` 本身进不了表格，所以这条没有额外代价，
   但代码块的语言选择器里出现 `mermaid` 时，用户可能以为选它就会出图 ——
   实际上会（切到 mermaid 就画），这一点是符合直觉的。
5. **`renderMermaid` 对空源码短路**（`EMPTY_DIAGRAM_MESSAGE`）。这不只是文案问题：
   不短路的话，一个**空**的代码块就会把 mermaid 那 3.4 MB 拉下来。
6. **全屏查看器与灯箱是两个组件**，不是同一个加开关。图表没有文件路径、
   没有原始尺寸，而灯箱的两条核心规则（恒深底、显示路径）对图表都不适用。

## 重审条件

1. **mermaid 支持按图种裁剪打包时**（或社区出现成熟的裁剪方案），
   重算 `dist/` 那 3.4 MB —— 多数文档只会用到 flowchart / sequence。
2. **mermaid 把 katex 依赖升到 `^0.18` 之后**，检查产物里是否只剩一份 KaTeX。
3. **用户反馈「深色主题下图的配色和正文不搭」时**，走 `theme: 'base'` +
   `themeVariables`，从 `document-styles.css` 的变量读色。
4. **出现「图表块很多、滚动卡顿」的反馈时**，重看 `MutationObserver`
   与每次渲染新建容器的开销；那时的方向是**可视区外不渲染**（而不是缓存 SVG）。
5. **要支持 `mmd` 等别名时**，先确认 GitHub / VS Code 默认也认它们 ——
   否则就是我们制造的分歧（见理由 2）。
