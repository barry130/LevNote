# 0033 · 往返保真度自检：给用户知情权，不替用户做主

日期：2026-10-05
状态：已采纳（P6 第 29 项落地）
关联：0004（编辑器内核）、`docs/open-decisions.md`「原文保真的实测与收窄」、
`core/fidelity.ts`（比对与报告）、`EditorHandle.roundTrip`（契约）、
`ROADMAP.md` 第 29 项

## 背景

Markdown 内核「打开 → 不改 → 保存」不保证逐字节还原：解析成文档树再
序列化回去会做**故意保留**的规范化（实测 2026-10-02 的基线：真实长文档
「改一个字」改写 30/765 行，全是表格对齐空格；`-` 列表与 `---` 已不再被
改写）。这些改写让写回的文件更规整，是正确的取舍 —— 但用户有权
**显式看到**「我的文件会被动到哪」，而不是某天保存后自己发现。

第 29 项要的就是这个：**一个显式的、如实报告差异的动作**。

## 决策

### 1. 它是诊断动作，不是修复

命令 `diagnostics.roundTrip`（分组「诊断」）：拿**磁盘上的原文**
（`doc.savedText`）走一遍内核自己的「解析 → 序列化」，与原文逐行比对，
弹窗报告「不改一个字保存会改写 N 行（修改 / 新增 / 删除）+ 至多三条样例」。
**只读不写** —— 不改文档、不落盘、不试图替用户把差异抹平
（「修复」等于把规范化悄悄撤销，那是另一个决策，且方向未必对）。

基准取 `savedText` 而不是当前编辑内容：用户改过的部分是「他的改动」，
不属于「内核会改写什么」这个问题。

### 2. 「解析 → 序列化」必须由内核实现，外壳不另起管线

契约加在 `EditorHandle.roundTrip?`（可选能力）。Markdown 内核的实现
**复用活实例的 parser / serializer** —— normalize-ast 插件、`-` 列表符号、
remark-stringify 选项都长在实例上，外壳里另起一条 remark 管线会漏掉它们，
量出来的差异是假的。这是硬约束 11 的推广：内核知识不许漏进外壳。

**trailing 规则的复刻**：真实保存路径的文档结尾会经 trailing 插件的
appendTransaction 补一个空段落（最后一个节点不是标题 / 段落时）。
roundTrip 不经过 dispatch，必须自己复刻同一条规则（规则抄自
`@milkdown/plugin-trailing` 的 `shouldAppend`），否则以代码块 / 表格结尾的
文档会**漏报**「保存会多出一个空段落」。内核测试钉住了
`roundTrip(source) === getMarkdown()`（真实保存路径的产物）。

代码与纯文本内核的实现是**恒等**（源码即文档，往返零改写）—— 如实实现，
让自检能报出「不会改写任何内容」。导图内核不实现，命令禁用。

### 3. 比对与报告是纯函数，外壳只管弹

`core/fidelity.ts`：行级 LCS（Int32Array，约 2000×2000 行上限），差异分
修改 / 新增 / 删除三类（连续的删+增折算成「修改」，报告读起来是
「这行被改了」）；超过上限退化为多重集计数并**如实标注「未逐行比对」**。
样例最多三条、每条截断 40 字符 —— 提示框是给人看的，不是给机器对账的。

## 后果

- 用户第一次有了「保存之前先看看会动什么」的入口；报告里的差异是有意
  保留的规范化，看到不代表要修。
- `EditorHandle` 契约多一个可选方法 —— 与 `search` / `blockHandle` 同一列
  可选能力，不实现按禁用显示。

## 重审条件

- **基线数字恶化**：如果自检实测出现新的改写类别（不再只是表格空格），
  先回到「原文保真的实测与收窄」判断该类别是规范化还是数据损失 ——
  损失类必须修内核，不能靠报告兜底。
- **字符级 diff 的需求**：行级 LCS 看不出「同一行里改了哪几个字符」；
  若反馈说样例不够用，先考虑样例加量（5 条、8 条），再考虑字符级。
- **导图内核**：若 `.mindmap` 的写回规范化也需要知情权，给 mindmap 内核
  实现 `roundTrip`（语义是「JSON 转置会不会改写用户数据」），不要复用
  Markdown 的行比对。
