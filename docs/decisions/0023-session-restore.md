# 0023 · 会话恢复：标签页与**未保存的草稿**一起回来

状态：**已采纳**

## 背景

到 M10 为止，关掉窗口再打开，一切从头开始：标签页没了、文件夹没了、
光标位置虽然在（ADR 0021），但**没保存的内容没了**。

这不是一个体验项。对标清单里它被单独标出来：

> `| A7 | 会话恢复 / 未保存草稿不丢 | ❌ 未做 | **这是数据安全问题**，不是体验项 |`

「数据安全」的判据很具体：**强杀进程后重启，未保存的标签页内容与光标位置都还在**。
用户崩一次就会失去信任 —— 而崩一次的成本，是他在那一刻正在写的所有字。

位置记忆（0021）已经解决了「光标」这一半，这一条解决另一半。

## 决策

1. **新增 `core/session.ts`**，单独一个存储键 `qingmo.session.v1`
   （与 `settings` / `positions` 各自独立）。
2. **草稿就是整篇 `doc.text`**，在标签页**被激活之前**写进 `DocumentStore`，
   于是那个标签页天然是脏的（`text !== savedText`）。
3. **`WorkspaceStore.restoreTabs(entries, activePath)` 批量恢复**：
   整个过程只通知一次、只创建一个内核。
4. **打不开的路径不写进 `openError`**，而是整份清单交回外壳，用一条横幅说完。
5. **容量有上限**（50 个标签页 / 150 万码元草稿），超出的按最后编辑时间从旧到新裁；
   **被裁掉几条要存进 `droppedDrafts`，在下一次启动时如实告诉用户**。
6. **`restoreSession` 是可见开关**（默认开）。关掉 = 不读也不写，且**清掉已有记录**。
7. **落盘防抖 1000ms**，另外在切标签页、`beforeunload`、
   `onCloseRequested` 三处立即结算。
8. **`sameSession` 挡住无谓的写**：内容没变就不写盘。

## 理由

### 1. 为什么草稿在标签页激活**之前**就写进 store

因为面板是**照着 `doc.text` 挂载的**（`DocumentPane` 把 `doc.text` 交给
`initialValue`）。顺序反过来的话，内核会先用磁盘内容建一遍、再被整篇替换一次 ——
白花一次内核创建（实测两万字文档 700ms 上下），中间还会闪一下磁盘版本。

这也顺手取消了「面板要记得别用 `doc.text` 覆盖草稿」这类约定：
**草稿在 store 里，`doc.text` 就是唯一真相**。

### 2. 为什么 `restoreTabs` 是批量方法，而不是循环调 `open()`

`open()` 每打开一个就把那个标签页**激活**一次。循环调它意味着启动时 N 次
`activeId` 变化、N 次外壳重渲染、N 次内核创建。十个标签页的会话会变成
「启动要等好几秒，中间还闪十下」。

批量方法把「塞进去」与「通知」分开：整个恢复过程只有**一次** `syncTabs()`，
也就只有一个内核被创建。

### 3. 为什么打不开的路径不能写进 `openError`

`openError` 是「一个错误横幅」的单槽位。启动恢复可能一次失败好几个，
逐条塞进去的结果是用户只看到**最后一条**，前面几个文件**悄无声息地不见了** ——
而它们里面有草稿。这正是硬约束 2 要挡的那种静默。

所以 `restoreTabs` 返回整份 `failed` 清单，由外壳用一条横幅把话说完。

### 4. 为什么会话的校验策略与 `positions` **相反**

`positions` 是「任何一项不合法就整条丢」：拿一个错的 `offset` 去恢复，
会把光标悄悄移到别处，用户会以为文件被改了 —— 丢掉它只是「回到顶部」，是诚实的失败。

会话是**逐条丢**：一个标签页的记录坏了，不该连累其余九个。
草稿不合法时**只丢草稿、保住路径**（路径还在就还能把文件打开），
路径不合法时整条丢且**不计入 `droppedDrafts`**（路径都没了，告诉用户也做不了任何事）。

两者的差别来自**损坏的代价**：位置记错是「光标在错的地方」，
会话记错是「用户刚写的字没了」。

### 5. 为什么「丢了几条草稿」必须**存下来**，而不是当场提示

裁剪发生在**写**的时候，而告知发生在**下一次启动**，中间隔着一次进程结束。
没有 `droppedDrafts` 这个字段，用户永远不会知道自己的草稿被丢了 ——
而他会以为它还在（这正是最坏的一种失败）。

`droppedDrafts` 因此是**累加**而不是覆盖：先丢 2 条、再丢 3 条，最后要提示 5 条。

### 6. 为什么 `restoreSession` 关掉时要**清掉**记录

只做「不再写」是不够的：用户关掉它、用一阵子、再打开，会突然恢复出
**几天前**那一批标签页与草稿。那不是「恢复上次」，那是从坟里刨东西。

### 7. 为什么恢复期间不许落盘（`sessionReadyRef`）

启动时 `workspace` 还是空的，而落盘是被防抖定时器驱动的。
恢复读完 N 个文件之前那一次写，会把一份**空会话**覆盖上去 ——
用户的草稿在他自己看到之前就没了。

这道闸门同时挡住了另一个陷阱：React 的 StrictMode 会把启动 effect
「建立 → 清理 → 再建立」跑一遍，而清理函数里有一次补写。

### 8. 为什么 `sameSession` 把 `droppedDrafts` 也算进比较

它读出来之后就该被清零。算进来的效果是：启动后的第一次写盘会因为
「旧账目 ≠ 0」而必然发生，正好把那份账目清掉。不算的话那次写盘可能被跳过，
用户**下一次启动又会看到同一条提示**。

### 9. 为什么外壳可以**普通订阅**文档 store

「外壳刻意不订阅文档 store」那条规则针对的是 `useSyncExternalStore` ——
那会让每次按键都重渲染整个外壳。这里用的是普通订阅，回调里只重置一个定时器、
不碰任何 state，没有任何渲染成本。用普通订阅换来的是**不必给面板再加一个回调 prop**，
而且顺手覆盖了编码 / 行尾这类不改文本的改动。

## 代价与已知偏离

- **只恢复磁盘上还在的文件。** 文件被删 / 被移走之后草稿没有落脚点。要救那种情况
  需要「无路径的虚拟标签页」（保存时得先问存哪儿，而那个对话框在启动恢复这条路径上
  会连着弹好几个）。当前取舍是**宁可明确地不恢复，也不要造一个用户看不懂的标签页** ——
  并且用横幅如实说出来。
- **只恢复文本，没恢复用户手动指定的编码与行尾。** 那两项在 `open()` 时重新探测，
  所以「改了行尾但还没保存就崩了」这一种改动会丢。不一起存是因为它们正常路径上是
  **磁盘的属性**，存一份等于造出第二个真相来源 —— 文件在关闭期间被别的工具转码之后，
  恢复的记录会以**旧编码**写回去，而那是一次静默转码。宁可丢一次「手动改了行尾」，
  也不要冒一次静默转码的风险。
- **草稿是整篇文本，存储开销与文档长度成正比。** 一份两万字的中文文档约 60 KB
  （utf-16 算 120 KB）。所以有上限、有裁剪、有「丢了几条」的如实告知。
  将来若要做「大文档不落草稿」的阈值，判据应该是**写一次 `setItem` 的耗时**，
  而不是文档大小 —— 目前没有实测数据支持设这个阈值。
- **没有做「崩溃恢复提示」的二次确认**（比如「要不要把草稿存成副本」）。
  当前是直接恢复到标签页里、保持脏状态，与崩溃前完全一样。
- **`restoreTabs` 会读 N 个文件**，启动时有一次与标签页数量成正比的 I/O。
  实测（jsdom，非真实磁盘）10 个标签页在毫秒级；真实磁盘未测。

## 重审条件

1. **启动耗时**。如果真实机器上「恢复 20 个标签页」超过 1 秒，就要改成
   先只开 `activePath` 那一个、其余延后到空闲时再开 ——
   但那会让标签栏先显示一个再慢慢长出来，是另一套体验，需要重新权衡。
2. **存储写不进去**（`saveSession` 返回 `ok: false`）。届时界面上会出现
   「会话记录写不进去」的横幅 —— 那说明「自动备份」这条线断了。
   如果这种情况在真实环境里出现得多，就要换掉 `localStorage`
   （Tauri 的 store 插件 / 应用数据目录里的一个 JSON 文件），而不是加提示。
3. **`droppedDrafts` 真的被触发过**。那说明 150 万码元这个上限定小了，
   或者「整篇草稿」这个做法在长文档上不成立 —— 后者要改成增量草稿，
   而那需要「保存基线 + 变更集」，是一次架构级的改动。
4. **第 14 项（Rust 侧 `watch`）落地之后**，`onCloseRequested` 那一次补写
   可以删掉：文件监听能更早地发现外部改动，而窗口关闭的时序不再是唯一的
   「最后一次机会」。
