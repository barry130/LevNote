# 0022 · 外壳改用 VSCode 式布局；视图从两态扩成三态（富文本 / 源码 / 源码+预览）

状态：**已采纳**

## 背景

两件事凑在一起，但它们其实是同一件事的两面。

**第一件：外壳的形状。** 到 M9 为止，外壳的形状是「标题栏 + 标签栏 + 侧栏 + 编辑区 + 大纲」，
配色是轻墨自己的品牌色。功能都齐了，但**面板的入口散落在三个快捷键和两个工具栏按钮里**，
而快捷键不是发现功能的入口 —— 这是 M9 写设置页时就已经承认过的判断。
同时，用户明确要求「使用 VSCode 的风格搭建 UI」。

**第二件：Markdown 只能看一边。** 视图只有两态（富文本 / 源码，ADR 0014），
而写 Markdown 最常用的姿势是**一边源码一边渲染**。Typora 用「所见即所得」绕开了这个问题，
但我们的富文本内核在保存时会对源码做规范化（这正是 ADR 0017 关掉 Crepe 的原因），
所以「源码原文」和「渲染结果」都需要能被看到 —— 最好是同时看到。

用户的原话是：

> 使用 VSCODE 的风格搭建 UI。md 格式需要支持源码和预览版放在一个页面
> 类似于这种布局风格，但是 md 可以源码版和预览版放在一个页面(也可以选择任意展示其中一个)

「也可以选择任意展示其中一个」是这句话里最要紧的部分：它不是「加一个分屏」，
而是**把视图从两态改成三态**。

## 决策

1. **外壳改用 VSCode Light Modern / Dark Modern 的语义色板**，
   但**品牌色（`--ink` / `--vermilion` / `--bamboo` / …）一个都不动**。
2. **新增活动栏**（`.activitybar`，48px）作为「这个应用有哪些面板」的常驻入口。
3. **`ViewMode` 从 `'rich' | 'source'` 扩成 `'rich' | 'source' | 'split'`**（枚举，不是两个布尔）。
4. **分屏 = 左栏 `primary.sourceView`（可编辑）+ 右栏 `primary` 加 `readOnly`（只读）**，
   两栏共用 `store` 里那份 `doc.text` 权威副本。
5. **右栏的只读靠 ProseMirror 的 `editable: () => false`**，不另造 Markdown → HTML 渲染管线。
6. **左栏 → 右栏的内容同步防抖 160ms**；**滚动联动复用 ADR 0021 的 `textLength` 凭据机制**，
   即「跨内核传位置时 textLength 必然对不上 → 右栏只滚不跳光标」。
7. **分屏比例存进 `ViewSettings`（`splitRatio`，0.2–0.8，只存比例不存像素）**。
8. **右栏创建失败只标右栏**（`previewFailedKey` 与 `failedKey` 分开），并**在界面上说出来**。

## 理由

### 1. 为什么是枚举而不是 `split: boolean`

「源码」和「分屏」不是两个独立的维度：**分屏的左栏就是源码视图**。
用两个布尔值表达，就等于允许界面进入 `{ source: true, split: true }` 这个
自己都说不清的状态 —— 而那种状态下两个按钮的亮灭组合看起来都是合理的，
用户没法判断哪个对。枚举把这个不可能的状态从类型上就消掉了。

`toggleSourceView` 的判据相应写成「是不是 `rich`」而不是「是不是 `source`」：
分屏也属于源码那一侧，从它切回去的落点应该是富文本 —— 与源码模式同一个出口。
少写这一层，用户从分屏点一下会落到一个他刚才没选过的状态上。

### 2. 为什么预览复用首选内核 + `readOnly`，而不是另造一条渲染管线

另一条路是「Markdown → HTML → 塞进 `dangerouslySetInnerHTML`」。它看着简单，代价有三层：

1. **长相会不一致**：预览和富文本视图会得到两套排版，用户一定会认为其中一个是错的；
2. **要各自维护一遍**表格、公式、图表、图片相对路径解析 —— 而这四样恰好是 M5 / M6 / M7 / M8
   各花一个里程碑做出来的东西；
3. **导出管线已经存在**（`core/export/`），再加一条就成了三条。

而复用首选内核只需要一个 `readOnly` 属性，而且 Markdown 内核**已经**支持它了：
`editorViewOptionsCtx` 里写的是 `editable: () => !options.readOnly`，
这是 ProseMirror 原生意义上的只读，不是「拦下按键」那种假只读。

> 这一条与硬约束 11 是同一个思路：**内核的东西，内核说了算**。
> 预览要的是「同一个内核的另一种用法」，不是「另一个内核」。

### 3. 为什么 `textLength` 对不上是**特性**而不是缺陷

滚动联动靠的是 `handlePositionChange` 里顺手调右栏的 `setPosition`。
左栏报的是源码字符数、右栏算的是 ProseMirror 的 `doc.content.size`，两者**必然对不上** ——
于是右栏会走 ADR 0021 定下的那条路：**只恢复滚动、不动光标**。

这正是分屏想要的效果：两栏一起滚，但预览栏不抢焦点。

> 换句话说：**跨内核传位置时「对不上」是这里唯一正确的行为。**
> 若哪天有人「修好」了 textLength 让两边相等，右栏就会开始跟着左栏跳光标，
> 而那是一个比不联动更糟的结果 —— 用户在左栏打字，右栏的选择区在动，
> 他每打一个字都要重新确认一次「我刚才是不是点错地方了」。

### 4. 为什么内容同步必须防抖

`doc.text` 每敲一个字就变一次，而右栏拿到新文本要**整篇重新解析**
（`setValue` 是一次完整 parse + 重新渲染全部节点）。逐字推过去等于
**把打字成本乘以文档长度** —— 而这正是 `open-decisions.md` 里 V3 要测的那类退化，
分屏恰恰是最容易把它引出来的场景。

窗口取 160ms：落在「连续击键间隔（约 80–150ms）」与「人开始察觉延迟（约 200ms）」之间。
连续打字时它一直在重置、一次都不推（等用户停手），停手后到预览更新只隔一次眨眼。

### 5. 为什么 `previewFailedKey` 必须与 `failedKey` 分开

共用会造成一个很难查的连锁反应：右栏起不来 → 标记成「这一次内核失败」→
左栏被判定失败 → **整个文档退化成白底 textarea**。
而实际情况是「预览渲染不出来，源码完全正常」—— 用户会以为文件坏了。

分开之后，失败只降该降的那一半，而且界面上有一条告示条如实说明
（「绝不静默」在分屏这一处的具体形态）。

### 6. 为什么品牌色不动

`--ink` / `--vermilion` / `--paper` / `--bamboo` / `--moss` / `--slate` / `--plum` / `--blue`
不只是外壳的颜色：它们是**语法着色**（`--syn-*`）与**导出文档**（`core/export/document-styles.css`
的 `--qm-*`）的身份色。换掉它们会连累用户**导出出去的每一份文件**。

所以「VSCode 风格」到外壳与编辑器表面为止，不越界去改文档长什么样。

### 7. 为什么分屏比例只存比例不存像素

比例与窗口大小无关，换个窗口宽度打开还是同一个观感；存像素的话，
在宽屏上调好的 800px 到了窄窗口就变成「预览只剩一条缝」。
这与位置记忆里滚动用比例（`EditorPosition.scrollRatio`）是同一条理由。

上下限**刻意不是 0 和 1**：那会让另一栏宽度归零而它仍然占着 DOM，
用户会看到「分屏开着但只有一栏」，既不知道为什么、也拖不回来
（分隔条本身也只剩一个像素）。要只看一栏请用另外两档。

## 代价与已知偏离

1. **状态栏不横跨整个窗口宽度。** VSCode 的状态栏横跨全宽，而我们的这一条是
   `DocumentPane` 的 footer，只横跨编辑器那一栏。原因是它显示的全是**这一份文档**的信息
   （编码、行尾、光标、字数、视图模式），而外壳刻意不订阅文档状态
   （见 `App.tsx` 顶部那段：否则用户每敲一个字整个外壳都要重渲染）。
   一条少横跨 240px 的状态栏，换掉「每次按键重渲染侧栏和标签栏」，这笔账是划算的。
2. **工具栏那个「源码 / 富文本」开关与状态栏的三档切换并存**，功能上有重叠。
   这是刻意的：那个是两态开关（按一下换一边，符合肌肉记忆），
   这个是三选一（一次点到分屏）。两者都不替代对方。
3. **`splitRatio` 拖动期间不落盘**，松手才写一次 —— 逐次 `pointermove` 都写
   localStorage 会让拖拽明显发涩。与 `sidebarWidth` 同一套处理。
4. **主包大了约 6.5 kB**（1,743.31 → 1,749.85 kB）。这部分是外壳本身，
   没有懒加载的余地（活动栏、图标、视图切换器都是首屏就要画的）。
5. **分屏的比例调整只有人眼能验**：jsdom 没有布局引擎，`getBoundingClientRect()` 全 0，
   所以单测只能钉住「量不到宽度时是空操作」这一条防线（否则会算出 `NaN` 并持久化）。

## 重审条件

- **V3（长文档输入延迟 ≤ 50ms）跑出结论之后。** 如果结论是「要换到源码优先架构」
  （horseMD 的远期方向：以 CodeMirror 文本为唯一数据模型、用 decorations 呈现格式化内容），
  那么分屏右栏就该换成「同一份源码的另一种 decorations 渲染」，
  而不再是「第二个内核实例」。**这会让决策 4 与 6 一起作废。**
- **如果 `splitRatio` 收到「我调好的比例又变回去了」这类反馈**，
  说明只存在 `ViewSettings` 里不够（它没有按文档记），需要重新考虑存储位置。
- **如果第三个内核（思维导图 / draw.io）声明了 `sourceView`**，
  分屏会自动对它可用 —— 那时要重新确认「右栏只读渲染」对它们是否也成立。
