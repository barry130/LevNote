# 0019 · M7 数学公式：不用已废弃的官方插件，自研节点 + 输入规则 + NodeView

状态：**已采纳**（M7）

## 背景

M7 的交付是「Markdown 里的 LaTeX 数学公式」：打字时识别、编辑时校验、
渲染成 KaTeX、导出时自包含。这是 `ROADMAP.md` 第 14 项。

它要一次定下六件事：

1. 用不用 Milkdown 官方的公式插件；
2. **打字时的识别**与**重新打开文件时的识别**怎么保证一致；
3. 公式值存在节点的哪个属性里；
4. KaTeX（约 259 KB 的 JS）进不进主包；
5. 导出的单文件怎么在没有网络的机器上也有字形；
6. KaTeX 的字体文件怎么处理（三份格式、20 个字族）。

## 决策

1. **不用 `@milkdown/plugin-math`，自研节点 + 输入规则 + NodeView。**
2. **识别的判定交给 `remark-math`**（`core/math.ts` 的 `inlineMathAtEnd`），
   不自己写正则去认 `$…$`。
3. **值统一存在 `attrs.value`**，DOM 上落成 `data-tex`。
4. **KaTeX 动态加载**（`import('katex')`），不进主包。
5. **导出时内联 KaTeX 的 CSS + 20 个 woff2 的 data URI**，只在文档真有公式时才拼。
6. **编辑器产物里只留 woff2**，woff / ttf 一律不进包。

## 理由

### 1. 为什么不用官方的 `@milkdown/plugin-math`

它**已废弃**：最后一版 `7.5.9` 停在 2024-12-16，而 `@milkdown/kit` 已经是
`7.22.2`。跨 17 个小版本的插件意味着「它引用的 composable 出口是否还在」
要自己验一遍，而它内部是 Vue 的 NodeView 实现 —— 与 0017 拒绝官方表格 /
代码块是同一条理由：**引入它就要连带引入它的 UI 框架与样式体系**。

自研的部分是：两个节点 schema、两条输入规则、一个 NodeView。公式与表格不同，
**没有跨单元格选择、没有行列增删**这类交互，NodeView 只有「渲染态 ↔ 原位编辑」
两个状态，自研的成本是可控的。

代价是「`$…$` 的边界规则」这件事得自己保证正确 —— 见下一条。

### 2. 识别必须复用解析器，不能自己写正则

一条 Markdown 的公式在**两个时刻**被识别：

- 用户刚打完 `$x$`（ProseMirror 的 `InputRule`）；
- 重新打开文件（`remark-math` 解析 mdast）。

这两处如果各写一套规则，就一定会分叉 —— 而分叉的表现是
**「打字时看着是公式，存盘重开变成一段字面文本」**，或者反过来。

所以 `core/math.ts` 的 `inlineMathAtEnd(text)` 直接把候选串喂给
`unified().use(remarkParse).use(remarkMath)` 跑一遍，再看最后那个 paragraph
的最后一个子节点是不是 `inlineMath`。**同一个解析器，同一个答案。**

这条路上有两个不显然的坑，都写进了实现：

- **`InputRule` 拿到的 `textBefore` 会被截断到 500 字符**（ProseMirror 的
  `MAX_MATCH`）。长段落里打公式就会静默认不出来。所以取的是
  `$end.parent.textBetween(0, $end.parentOffset)` 这一整块，不是 `textBefore`。
- **判「公式是否贴着文本末尾」必须用绝对偏移。** remark 不会为末尾空格留
  文本节点，所以 `'$x$ '` 的最后一个子节点**就是** `inlineMath` —— 只看类型
  会把它误判成「贴着末尾」。判据是 `position.end.offset === text.length`。

### 3. 值存 `attrs.value` + `data-tex`

`data-tex` 同时是三个地方的契约：NodeView 读它、导出扫它
（`querySelector('[data-tex]')` 判断「这篇文档有没有公式」）、测试钉它。

用 `data-` 而不是类名，是因为类名是渲染细节（0018 的灯箱讨论过同一件事），
而 `data-tex` 是**文档内容的投影**。

### 4. KaTeX 动态加载

`katex` 的 JS 是 **258.94 kB（gzip 77.67 kB）**。主包本来就是 1.7 MB，
再加 259 KB 而绝大多数会话根本不写公式，不划算。

`core/katex.ts` 用 `import('katex')` 并缓存那个 Promise，
**失败时不缓存**（否则一次网络抖动会让整个会话都渲染不出公式）。
实测产物里它是独立 chunk（`katex-*.js`），主包大小与 M6 之前一致。

### 5. 导出：只在真有公式时才拼那份样式

KaTeX 的 CSS 加上 20 个字体的 data URI 大约是 **354 KB**（CSS 约 20 KB +
字体 254 KB 的 base64，膨胀约 1/3）。一份没有公式的文档不该背这个包袱。

所以导出路径先 `root.querySelector('[data-tex]')` 探一下，
**没有公式就一个字节都不拼** —— 有测试用「一调用就抛的 io」钉着这条：
真去读了，测试就红。

内联字体而不是让导出文件去引用外部字体，是 0001（自包含导出）的直接后果：
导出的 HTML 要能在断网机器上双击打开。

### 6. 构建期只留 woff2（798 KB 死重）

`katex.min.css` 的每条 `@font-face` 指向三个文件。编辑器那份 CSS 一旦
`@import` 它，Vite 就把**三个都**当资源产出：实测 60 个文件、1.05 MB，
其中 woff 与 ttf 那 **798 KB 永远不会被取用** —— 目标环境只有 WebView2
（Chromium）与 WKWebView（WebKit），两者从 2016 年起就支持 woff2。

所以加了一个 PostCSS 插件（`vite.config.ts` 的 `katexWoff2Only`），
把每条 `src` 收敛成只留 woff2。修复后 dist 从 3.2 MB 降到 2.4 MB，
字体从 1.05 MB 降到 **253.7 KB（20 个 woff2，一个不多一个不少）**，
而 woff2 那部分的资源哈希与修复前**逐字节一致** —— 说明只掉了死重。

## 代价与已知的坑

### 1. `$5 到 $` 会被当成公式 —— 这是上游规则，我们选择跟随

`micromark-extension-math` 只在内容**首尾同时是空白**时才剥离空白，
所以 `$5 到 $` 的值是 `'5 到 '`，是一条合法的行内公式。

**不修正它。** 一旦我们在识别上偏离上游，第 2 条决策（「同一个解析器，
同一个答案」）就破了 —— 表现是打字与重开不一致。用户遇到这种情况的
出路是写成 `\$5 到 \$`，这也是 Markdown 里表达字面量美元符号的通行写法。

### 2. `remark-math` 的两个往返坏例（实测，不是推测）

测试里**真的用 `remark-stringify` 存一遍再读回来**，钉住两条：

| 情形 | 后果 |
|---|---|
| 行内公式的值为**空** | 序列化成 `$$`，读回来变**块级公式**，把段落劈成两半 |
| 行内公式的值含**空行** | 读回来**整段消失**（变回两段普通文本） |

块级公式**一个都不坏**（含空行、含值里自带 `$$` 都正确）。

所以 `texProblem(tex, 'inline')` 会拦住这两种值。而输入规则里也加了同一条
判断 —— 否则 `$ $` 会生成一个「自己拒绝保存」的节点，属于内部不自洽。

> 顺带一个实现细节：行内公式的编辑器是 `<input>`，它会**剥掉值里的换行**，
> 所以「行内公式含空行」在界面上走不到；那条拦截防的是**程序写入**
> （粘贴、将来的导入）。块级用 `<textarea>`，可以含空行。

### 3. `setBlockType` 只接受 textblock —— 块级输入规则踩过

块级公式是**块级原子节点**。初版输入规则写成
`tr.delete(…).setBlockType(…, mathBlockSchema.type(ctx))`，
抛出 `RangeError: Type given to setBlockType should be a textblock`。

这是一条**未捕获异常**，会顺着 `handleTextInput` 冒出来 —— 用户看到的只是
「`$$ ` 变成了字面量」，整次输入无声失败。改用
`tr.replaceWith($end.before(), $end.after(), type.create())`。

### 4. 斜杠菜单插入块级公式**不能吃掉段落文字**

初版 `insertMathBlock` 无条件 `replaceWith($from.before(), $from.after(), node)`。
实测 `前文/公` → 插入后只剩 `$$\n$$`，**`前文` 消失了** —— 而
`table` / `codeBlock` / `hr` 都保留内容。改成「段落为空才整块替换，
有文字就插在后面」，并补了回归用例。

这条和上一条都是**探针先证实、再修、再补测试**，不是读代码读出来的。

### 5. KaTeX 的错误信息不能直接显示

`renderToString` 抛出的错误里，`message` 含**组合下划线** `\u0332`
（KaTeX 用它标出错误位置），直接渲染出来是一串乱码似的重影。
可用的是 `rawMessage`（如 `Undefined control sequence: \foo`）加 `position`。
`describeMathError` 优先用这两个，并译成「第 N 个字符起」。

### 6. `trust: false` 的安全边界（有测试钉着）

`trust: false` 下 `\href` / `\url` / `\includegraphics` / `\htmlStyle` /
`\htmlClass` / `\htmlId` / `\htmlData` 都被渲染成红色的命令名
（`<mstyle mathcolor="#cc0000">`），**不产出 `<a>` / `href=` / `src=`**。

源码原文会嵌进 `<annotation encoding="application/x-tex">`，且**会被 HTML
转义**（`\text{<script>}` → `&lt;script&gt;`）。

有一条用例专门断言「渲染结果里没有 `<a>`、没有 `href=`、没有 `src=`」，
另有一条钉住尖括号被转义。

### 7. woff2 **不能**内联成 data URI（CSP）

Vite 默认把小于 4 KB 的资源内联成 `data:` URI，而
`KaTeX_Size3-Regular.woff2` 正好是 **3624 字节**，会踩中这条线。

一旦它变成 data URI，导出侧那句 `fetch('data:…')` 会被 Tauri 的 CSP 拦下来
（`connect-src 'self'` **不含** `data:`），于是**这个字体静默缺失** ——
导出的文件里 `\sum` 之类的大号符号掉字形，而导出提示什么都不说
（它只知道「这个字体没拿到」，不知道「为什么」）。

所以 `vite.config.ts` 里 `assetsInlineLimit` 对 `.woff2` 一律返回 `false`。

### 8. 不做字体子集化 —— 而且理由是具体的

很自然会想「按用到的字族裁剪字体」。**实测推翻了它**：
`KaTeX_Main` 走的是 `.katex{font:…KaTeX_Main…}` 这个 **`font` 简写 + 继承**，
按选择器匹配字族名**会漏掉它** —— 而漏掉的表现是**整篇公式的字母掉字形**。

这也正是「不做」而不是「暂时不做」的理由：判据本身不可靠，
出错方式是静默的、全局的。

### 9. 那两条弯路（都值得记，因为都是「构建成功但产物坏」）

**弯路一：Vite 的 `transform` 钩子改不到 `@import` 进来的 CSS。**
第一版把「只留 woff2」写成 `transform(code, id)` + `enforce: 'pre'`，
**实测无效** —— 重建后 woff/ttf 一个没少。根因是 `@import` 由
`postcss-import` 在 PostCSS 管线内部读盘内联，**根本不经过 Vite 的模块图**
（探针里 `katex.min.css` 从未以模块形式出现在 `resolveId` / `load` /
`transform` 的任何一次调用里）。钩子挂在一个永远不会被经过的路口上。

**弯路二：把 CSS 重新 `postcss.parse` 一遍，会让字体 404。**
改成 PostCSS 插件后，第一版实现是「`root.toString()` → 文本变换 →
`postcss.parse` → 换掉整棵节点树」。构建**成功**，但日志里出现

```
fonts/KaTeX_Main-BoldItalic.woff2 referenced in … didn't resolve at build time
```

根因：Vite 解析 `url()` 时用的 importer 是**每个声明自己的**
`declaration.source.input.file`（`vite-url-rewrite` 插件里那句
`const importer = declaration.source?.input.file`）。重建节点把来源从
`katex.min.css` 改成了 `markdown.css`，相对路径的基准就变了 ——
产物里字体 404、公式全部掉字形，而构建照样成功。

**所以现在的实现是就地改 `decl.value`，一个节点都不重建**，
并有一条用例钉住「节点对象与来源信息都不换」。

> 这两条的共同教训：**「构建成功」不能作为「产物正确」的证据。**
> 它们只有真的跑一次 `vite build` 再打开产物才会暴露。

## 与既有决策的关系

- **0017（M5 自研两半）**：M7 继续自研。理由同构：官方实现要么已废弃，
  要么绑定别的 UI 框架。
- **0018（M6 图片）**：同一套「内核画 DOM、外壳画界面」的分工。
  公式的 NodeView 与图片的 NodeView 是同一个模式；不同之处是公式有
  **原位编辑态**，图片没有。
- **0011（优雅降级）**：公式渲染失败时**保留源码 + 说明原因**，
  而不是留一个空壳或一行红字。这与「降级要掉到次优而不是最底」是同一条。
- **0001（自包含导出）**：第 5 条决策（内联字体）直接来自它。

## 重审条件

1. **`@milkdown/plugin-math` 复活并跟上 `@milkdown/kit` 的主版本** →
   重新评估要不要换回官方实现（判据：它的 NodeView 是否还依赖 Vue）。
2. **`remark-math` 改变 `$…$` 的边界规则**（例如开始支持转义更激进的写法）→
   第 2 条决策（识别复用解析器）让这件事**自动跟随**，但
   `core/math.test.ts` 里那两条往返坏例要重跑确认。
3. **KaTeX 的 CSS 结构变了**（出现 `@media` 或嵌套 `{}`）→
   `katex-fonts.ts` 的正则切法失效。它会**让构建失败**（不是静默），
   届时改成正则适配或换通用解析器。
4. **有人真的需要「只打包用到的字族」** → 先解决第 8 条那个判据问题
   （`font` 简写 + 继承），否则不要动。
5. **KaTeX 的体积成为负担**（例如将来要做「公式很多的文档」的启动性能）→
   评估更小的渲染器或预渲染，但那会牺牲「编辑时即时渲染」。
