# 0006 · macOS：延迟签名发布，不延迟渲染验证

日期：2026-09-28
状态：已采纳
关联：0001（桌面端优先）、0005（draw.io 路线）

## 背景

macOS 是桌面产品的必争之地，但它的**分发成本**远高于 Windows：

| 项 | 事实 |
|---|---|
| 分发门槛 | 苹果开发者账号 **99 美元/年**。免费账号能签名，但**拿不到公证** |
| 硬件要求 | 签名需要 Mac（或 macOS CI runner；GitHub Actions 的 macOS runner 计费倍率是 Linux 的 10 倍） |
| 未签名后果 | macOS 15 Sequoia 起**取消了「右键打开」绕过**，用户被引到系统设置里多次确认；业界统计**约一半的首次尝试在应用打开前就失败** |
| 首次搭建成本 | 业界经验：CI 签名 + 公证流水线首次打通是 **2–3 周**；之后一次发布约 12–18 分钟 |
| 工程陷阱 | Tauri 需要 `allow-jit` / `allow-unsigned-executable-memory` / `allow-dyld-environment-variables` 等 entitlement，否则**公证后启动即崩** |

另有一条把本决策与 0005 绑在一起的硬约束：**WKWebView 的版本跟随操作系统，无法像 Windows 的
WebView2 那样独立更新。** 内嵌 draw.io 要求 Safari 17.5+，因此等于声明最低 **macOS 14.5**。

## 决策

**把「签名与发布」推迟，但不推迟「渲染验证」。**

1. **从 P2 起，每周跑一次 macOS 渲染冒烟**：用一台二手机器或按小时租的云 Mac，
   运行 `tauri dev`，人工过一遍 Markdown 排版、滚动、输入法、拖拽、文件对话框。
   **不签名、不公证、不上架。**
2. **完整签名与公证流水线推迟到 P3 结束、界面临近冻结时再搭建。** 那时返工成本最低。
3. 产品下载页必须**明确声明最低 macOS 版本**，且该数字由 0005 的落地形态决定：
   只内置 viewer 可支持更早系统；内嵌完整编辑器则最低 macOS 14.5。
4. 不采用「只做 Windows、永不支持 macOS」的方案。

## 理由

- **成本的性质不同。** macOS 的成本主要是**分发机制**（账号、证书、CI、entitlement），
  不是应用代码 —— 只要 `DocumentProvider` 保持为唯一平台差异点（P1 已确立），
  移植本身不贵。所以「推迟分发」不会让应用代码腐烂。
- **但渲染差异会腐烂。** WebKit 与 WebView2 在行高计算、字体回退、滚动惯性、输入法组合上都有差异。
  一个 Markdown 所见即所得编辑器，排版就是产品本身。这类差异**越晚发现，返工面积越大**。
- **不可逆性判断**：「只做 Windows」会永久放弃一整块用户群，且越晚补做、早期界面假设越固化；
  而「延迟签名」只是一个排期决定，随时可补。**两件事的风险不对称。**
- 3.2 MB 的安装包 + 无服务端成本，本来就是 macOS 用户群最在意的两个点。

## 前置条件（阻塞项）

**需要确认是否有可用的 Mac。** 若没有，本决策的成本要从「99 美元/年」重估为
「99 美元/年 + 一台 Mac 或云 Mac 的持续租金」，且第 1 条（每周冒烟）需要先落实设备才能启动。
在设备落实之前，第 1 条处于**未启动**状态，这本身就是一个需要跟踪的风险。

## 重审条件

- 若 P2 的界面工作在 macOS 上暴露出**结构性**问题（而非样式微调），应把 macOS 验证提前到与
  Windows 并行，而不是继续往后推。
- 若获得用户反馈表明目标用户里 macOS 占比超过三成，应把签名流水线提前到 P3 之前。
