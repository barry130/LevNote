# 0008 · 范围与排序：按「小投入」情形执行，P2 只做 Markdown + 自包含导出

日期：2026-09-28
状态：已采纳
关联：0001（自包含导出）、0006（macOS）

## 背景

原规划给了三种人员配置下的排期（单人 22 周 / 2 人 15 周 / 3 人 12 周），
并把这个选择标为「决定 P2–P5 是否并行」的关键决策。**该问题的答案尚未确定。**

但排期不能空转。原规划里有一个可直接采用的结构性事实：

> 关键路径是 P1 → P2/P4 → P6 → P7；P5 结束时四个模块可独立使用，是「停下就算成品」的节点。

这意味着**范围可以按可交付性排序，而不必等排期确定**。

## 决策

1. **按「小投入」情形（单人业余 < 10 h/周，或单人全职 / 2 人）执行。**
   这是**保底选择**：小体积、延迟发布、轻依赖 —— 资源变多时不会后悔，资源不足时不会崩盘。
2. **P2 的范围收窄为两件事：Markdown 内核 + 自包含 HTML 导出。**
   原规划把 P2 定为 4 周并包含表格编辑、公式、Mermaid、图片落盘、大纲面板、专注模式、PDF 导出。
   这次收窄**不删除这些内容，只调整顺序**：
   - **留在 P2**：Milkdown 集成与主题、表格编辑、代码块、公式、**自包含 HTML 导出**。
   - **推到 P2 之后**：Mermaid、大纲面板、专注 / 打字机模式、PDF 导出（PDF 依赖打印管线，
     与自包含导出共用渲染结果，放在其后更省事）。
3. **P2 不做导图与 draw.io。** 它们按原规划在 P4 / P5。
4. **自包含导出是本阶段的一等交付物，不是附属功能。**
5. **不采用「先做全部四个内核、再回头补质量」的路线。**

## 理由

- **自包含导出承担了「没有分享链接」之后「把成果发给别人」的角色**（见 0001）。
  它决定产品**能不能用**；导图与图表决定**好不好用**。先解决能不能。
- **P1 已经把文档生命周期跑通**（打开 / 脏标记 / 冲突 / 编码 / 原子写入，44 项前端单测 + 11 项 Rust 单测），
  这是四个内核对齐的共同地基。在它之上先接通一个真实内核，能把 `EditorAdapter` 契约验对，
  避免四个内核各自发明一套接入方式。
- **「小投入」是保底而非悲观。** 它的产物（小体积、延迟发布、轻依赖）在任何投入水平下都不后悔，
  而「按 3 人规模铺开、实际只有 1 人」会直接交出半成品 —— 这是不可逆的一类错误。

## 后果

- 排期无法给出确定日期，只能给出**阶段顺序与可交付节点**。
- P2 结束时产品可以「自己用起来」：写 Markdown、导出单文件 HTML 发人。
  **P5 结束是第一个可灰度发布的节点**（四个模块独立可用），P6 结束后差异化成立、才适合对外发布。
- **范围收窄的可见代价**：P2 结束时没有 Mermaid、没有大纲面板、没有 PDF 导出。
  这三项要在 P2 之后的独立小阶段补，不能无声丢失 —— 已登记在 `open-decisions.md` 的待验证清单里。

## 仍未确定、需要被跟踪的事项

**每周实际可投入小时数，以及是否有人可以并行。** 这个答案会决定：
- 是否需要把 P3–P5 中的某些模块进一步延期或直接砍掉；
- 是否值得搭建 macOS 签名流水线（见 0006 的直接前置条件）。

在得到答案之前，按本 ADR 第 1 条执行。**这不是「不必回答」，而是「答案到来之前先按保底走」。**

## 重审条件

- 若投入水平确认为「3 人以上」，本 ADR 第 1、2 条应重审：可以并行推进，范围也可放宽。
- 若在 P2 中发现「没有大纲面板 / 没有 PDF 导出」会让产品无法交付给真实用户，
  应把它们提回 P2，而不是硬按顺序走。
