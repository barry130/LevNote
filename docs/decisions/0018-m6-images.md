# 0018 · M6 图片：`<文档名>.assets/` + `data:` URI 显示 + 自研灯箱

状态：**已采纳**（M6）

## 背景

M6 的交付是「图片粘贴落盘 + 相对路径解析 + 灯箱」。它同时是
`ROADMAP.md` 第 13 项（「图片粘贴落盘 + 相对路径策略」）与
`docs/gap-analysis-horsemd.md` 里「自包含导出的最后一块拼图」。

在这之前，项目对图片的处理是**只有导出那一半**：`core/export/inline-html.ts`
能把图片读成 `data:` URI 内联进单文件 HTML，但**写不进去** ——
编辑器里粘一张图，什么都不会发生。

这一条要一次定下四件事：

1. 图片存在**哪**、叫**什么名**；
2. 文档里写成什么（绝对路径还是相对路径）；
3. 编辑器里**怎么显示**本地图片（WebView 的 base URL 是应用自身，
   `./a.assets/x.png` 直接塞进 `<img>` 会 404）；
4. 落盘失败 / 图片读不到时**说什么**。

## 决策

1. **落在与文档同级的 `<文档名>.assets/` 目录**，文件名
   `image-<时间戳>-<4 位随机盐><扩展名>`。
2. **文档里一律写相对路径**（`./读书笔记.assets/image-….png`），
   绝不写本机绝对路径。
3. **显示走 `data:` URI**，由已有的 `read_binary_file` 命令读字节、
   `core/image.ts` 的 `bytesToDataUrl` 拼出来。**不启用 Tauri 的
   `asset:` 协议**。
4. **灯箱自研**（`ui/Lightbox.tsx`），内核只通过新的 `onImageClick`
   上报「点了哪张图」。

## 理由

### 1. 目录布局：为什么不是 `assets/` 也不是 `assets/<文档名>/`

| 方案 | 问题 |
|---|---|
| 全局 `assets/` | 一个目录里十份文档共用一个资源目录。删掉其中一份文档时，**没人知道哪些图还属于别人** —— 用户要么整目录留着（越积越多），要么赌一把全删 |
| `assets/<文档名>/` | 归属关系是对的，但**目录名与文档名的对应藏进了第二层**。用户在文件管理器里按名字排序时看不出来 |
| **`<文档名>.assets/`** | 归属明确（整目录可以放心删或搬走），且排序时紧挨着文档本身 |

代价是多一个目录层级的视觉重复（`读书笔记.md` / `读书笔记.assets/`）。
这是可接受的：它换来的正是「归属一眼可见」。

### 2. 文件名：为什么带时间戳 + 随机盐，而不是 `image-1.png`

`image-1.png` 需要**先列目录**才知道 1 有没有被占用。那会把
「生成一个名字」从一个纯函数变成一次**可能失败的异步 IO**，
中间还夹着「列完目录到真正写入之间，别人占了这个名字」的竞态。

时间戳 + 4 位十六进制随机（同秒撞名约 6.5 万分之一）把冲突压到
用户一辈子遇不到，而且**没有 IO**。副产品是文件名可读、按名字排序就是时间顺序。

撞名时的策略是**换一个盐重试（最多 3 次），绝不覆盖**。
两种撞名都是覆盖错的：同秒两次粘贴（会丢掉刚粘的那张）、
目标目录里真有一个同名文件（会毁掉用户的文件）。

### 3. 显示：为什么不用 `asset:` 协议

Tauri 提供 `convertFileSrc()`，它让 WebView 直接按路径流式加载本地文件，
不必把字节读进 JS。代价是要打开 `app.security.assetProtocol`
并配置一份**路径白名单**（scope）。

**没有用它**，理由是安全面：白名单写窄了功能不通，写宽了就等于
允许页面读取任意本地文件 —— 而那是一个需要长期维护的配置面。
`data:` 走的是已有的 `read_binary_file` 命令，权限收口在同一个地方
（我们自己的 capability），**没有新增面**。

代价是明确的两条：

- base64 比原始字节大约 1/3；
- 它会作为属性**常驻在 DOM 上**（不是临时的），所以内存占用与文档里的图片总大小相关。

上游 `read_binary_file` 已经卡了 **24 MB** 的单文件上限（与导出内联共用），
所以最坏情况是有界的。

> **重审条件**：当一份文档里有几十张大图、打开明显变慢（或内存占用可观测地偏高）时，
> 重新评估切到 `asset:` 协议。届时要一并给出白名单的配置方案，
> 而不是只把开关打开。

**顺带一个刻意的选择：显示不做缓存。** 缓存的对象是 `data:` URI，
一张 1 MB 的图会变成约 1.4 MB 的字符串，而且是常驻的 ——
一份有三十张截图的文档就能吃掉几十 MB，且**没有任何上界**。
不缓存的代价有限：NodeView 只在节点创建时解析一次，
重渲染不重读（`update()` 只在 `src` 变了才加载）；真正会重读的只有
「切换视图模式」，而那是用户主动的一次动作。
**重审条件**：实测切视图出现可感知卡顿时，再加一个**按字节总量**设上界的缓存。

### 4. 灯箱：为什么监听挂在 NodeView 上，而不是外壳做事件委托

最省事的做法是外壳在编辑器容器上挂一个 `click`，命中 `img.qm-img-el` 就开灯箱。
**没这么做**：那样外壳就得认识**内核画的类名**，而项目的依赖方向是
`modules/` → `core/editor/types.ts` ← `ui/` —— **外壳不许 import 任何具体内核**。

把类名挪进 `core/` 只是把耦合换个地方藏起来：那份类名本质上是内核的渲染细节。
所以契约加了 `onImageClick(image: ImageInfo)`，监听挂在内核自己造的那个
元素上。`ImageInfo` 带 `url`（已经解析好的那个，不重新读盘）、
`src`（文档里那一串，用于在灯箱上标出这是哪个文件）、`alt` / `title`。

**灯箱的底色恒定是深的，不跟主题走。** 这是全项目唯一一处刻意如此的地方，
理由是具体的：图片的观感取决于它周围的亮度 —— 同一个浅色截图，
放在白底上显得发灰、放在深底上显得通透。用浅色底会让用户对
「这张图到底亮不亮」判断错。所有正经的看图工具都是深底，正是这个原因。

## 代价与已知的坑

### 1. `joinPath` 必须统一分隔符风格（这条是实测暴露的）

Markdown 里的图片地址**必须是正斜杠**（`./a.assets/x.png`），
而 Windows 上的文档路径是反斜杠。直接拼会得到 `C:\笔记\a.assets/x.png`
这种混排字符串。

文件系统不在乎（Win32 两种都认），但**我们的代码在乎**：这条路径会被当作
字符串用在两条路上 ——

- **写入**时文件名是裸名：`joinPath('C:\笔记\a.assets', 'image-x.png')` → 全反斜杠；
- **回读**时来自 Markdown：`joinPath('C:\笔记', './a.assets/image-x.png')` → 混排。

同一个文件两个字符串。任何按字符串比较的地方（缓存键、去重、相等判断）
都会悄悄失配，而**文件系统那边一切正常** —— 表现为「图写进去了但显示不出来」。

所以 `joinPath` 现在会把相对部分的分隔符统一成基路径的风格。
**只换风格**：不折叠重复分隔符、不解析 `..`（那些仍然属于写入层）。
已加一条「写进去的路径与回读时算出来的路径**逐字符相同**」的用例钉住。

> 值得记一笔的是这条**在单元测试里看不到**：内核那一层的 NodeView 拿到的
> resolver 是测试自己给的假函数，返回什么都是我说了算。只有 App 级测试
> 走到「真写盘 → 真回读」才把它照出来。

### 2. `ignoreMutation` 与 `USER_EDIT_META` 一个都不能少

- 图片是叶子节点、没有 `contentDOM`，所以 `ignoreMutation()` 必须返回 `true`。
  少了它，ProseMirror 会把我们写进 `<img>` 的 **data URI 当成用户输入读进文档**，
  存出来的 Markdown 里多出一大段 base64，而界面上一切正常。
- 粘贴必须自己打 `USER_EDIT_META`。落盘是异步的，等它回来时
  「刚发生过用户输入」的窗口早过了 —— 不声明的话按 Ctrl+S 写回磁盘的是
  **粘贴之前**的文本，而界面上那张图还在。这是本项目**第五次**遇到这条路径。

### 3. 只读文档里不会写出孤儿文件（读源码确认，不是猜的）

我们的处理顺序是「**先落盘、再插节点**」（先插节点的话，落盘失败会留下
一个指向不存在文件的图片节点，用户保存后得到一份「打开就有破图」的文档）。
于是很自然会担心：只读文档里粘贴，会不会先写了一个文件、然后编辑被拒？

**不会。** `prosemirror-view` 注册事件监听时用的是
`view.editable || !(event.type in editHandlers)` —— 只读视图里 `paste`
这个监听**根本没装上**。

这条不能想当然（它决定要不要写一个 `readOnly` 判断），所以去读了源码，
并把结论写进了 `setup.ts` 的注释。**刻意不加那个判断**：
加了会让「ProseMirror 到底拦不拦」变成没人知道的事。

### 4. 浏览器预览模式的二进制盘只在内存里

`createBrowserProvider` 原本对 `readBinaryFile` 一律抛 `NOT_SUPPORTED`。
M6 加了一个内存 `binaries` 表（**刷新即失**），因为粘贴图片是**看得见**的功能 ——
预览模式下拒收字节的话，`npm run dev` 里就完全走不到「粘一张图 →
占位消失 → 图出现 → 点开灯箱」这条链路，而那正是最需要眼睛确认的一段。

**这些字节不会被写进任何文件。** 它替代不了桌面版，只是让界面开发
不用为了看一眼效果去编译 Rust。

## 与既有决策的关系

- **0001（只做桌面端 + 自包含导出）**：相对路径是自包含导出的前提 ——
  绝对路径写进文档会让它在别人的机器上、在 Git 仓库里都失去意义。
  0018 把这条从「导出时怎么处理」延伸到了「写入时怎么写」。
- **0003（不静默转码、原子写入）**：`write_binary_file` 复用
  `atomic::write_atomic`，并在目标已存在时**拒绝**而不是覆盖 ——
  与文本写入的 mtime 乐观锁是同一精神的不同实现。
- **0017（M5 自研两半）**：M6 继续自研。灯箱与图片 NodeView 加起来
  不到 700 行（含注释），而引入任何现成的图片组件都要连带引入
  它的 UI 框架与样式体系。
- **0015 / 0016（浮层由外壳画）**：灯箱沿用同一条线 ——
  内核只上报状态与数据，画界面是外壳的事。但**触发方式不同**：
  浮层跟着光标或打字走，灯箱只由用户点图片决定。

## 重审条件

1. **一份文档里几十张大图、打开明显变慢** → 评估 `asset:` 协议
   （必须同时给出路径白名单的配置方案）。
2. **实测切换视图模式出现可感知卡顿** → 给 `data:` URI 加一个
   **按字节总量**设上界的缓存。
3. **用户开始要求「图片也能导出到别的格式」**（PDF / 单独的图片文件）→
   那时 `<文档名>.assets/` 这个布局要重新评估（PDF 导出是 `ROADMAP` 第 16 项）。
4. **剪贴板给出表里没有的图片格式**（比如 `image/avif` 之外的下一代格式）→
   `core/image.ts` 的两张表各加一行即可，但**必须同时**加，
   否则会出现「编辑器里能看、导出后打不开」。
