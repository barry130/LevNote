# 0036 · 块级互操作第二步：L2 就地编辑 = 同面板钻取 + 返回栈

日期：2026-10-05
状态：已采纳（P6 第 28 项的第二阶段）
关联：0035（第一阶段：L3 结构变换 + L1 引用卡片）、0034（面板常驻）、0021（位置记忆）、format-spec §1（L1/L2/L3 定义）

## 背景

ADR 0035 明确推迟了两件事，等这个 ADR 一起定：**L2 就地编辑**（在主文档里
直接编辑被引用的文档、保存回原文件）与**内嵌预览**（卡片里渲染被引用文档的
只读内容）。推迟的原因是二选一的架构决策没有做：

- **嵌套内核**：在宿主文档的 doc-block 节点视图里再挂一个可编辑内核，
  直接编辑被引用文件的内容；
- **面板叠加另一份 store**：编辑发生在被引用文档自己的真实文档路径上。

format-spec §1 对 L2 的定义只有两条语义：**直接编辑被引用文档**、
**保存回原文件**（路径，无副本）。它没有规定「编辑面必须长在宿主文档的
文档流里」—— 这给了取舍空间。

## 决策

### 1. 就地编辑 = 同面板钻取 + 返回栈

卡片新增「就地编辑」动作：被引用文档按**正常文档路径**打开 —— 它有自己
的 store、自己的脏标记、自己的 Ctrl+S、文件监听冲突判定与位置记忆 ——
面板切过去；来源记录在目标标签页的 `drilledFrom` 上，标签栏出现
「↩ 返回」chip，一键回来源。回到来源时 P3-19 的面板常驻保证光标、滚动、
撤销栈、分屏状态原样。

规范的两条语义由此都成立：

- **直接编辑被引用文档** —— 编辑发生在它唯一的活动编辑面上；
- **保存回原文件** —— Ctrl+S 写回 `src` 指向的文件，宿主文档的引用块
  一个字不动（不存在「副本」，与规范「路径，无副本」一致）。

### 2. 嵌套内核否决

不是「暂不支持」，是「否决」。六条理由，每条都对应这个代码库里一条
已付过学费的约束：

1. **单一编辑面被打破**。store 按路径去重的背后是一条不变量：同一份磁盘
   文件同一时刻只有一个内核在编辑。引用已在别的标签页打开时，嵌套内核
   造出第二个编辑面；否则就要发明「没有标签页的文档」这种新实体，
   会话恢复、保存全部（save all）、脏标记汇总都要跟着改。
2. **脏标记与保存路由无处安放**。脏标记挂在真实标签页上（标签栏圆点、
   状态栏）；嵌套面的未保存改动不属于宿主文档、又没有自己的标签页。
   Ctrl+S 保存谁要按焦点猜 —— 而「按焦点猜」在浮层键盘、快捷键两处
   都踩过坑（坑 9、ADR 0032 的冲突顶掉）。
3. **P3-19 的整套机制以「面板」为单位**。句柄分桶、失败标记（`failedKey`）、
   会话恢复、停用收浮层，全都假设一个内核属于一个面板槽位。块内内核
   不属于任何面板 —— 等于在机制最密的地方再开一个例外。
4. **文件监听要再接一遍**。`watch` 的事件是通知、mtime 才是判决
   （ADR 0029），判决对象是打开的 store。块内编辑的文件若是
   「无标签页文档」，冲突判定、外部改动提示全部要为它重做。
5. **ProseMirror 节点视图里嵌第二个可编辑内核是新坑面**。宿主 doc-block
   是带内容的节点（光标进块要编辑属性区），嵌套内核要处理
   `stopEvent` / `ignoreMutation` / 选区边界 / 两个撤销栈的交错 ——
   每一条都是「换个写法就会坏」级别的约束。
6. **收益只剩「并排同时编辑两份文档」**。钻取 + 返回已经覆盖
   「看到引用 → 进去改 → 回来继续写」的完整往返；并排编辑本应用至今
   没有任何先例（分屏是同一文档的源码/预览两视图，不是跨文档）。

### 3. 内嵌预览 = 卡片展开的结构摘要（不渲染成 HTML）

卡片新增「预览」开关。**数据由外壳提供（文件是外壳的领域），内核只画** ——
与 `resolveImageUrl` 同一条分工。新契约
`EditorMountProps.resolveDocBlockPreview(ref): Promise<DocBlockPreview | null>`。

按 kind 给**结构摘要**，刻意不做全文渲染：

- **markdown**：标题树（最多 8 条，`core/outline` 的 `extractOutline`，
  已剥行内标记）+ 字数（`core/statistics` 的 `analyze`）；
- **text**：行数 + 首 40 行纯文本片段（`<pre>`，不高亮 —— 片段的作用是
  「认出这是不是我要的文件」，零风险地做到即可）;
- **mindmap**：根主题 + 节点数（`core/mindmap` 的 `parseMindmap`，纯函数）；
- **读不到 / 解析失败**：摘要位置如实写原因 —— 摘要本身就是外壳读文件的
  产物，失败必须可见（硬约束 2）。

**markdown 刻意不渲染成 HTML**：与导出同源的管线（`buildSelfContainedHtml`）
为单文件自包含而生，把 KaTeX/Mermaid 全量内联，一张展开的卡片不该付这个
重量；自己写半份 md→HTML 渲染器则是保真陷阱 —— 显示得和编辑器不一样，
比不显示更糟。结构摘要是如实的话。

摘要不缓存：展开即读，笔记场景的文件都很小；缓存换来的只是过期风险。

### 4. 卡片结构随动作数调整

第一版的卡片是单个 `<button>`（整张可点 = 打开）。动作到三个之后
button 里不能再嵌 button，改为 `div`：标题区（点 = 打开，行为不变）+
右下动作行（「预览」开关、「就地编辑」）。内核画的元素挂内核的监听，
外壳经契约收事件（硬约束 11），与第一版一致。

## 后果

- `core/workspace/store.ts`：`Tab` / `TabSummary` 增加 `drilledFrom`；
  新增 `openInPlace(fromId, path)` 与 `goBackDrill(id)`。**普通 `open()`
  命中已有标签页时清掉旧的 `drilledFrom`**（用户显式打开 = 旧的来路作废）；
  `closeTab` 顺手清掉「指着自己」的来路（悬空来路不值得保留）。
  **返回栈不进会话恢复**：它是导航上下文，标签 id 每次启动重新编号，
  跨会话保留只会指向错的标签页。
- 契约新增 `onDocBlockEditInPlace` / `resolveDocBlockPreview` /
  `DocBlockPreview`（判别联合，kernel 按 kind 画）。
- 摘要的计算在 `core/document/block-preview.ts`，依赖注入（读文件），
  与 `block-ops.ts` 同一条编排纪律。
- 未支持的 kind 到不了卡片（0035 的 CARD_KINDS 门），预览不用考虑它们。

## 重审条件

- **跨文档分屏**（两份文档同时可见可编辑）立项时，嵌套/并排的架构前提
  才第一次成立 —— 那时重审决策 2。
- 若卡片动作继续增加（超过三个），收进右键菜单而不是继续摆一行。
- 若实测用户大量「预览 → 还是得打开」，考虑给 markdown 摘要补「首段
  原文」字段；全文渲染仍维持否决，除非导出管线出轻量只读变体。
