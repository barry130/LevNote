# 0026 · 工作区全文检索（Rust 流式 + 可取消 + 尊重 `.gitignore`）

日期：2026-10-04
状态：已采纳（P4 第 23 项落地）
关联：0003（编码不静默转码）、0012（命令注册表）、0021（位置由内核往返）、0022（VSCode 式外壳）、
`core/search/find.ts`（文档内查找，语义对齐的另一半）

## 背景

四类一等公民里，Markdown 与思维导图已经可以独立使用（第 20–22 项）。第 23 项
是 P4 的最后一项：**在整个文件夹里找一句话，点一下跳过去**。

它与「在当前文档里查找」（`find.ts`）是两件完全不同的事，不能共用一套形状：

| | 文档内查找 | 工作区检索 |
|---|---|---|
| 范围 | 一份文档，内存里 | 一整个目录，磁盘上 |
| 耗时 | 微秒级 | 秒级 |
| 形态 | 同步返回全部匹配 | 流式，分批回来 |
| 谁在算 | 内核自己 | Rust 侧的阻塞线程 |

## 决策

### 1. 检索是一个「会话」，不是一个「调用」

防抖、取消、过期批次，这三件事全是「写错了不报错」的类型（尤其是第三条：
被取消的那次检索还有几批在路上，混进新结果里看起来完全正常）。放在组件里
只能靠渲染测试去够它们，而它们全是**时序**问题。

所以前端是一个纯 JS 的 store（`core/search/workspace.ts`），组件没有自己的状态：
用户停手 250ms 才发起（回车不受限）；新检索发起时旧的真的停下来（Rust 侧置位）；
`searchId` 对不上号的批次一律丢弃。

**进度与结果是两种更新方式**：`files` 是追加的，`progress` 是替换的
（Rust 报的是累计值）。混用任何一种都会错——结果翻倍，或第一批之后全没了。

### 2. Rust 侧：`ignore` + `regex`，语义微妙的就用参考实现

`.gitignore` 的语义一点都不小：否定规则 `!`、前导 `/` 的锚定、目录专属的尾随
`/`、`**` 跨目录、深层覆盖浅层的优先级。自己写一份的代价不是「写不出来」，
而是**写错了不报错**：多排掉一个文件 = 用户的搜索结果里**静静地少一个文件**，
与硬约束 2 直接冲突。所以用 ripgrep 的 `ignore` 库（顺带白拿 `.ignore`、
`.git/info/exclude`、全局 gitignore、以及「跳过隐藏项」——`.git` 因此天然不在
结果里）。**不是 git 仓库也认 `.gitignore`**：产品说的是「尊重 .gitignore」，
不是「在 git 仓库里尊重 .gitignore」。

`regex` 本来就在依赖图里（tauri-utils 那条链），提为直接依赖不加编译单元。

**`includeIgnored` 开关是这条规则的逃生口**——少了它，「结果里没有我的文件」
就是一件无法自救的事。但它关掉的只是「规则」，隐藏项（`.` 开头）仍然跳过，
否则 `.git/` 会被整棵搜一遍。

### 3. 流式：通道只管批次，结局是返回值

批次走 Tauri 的 `Channel`（随请求传下去，检索结束自动清理；自带消息序号，
批次不会乱序）；**这一次检索怎么结束的**（正常 / 被取消 / 到上限）是 `invoke`
的返回值。

一开始的设计是把结局也做成通道事件，于是前端有两条互相竞速的终局路径，
得靠「谁先到」去猜。现在只有一条：`await invoke(...)` 拿到的就是结局。
代价是**通道上可能还有一批在路上**（Rust 发完最后一批就返回了），所以前端在
收到结局之后**不许让进度回退**——收尾之后到的最后一批，`files` 要收（它是结果
的一部分），计数不要收（那是收尾之前的快照）。

批次按「攒够 12 个有命中的文件」或「过了 150ms」推——后者保证一个命中都没有时
进度也在动，用户不会以为卡死了。

### 4. 列号是 UTF-16 码元；转换只在 Rust 侧做一次

命中要能跳过去，跳转的落点是「第几行第几列」。Rust 侧天然是字节偏移，JS 侧
天然是 UTF-16 码元（`String` 下标、CodeMirror 的 `ch`、`textarea.selectionStart`
全是它）。选 UTF-16 是因为转换只需要在 Rust 侧做一次、且做得准（`char::len_utf16`）；
用「字符数」这种看着更中性的单位最糟——中文与 emoji 的 `char` 计数与 JS 下标
都对不上，而**差一位**的表现是「跳到命中右边一格」，没人会怀疑是单位问题。

### 5. 逐行匹配；用户的正则不能跨行（刻意）

结果要能跳到「第几行」，这个坐标只有在按行扫时才是天然的；`^` / `$` 也因此
自然等于行首行尾，不需要 `(?m)`；内存里一次只多一行。代价写清楚：**跨行匹配
不支持**——跨行的命中没法用一个「第几行」表示，这是设计，不是缺失。

与文档内查找的语义对齐（同一份 UI 语言里的「区分大小写 / 全词 / 正则」必须
是同一个意思），唯一刻意的差异是**非法正则在这里报错**：那边是边打字边查
（`(` 的中间态就是非法的，报错会让查找栏一直闪红），这边停下来才查，
还报错说明用户真的写错了。

### 6. 跳转契约：`revealSourceLocation` 是可选能力，回落链收敛在外壳

`EditorHandle.revealSourceLocation({ line, column, length })`，代码内核与纯文本
内核**精确**实现（`doc` 就是文件本身），富文本内核不实现——ProseMirror 的文档树
里没有「第几行」，硬猜一个位置比不跳更糟。

外壳的回落链：① 内核实现了 → 直接用；② 没有但有源码视图 → 切到源码视图，
**只切一次**（防来回弹）；③ 都没有 → 放弃，待办必须收掉（留着的下一次点击会
先消费掉它——「点 A 没反应，点 B 跳到了 A」）。

### 7. 落地时机 = 内核就绪那一刻，与位置记忆同一个时刻（踩过的坑）

最初版由外壳握着句柄在 effect 里「戳一次」。测试在 StrictMode 下当场抓住：
**React 19 的 StrictMode 会把「模拟卸载→重挂」推迟到挂载之后的某个异步点执行**，
而假 provider 的微任务让内核先就绪、定位先落了地——随后那次重挂把面板的
本地状态（光标读数）连同新内核的选区一起销毁，而外壳早已把待办清掉，
**再也没有人补那一次定位**。生产构建不受影响，但本项目的测试全程开 StrictMode，
开发模式下这条竞态也真实存在。

修法是把 reveal 变成与 `initialPosition`（位置记忆）**完全同构**的东西：
外壳立起请求（state），作为 prop 传给面板，**面板在 `handleEditorReady` 里应用**，
任何一次内核重建都会重新落地——竞态从设计上消失，而不是被时序技巧堵住。

配套的三条：

- **「已落地」台账是面板实例自己的 ref**：它挡「同一次内核重建里重复落地」，
  但**挡不住**重挂——重挂连 ref 一起销毁，新实例拿着同一个请求重新落地，
  这正是要的。
- **请求在 `open()` 成功之后才立起来**：那一刻 `activePath` 已经是目标文件，
  「用户切走标签页就收掉请求」的对账 effect 不需要区分「正在赶往目标」的窗口期。
- **重挂之后补落地的是「面板重新走一遍 ready 流程」**，所以状态栏的光标读数
  也一起回来了——它本来就是内核上报的，不是面板记住的。

### 8. 跳过必须说出口；结果顺序必须确定

二进制（前 8KB 含 NUL）、超大（默认 4 MiB）、读不到（权限 / 断链 / 解码失败），
三类跳过全部计数上报，出现在收尾统计里。用户看不到某个文件时，至少要能分辨
「它被跳过了」和「它里面真的没有这个词」——硬约束 2 在检索上的落点。
两个细节：UTF-16 文件每两个字节就有一个 NUL，**先看 BOM 再判二进制**，
否则「打开能看、检索搜不到」；解码走与打开文件**同一个** `codec::decode`
（UTF-8 合法的快路径直通，否则跑统计式探测会拖慢整次扫描）。

结果顺序确定（单线程遍历 + 按路径排序）：并行走完再排序要多存一份全部结果，
而文档编辑器的目录不需要那点吞吐；稳定顺序 = 面板里的结果不会自己跳。

### 9. 侧栏两栏与「侧栏可见」是两个独立的偏好

`sidebarView: 'files' | 'search'` 与 `sidebarVisible` 分开，不合成一个三态枚举：
「关掉侧栏再打开」应该回到**用户上次看的那一栏**（正在搜到一半、先关掉看一眼
代码），合成枚举会把它丢掉。活动栏的两个入口语义也不同：
`Ctrl+B` 是「收起 / 放出侧栏」（保留正在看的那一栏），活动栏按钮是「我要看那一栏」
（正显示另一栏时**换过去**）。

### 10. 平台能力问执行者自己，不问平台

「能不能检索」是 `WorkspaceSearcher.available`，由执行者自己回答。浏览器预览有
内存虚拟盘（文档链路能用）但没有目录树，给的是**明确拒绝**的执行者，面板显示
一句说明——而不是一个点了没反应的面板。让外壳另问一次 `isDesktop()` 就是同一个
问题两份答案，将来加平台必得「按钮亮着、点下去被拒绝」。

## 代价

- 主包 1,872.79 → **1,886.68 kB**（+13.89 kB，gzip 624.53）。面板、store、图标、
  样式全是首屏就要用的，没有懒加载余地。
- 用户的正则**不能跨行**（见决策 5）。
- 单文件默认 4 MiB、总命中默认 2000 条的上限——超限**如实说**（「已达上限，
  结果可能不全」），不安静截断。

## 重审条件

1. **性能**：如果大目录（万级文件）扫描明显卡顿或内存吃紧，再考虑
   `WalkBuilder` 的并行模式 + 结果排序、以及流式解码（当前是整文件读入）。
   先量再改。
2. **`Channel` 的负载上限**：单条命中预览截到 240 码元、单文件命中数随总量
   2000 封顶，都是为了不让 IPC 负载失控。如果将来放开「搜全部命中」的需求，
   先量 IPC 的序列化成本。
3. **`ignore` / `regex`**：如果检索面板被砍掉（产品方向变化），这两个直接依赖
   一起删，`cargo check --all-targets` 验证。
4. **文档内查找与这里语义分叉时**（例如全词匹配的 `\b` 口径改了任何一边），
   两边的测试必须一起改——它们钉的是「两个入口同一个语义」。
