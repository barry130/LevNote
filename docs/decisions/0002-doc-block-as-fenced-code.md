# 0002 · 用围栏代码块 `doc-block` 承载互操作

日期：2026-09-28
状态：已采纳

## 背景

四类文档要能互相引用与嵌入。需要一个写进 Markdown 的载体语法。候选：

| 方案 | 说明 |
|---|---|
| A. YAML front-matter | 放在文件头部，`---` 包裹 |
| B. 自定义行内标记 | 如 `{{diagram: arch.drawio}}` |
| C. 围栏代码块 ` ```doc-block ` | 信息串为 `doc-block` 的普通代码块 |
| D. HTML 注释 / 自定义标签 | `<!-- doc-block ... -->` |

## 决策

选 **C**。

## 理由

关键约束是**降级行为**：轻墨没有分享链接（见 0001），文件外发是主要协作方式。
收件人很可能不用轻墨，甚至不用 Markdown 编辑器。那么这份文件在他眼里是什么？

- **A 失败**：多数渲染器会直接把 front-matter 渲染成正文，
  用户看到一堆 `id: arch` 和 `---` 横线。而且 front-matter 是**文件级**的，
  一个文档里要放多个块时它根本表达不了。
- **B 失败**：`{{diagram: arch.drawio}}` 在别的渲染器里就是一行字面文本，
  收件人完全不知道这里原本有张图。
- **D 失败**：HTML 注释渲染后彻底不可见，
  内容在收件人眼里**直接消失** —— 这是最坏的一种失败。
- **C 成立**：不认得 `doc-block` 的渲染器把它当普通代码块，
  元数据以等宽字体显示出来，读者能看懂「这里原本有个 draw.io 图，在 diagrams/arch.drawio」。
  **内容可见、语义可推断**，而不是消失或错乱。

附加好处：
- 可以出现任意多次（不像 front-matter 只有一个头部）。
- 嵌套问题有现成答案：CommonMark 的围栏加长规则，用户不用学新东西。
- 可以出现在文档中间、列表项里、引用块里，位置自由。

## 代价与缓解

- **代价**：不如专用语法紧凑；在不认得的渲染器里会多出一段代码块。
  - 缓解：属性区只放必要字段；`mode`/`id` 之外都可省。
- **代价**：手写时容易漏掉 `---` 结束行。
  - 缓解：解析器给出 `MISSING_TERMINATOR` 明确定位，编辑器侧提供插入片段的快捷键。

## 重审条件

- 若 Markdown 生态出现被广泛支持的「文档嵌入」标准语法，应评估迁移而非固执己见。
- 若实测发现用户在文档里有大量短内联块（比如几十个小公式），
  围栏的语法噪音会变得难以忍受，届时应为高频小片段单独设计更轻的行内语法。
