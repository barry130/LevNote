# 0007 · 思维导图内核选 mind-elixir，锁定 5.15.1

日期：2026-09-28
状态：已采纳（**2026-10-02 P4 开工前复评，维持** —— 见文末「复评记录」）
关联：0004（编辑器内核选型）、format-spec.md §7.1

## 背景

`docs/format-spec.md` §7.1 定了一个**刻意最小**的 `.mindmap` v0 骨架
（`id` / `topic` / `note` / `collapsed` / `style` / `children`），并明确把「用哪个内核」留作待定。
现在到了必须在 P4 之前定下来的时点。

实测数据（2026-09-28，取自 npm registry 与 GitHub API）：

| | **mind-elixir** | **simple-mind-map** |
|---|---|---|
| 许可 | MIT | MIT |
| npm 稳定版 | **5.15.1（2026-08-05）** | **0.14.0（2025-04-08）** |
| 该版本之后 | 6.0.0 活跃迭代（next.1 → next.9，2026-08~09） | **只有 `0.14.0-fix.1/.2/.3` 三次修复重发**（最近 2026-07-07） |
| 包体积（解压） | **327 KB** | **26 MB** |
| 依赖数 | **0** | **14** |
| 依赖内容 | — | quill、pdf-lib、katex、jszip、svg.js、tern、xml-js、**yjs + y-webrtc + ws** |
| GitHub ★ | 3,170 | 12,771 |
| Open issues | **13** | **127** |
| 实现语言 | TypeScript | JavaScript |
| 数据结构 | `{nodeData: {id, topic, children}}` | `{data: {text, …}, children}` |
| 特色能力 | 小而干净、框架无关、零依赖 | XMind 导入导出、多布局、PDF/PNG 导出、富文本节点 |

## 决策

选 **mind-elixir**，并**显式锁定 `5.15.1`**。

## 理由

1. **维护状态是决定性的。** simple-mind-map 上一个真正的功能版本是 **2025-04**，
   之后 17 个月只有修复重发，同时挂着 127 个未处理 issue。★ 数高（12,771）说明它历史上做得好，
   但我们要在一个计划维护多年的产品里长期依赖它 —— **「还在往前走」比「功能多」重要**。
2. **体积与依赖与产品定位直接冲突。** 26 MB + 14 个依赖，其中 `yjs` / `y-webrtc` / `ws`
   是一整套**实时协作栈**。轻墨是桌面单机（ADR 0001），协作能力一个都用不上，等于纯背上成本。
   而「轻」是本产品的名字与卖点。
3. **数据结构与我们的规范同源。** 规范 §7.1 用的是 `topic` + `children`，正是 mind-elixir 的字段名；
   simple-mind-map 用 `text` 且把节点属性埋在 `data` 层，需要写一层映射。
   映射层越厚，**将来换内核时用户文件的损失越大**。这一条与 §7.1「刻意只固定最小骨架」的设计意图一致。
4. **TypeScript 原生**，与本项目的严格模式（`noUncheckedIndexedAccess` / `verbatimModuleSyntax`）配合更好。

## 后果与必须注意的坑

1. **绝不能写 `npm i mind-elixir`。** 它的 npm `latest` 标签被**错误地指向了 `6.0.0-next.4`**
   （`beta` = next.5、`next` = next.9）。必须锁死 `mind-elixir@5.15.1` 并在 `package.json` 里
   使用精确版本（不加 `^`）。
2. **6.0.0 迭代很活跃（一个月内 next.1 → next.9），说明 5 → 6 会有 API 迁移。**
   因此 `.mindmap` 的读写必须包一层**薄适配层**（`src/modules/mindmap/adapter.ts`），
   把内核版本变化隔离在这一层内，**规范里的文件格式不受内核升级影响**。
3. 一旦引入，就要接受它作为供应链依赖：加入 P7 的许可证清单，并关注其发布节奏。

## 放弃的方案

- **simple-mind-map**：见上。除非命中下面的出口条件。
- **自研导图**：规范骨架很浅，自研一个可用的导图（逻辑结构图 + 节点增删拖拽 + 折叠 + 导出 PNG）
  约 1–1.5 人月。**当前不划算** —— 327 KB 的零依赖库已经解决问题。
  但若 mind-elixir 出现停更，**自研会比迁移到 26 MB 的 simple-mind-map 更可控**。

## 重审条件（出口条件，命中任一条即换）

1. 500 节点规模下渲染或拖拽明显卡顿（判据：输入到反馈 > 50ms —— 与 0004 给 Markdown 内核定的同一条线）；
2. **XMind 往返导入导出被验证为刚需** —— 这是 simple-mind-map 的独有能力；
3. mind-elixir 停止维护，或 6.x 出现不兼容的协议/许可变更。

命中 1 或 3 时的第一选择是**自研**，而非迁移到 simple-mind-map；
命中 2 时迁移到 simple-mind-map 并接受 26 MB。

> **条件 1 已在 2026-10-02 复评后重新表述**（原文的「500 节点」是个不足的限定 ——
> 实测证明答案取决于**顶层分支数**，不取决于节点总数）。
> 判定与后果见文末「复评记录」；重审时**以那一节为准**。

## 复评记录（2026-10-02，P4 开工前）

**结论：维持原决策 —— 继续用 mind-elixir 5.15.1，不换内核，不自研。**
但重审条件 1 需要**重新表述**，并且 P4 要带着一条已知边界开工。完整读数在
`docs/open-decisions.md` 的「V2 实测记录（2026-10-02）」；这里只留判定与后果。

### 重审条件 1（500 节点卡顿）的判定：**看形状**

实测（500 节点，mind-elixir 5.15.1，真实 Edge + CDP，120Hz）：

| 顶层分支数 | `refresh` p50（用户提交一次编辑 / 加一个节点到画面更新） |
|---:|---:|
| 3–150 | **29–42ms** —— 全部在 50ms 判据内 |
| 175 | 50.3ms —— 穿过判据 |
| 250–400 | 76–128ms |
| 499（`wide`） | 约 170–240ms |

**成本由「顶层分支数」决定，不由总节点数** —— 因为 `linkDiv` 的主循环是
「每轮写一次 `style.borderColor`、再读一次 `offsetWidth/offsetLeft`」（强制同步布局），
循环次数就是顶层分支数，而这张图有 3–5 万 px 高。所以「500 节点卡不卡」**没有唯一答案**。

**判定：**
- **常见形状（≤150 条顶层分支）未命中** —— 而且 150 条顶层分支本身已经远超
  一张真人画的思维导图（那不是导图，是一张列表）；
- **极端形状命中** —— 字面上确实越过了 50ms。

### 为什么维持决策

1. **命中的是「不是导图的形状」。** 拐点在 175 条顶层分支；真人导图的顶层分支
   通常在 3–12 条。用一个不现实的形状触发出口条件，等于把决策交给最不具代表性的用例。
2. **50ms 这条线本来不是给这类操作用的。** 它来自 ADR 0004，量的是**打字**（连续输入、
   延迟最敏感）。V2 把它套在**结构操作**（提交一次编辑、加一个节点）上，语义已经变了 ——
   这类操作的公认阈值是 **100ms（「瞬时」）** 与 **1000ms（「打断思路」）**。
   按 100ms 看，拐点在 **约 250–300 条分支**；按 1000ms 看，连 `wide` 都在线内。
   **这不是为了绕开出口条件而改线** —— 两条线都记在案，判定靠的是第 1 条。
3. **换内核解决不了这个问题。** simple-mind-map 是 26 MB + 14 个依赖（含整套实时协作栈），
   而**没有任何证据表明它在 499 条顶层分支下更快** —— V2 没有测它。
   为了一个未被验证的、且不在现实形状里的收益，去背上 26 MB，是拿确定成本换不确定收益。
4. **自研也不解决这个问题。** 自研要重新实现的就是同一个 `linkDiv` 等价物，
   而 1–1.5 人月的成本换不来「比 mind-elixir 快」的保证。

### P4 必须带上的三条边界（不能假装它不存在）

1. **`>150` 条顶层分支时要有可见的降级提示**，而不是让用户面对一个卡住的界面。
   与硬约束 2「绝不静默」一致 —— 降级要在 UI 上说清楚。
2. **评估「分批渲染 / 增量更新连线」的可行性**：`linkDiv` 整篇重画是内核的实现选择，
   外壳无法绕过（也不该绕过 —— 硬约束 1）。若 P4 中确认无法从外部缓解，
   就把第 1 条的提示做成正式交互，而不是待办。
3. **大树不作为 P4 的验收目标。** P4 的验收是「导图这一类文档能作为一等公民读写与编辑」，
   不是「扛住 500 节点任意形状」。**若将来真实用户撞上这条线，再回来重审本 ADR** ——
   那时的输入是真实用例，比合成压测更有分量。

### 判据本身的修正（比上面任何一条都重要）

**V2 原定的判据「输入到反馈 ≤ 50ms」照字面去量打字，会得到一个正确的假绿。**

mind-elixir 的编辑框是 `div#input-box`（`contentEditable="plaintext-only"`），
**只挂了 `keydown` 与 `blur`，没有任何 `input` / `beforeinput` 监听**；
`blur` 时才提交并调 `linkDiv()`。所以**在编辑框里敲字时内核一行代码都不跑** ——
节点数再多也不会让这条路径变慢。

**这与 ADR 0004 的 V3 第一轮是同一类错误**（用 `paint` 当判据：读数没有误差，
但指标选错了）。**主判据应为 `refresh`（提交一次编辑 / 加一个节点后到画面更新）**，
`linkDiv` 是它的归因分解。ADR 0004 那边也应记下这一条 —— 两处判据的修正理由是同一条。

### 数据格式那半边：对齐损耗可隔离

`scripts/v2-align.mjs` 往返官方 88 节点样本：**一次写盘丢 40 处字段 + 顶层 4 项**，
但**二次往返幂等**（第二次不再变化）；`expanded` ↔ `collapsed` 是**改名**；
`layout` 只固定 `logicalStructure`。

**结论：本 ADR「后果 2」要求的薄适配层是够用的**，损耗全部落在
`src/modules/mindmap/adapter.ts` 这一层里，不需要在适配层里做状态机，
也不影响 §7.1 的骨架设计。**§7.1 的 v0 骨架保持不变。**

### 复评时点

- **P4 开工前**的压测与数据对齐验证 **✅ 已完成（2026-10-02）**，本 ADR 结论已复核并维持；
- **下一次复评的触发条件**：真实用户撞上 `>150` 条顶层分支；或 mind-elixir 停更 /
  6.x 不兼容（原重审条件 3）；或 XMind 往返被验证为刚需（原重审条件 2）。
