# 0029 · 文件监听：事件是通知，mtime 才是判决

日期：2026-10-04
状态：已采纳（P3 第 14 项落地，`watch/mod.rs` 空壳转正）
关联：0003（mtime 乐观锁与原子写）、`core/document/store.ts` 的
`checkExternalChange`、`core/workspace/store.ts` 的 `handleFsChanges`、
`ROADMAP.md` 第 14 项

## 背景

在 0029 之前，`src-tauri/src/watch/mod.rs` 是返回 `NOT_SUPPORTED` 的空壳，
「外部程序改了文件」只有一条发现路径：**窗口重新聚焦时全量比对 mtime**
（`checkExternalChanges`）。它有两个可感知的缺陷：

1. 开着的文档被外部改写，用户要**切走再切回来**才会看到冲突提示；
2. 文件树完全静止 —— 外部新建 / 删除 / 改名的文件，不手动刷新就永远不出现 / 不消失。

真正的文件监听（`watch`）因此提上日程。要回答的问题不是「能不能监听」
（notify 库显然能），而是：**事件推上来之后，前端拿它当什么？**

## 决策

### 1. 事件是**通知**，mtime 比对是**裁决**

监听事件只回答「哪些路径**可能**变了、尽快告诉前端」。它**不**回答
「文档是否真的被外部改了」—— 那个判断仍然由 `checkExternalChange()`
按 mtime 比对做出（与保存时的乐观锁同一套逻辑）。

理由：文件事件系统**天生不可靠**。事件会丢（监听建立前的变更）、会重
（一次保存触发多个原始事件）、会误（某些编辑器是「写临时文件再改名」，
路径对不上）。如果前端把事件当判决 ——「收到事件就弹冲突」—— 这三类
噪声都会变成错误的打扰。反过来，把事件当通知：丢了最多慢一拍（焦点
兜底还在），重了、误了会被 mtime 比对安静过滤掉。

### 2. 整表替换 API（`watch_replace(paths) -> failed`），不做 start/stop

前端每次「打开文件夹 / 开关标签页」之后，把**想要的**监视集合整体推给
Rust（工作区根目录 + 不在根目录下的打开文件），Rust 对当前集合做差量
watch / unwatch，返回**没监视上**的路径。

不做增量 `watch_add` / `watch_remove` 的理由：那要求前端自己记「Rust 侧
现在监视着什么」，两份状态必然漂移（前端崩溃重启、标签页恢复到一半）。
整表替换是幂等的 —— 重复发送无害，崩溃后发一次全量即收敛。差量只存在于
**Rust 侧内部**（`plan_diff` 纯函数，已被 5 条单测钉住）：已经在集合里的
路径不动，因为 notify 对重复 watch 会报错。

### 3. 目录递归、散文件非递归

工作区根目录按 `RecursiveMode::Recursive` 监视 —— 目录树要的是「根下任何
一层的新增 / 删除」，递归交给 notify，前端不用维护「展开了哪些层」的清单。
根目录之外的打开文件（拖出来的散文件）按 `NonRecursive` 补上。

### 4. Rust 侧防抖 250ms + 批内去重，错误也走批次

`notify-debouncer-mini` 在 Rust 侧收口（保存一次文件的截断 / 写入 / 元数据
多个事件合并成一批），批内用 `HashSet` 去重，经 `emit("fs://changed")`
推送 `{ paths, error }`。**监听后端自身的错误**（比如被监视的目录被整个
删掉）不是静默吞掉 —— 填进批次的 `error` 字段，前端 `console.warn` 说出
来。250ms 的取值：编辑器一次保存的多个事件必然落进同一批，同时「保存后
看目录树」的等待不超过四分之一秒。

### 5. 前端只做「点名」，不做重算

`WorkspaceStore.handleFsChanges(paths)` 拿到批次后：

- 打开的文档里**只有路径命中的**才调 `checkExternalChange()`（mtime 裁决）；
- 目录树只重拉「**已经加载过的**」受影响目录 —— 没展开的层级不在界面上，
  重拉纯属浪费；变更路径本身是已加载目录时（被删 / 改名）重拉它自己那层。

窗口焦点时的全量比对**保留作兜底** —— 事件系统永远可能丢，焦点比对是那个
「迟到最后但一定会到」的检查。两条路径最终都汇入同一个 mtime 裁决，语义一致。

### 6. 依赖：notify 8 + notify-debouncer-mini 0.7，主版本锁死

`Cargo.toml` 里两者的主版本必须一致（notify 8 ↔ debouncer-mini 0.7），
否则会**编译进两份 notify**，事件在两套类型之间对不上。这个约束写在
`Cargo.toml` 的注释里。

## 后果

- 外部改写开着的文档 → 250ms 内弹出冲突提示（原来要切窗口）；外部新建 /
  删除的文件 → 目录树自动跟上（原来完全静止）。
- 常驻一个 notify 线程；Windows 上根目录递归监视走
  `ReadDirectoryChangesW`，单根目录的成本可接受。
- `watch_replace` 在「集合没变」时是零操作（差量为空）—— 前端因此可以
  在每次 tabs / tree 变化后无脑推送（App.tsx 用 `JSON.stringify` 后的
  路径串做 useMemo 依赖，集合没变连推送都不发）。

## 重审条件

- **事件质量**：如果某个平台 / 文件系统（网络盘、部分 NAS 挂载）上 notify
  丢事件丢到「焦点兜底也明显感知得到」的程度，考虑直连
  `ReadDirectoryChangesW` 或对该类路径退回轮询 —— 判据是实测丢事件率，
  不是猜。
- **API 形状**：如果「整表替换」的可感知成本出现（标签页数极多时每次
  推送都要全量 diff），可以改增量 API —— 但必须同时带上「前端重启后
  重同步」的机制，否则只是把状态漂移从 Rust 挪到前端。
- **防抖窗口**：如果出现「保存后目录树刷新慢到可感知」的反馈，先量再改
  （250ms 不是拍脑袋，但也不是不可动）。
