# 0046 · 本次运行的问题：说过一次还不够，得留得住

- 日期：2026-10-12
- 状态：已接受
- 关联：硬约束 2（绝不静默）、ADR 0001（纯本地、无账号、无网络、无遥测 —— 本 ADR
  是它在「怎么把问题告诉别人」这一格上的推论）、ADR 0042 / 0043 / 0044 / 0045
  （这一族的四个「说出来」，本 ADR 讲的是它们**留下**什么）

## 背景

0042–0045 做完之后，应用里每一处「会失败却静默」的地方都已经在**当场**说话了：
写不进去说「偏好和会话都没能记住」，读不出来说「有 2 项偏好没读回来」，
监听没起来说「外部改动可能发现不了」，内核拒绝接管说清楚是哪一条理由。

但横幅是一种**回答「此刻」的机制**，它有四个结构性的窟窿：

1. **按掉就没了，而按掉的动机恰恰是「我不想现在处理」。**
   横幅的整个交互设计就是在邀请用户把它关掉；关掉之后，那一次降级
   在用户的视野里就**第二次消失**了 —— 比第一次那一次还彻底。
2. **一次运行里可能先后出三四件事，横幅一次只占那么一行位置。**
   监听在第 3 分钟停了、位置记录在第 8 分钟读坏了、用户在第 20 分钟才回来 ——
   界面上是一条横幅，而「到底有过几件事」这个信息已经不存在了。
3. **关掉应用就没有了。** 而「刚才那一下到底提示了什么」恰恰是用户回来
   描述问题时要说的第一句话。
4. **没有账号、没有网络、没有遥测（ADR 0001）。** 所以除了这一页，
   这个应用**没有任何一条**把内部状态交给别人的路。

第 4 条决定了这一页必须能**复制走**：一份自足的纯文本，就是这个纯本地应用
全部的「报 bug」能力。

## 取舍

### 1. 一个纯函数的记录本，**只活一次运行**

`core/health.ts` 是纯数据 + 纯函数：`recordIssue` / `resolveIssue` / `clearHealth` /
`syncFamily` / `activeHealth`。**没有时间源** —— `at` 由调用方传进来，
所以整个模块可以逐字钉在测试里。

**刻意不落盘。** 落盘看起来「更持久」，实际上是把两件事搅在一起：一份跨运行的
降级日志会在下一次运行时以「上次的记录」的样子回来，而那不是**本次运行**发生的事；
而它又会变成一份没人读的垃圾（真需要长期日志的人会去看系统日志）。
这一页的承诺是「**这次运行**发生过什么」，那它就该在这次运行结束的那一刻消失。

### 2. 存 key + values，不存成品句子

`HealthLine` 是 `{ key: MessageKey; values: Record<string, string | number> }`，
渲染那一刻才 `t()`。

理由与 ADR 0031 里「命令标题为什么不能是数组字面量里的 `t(...)`」完全一样：
**在记账那一刻就把句子烤下来，等于把语言钉死在记账那一刻。** 用户在
运行途中切语言，清单上的句子不会跟着变 —— 那是一条已经坏了的 i18n。

### 3. 按 id 幂等；恢复显式，而且**永不删除**

`HealthRecord` 有 `count` / `firstSeenAt` / `lastSeenAt` / `resolvedAt`。
同一个 id 再报一次是**累加**（可能丢的是另一批文档），不是新增一条；
新 id 排在最前面。

「已恢复」的记录**留在清单里**，只是打上标记并盖一层半透明。
自动收起来是这一族里最难看的一种静默：用户连「有过这件事」都不知道。
`resolveIssue` 对没出现过的 id 和已经恢复过的 id 都交回**同一个数组引用**，
所以「这一帧什么都没变」不会触发任何重渲染。

### 4. 两类来源，分开处理

| 来源 | 谁 | 进清单的方式 |
|---|---|---|
| 横幅族（读侧丢失 / 监听问题） | `App.tsx` 里两个 `useEffect` | `syncFamily(log, notes, ids, at)`：**有的记上，消失的标成已恢复** |
| 一次性发生（内核加载失败、写不进去、恢复的草稿与文件失败） | 上报点自己 | `recordIssue` —— 它们没有「恢复」这个状态，硬套只会让记录变成另一种含糊 |

监听的恢复尤其只能靠 `syncFamily`：用户在界面上看到横幅消失的那一刻，
清单里就该同时出现「已经恢复」的时刻，否则那一格会永远是红的。

### 5. 「重复的那次」不算又发生一次

`syncFamily` 里，同一个 id、内容一字未改、且还没恢复 —— **什么都不做**。
上报点在渲染里，而 React 的开发模式会把渲染重跑一遍；那不是又出了一次问题，
是同一次问题的第二次读。没有这条，双挂会让「发生过 2 次」对着一个只发生过一次的问题说话。

### 6. 写失败要加闩

写不进去这一条是**每一笔**都会重试的（位置记忆每 600ms 落一次盘），
所以 `reportPersistFailure` 里有一个 ref 闩：同一次运行只记一条。
不加的话「发生过 47 次」就是这么来的 —— 那不是 47 次问题，是同一个问题的第 47 次提醒。

闩只能挂在上报点本身，**不能**从横幅的 `writeFailed` 闩推出来：那个闩会被
「知道了」清掉，而横幅被关掉不等于问题不再发生。

### 7. 措辞与排版

- **按族分组**（存储 / 会话 / 文件监听 / 编辑内核），不按时间倒序铺平 ——
  同一个故障反复出现时，倒序会让同一条散成一片；分组之后四个格子各自自洽。
  族名用 `satisfies Readonly<Record<HealthArea, MessageKey>>` 钉死：
  将来加了新的一族而忘了写标签名，编译期就会拦下。
- **「发生过 n 次」只在 n > 1 时出现。** 一条永远为真的信息就是噪音，
  而噪音会让人把「这次是 3 次」也一起划过去。
- 严重级只有两档：丢东西的用 error，只丢机会的用 warning。

### 8. 复制全部：自足，而且失败要说

复制出去的文本带应用名、当前时刻、按族分组、每条的时刻与状态 ——
它是「我把这个贴给开发者」用的，所以必须脱离界面也读得懂。
剪贴板失败要有一张脸（`core.cmd.clipCopyDenied` 记着同一件事：失败要有一张脸）。

### 9. 入口：命令 + 帮助菜单，**刻意不给快捷键**

`diagnostics.issues` 挂在「帮助」菜单里（那是「关于这个应用 / 它的状态」那一格），
永远可用 —— **空列表本身也是一个答案**，所以它没有「有没有问题」的前置条件。
不给默认快捷键：诊断入口不该抢键盘。

与设置页**互斥**（开一个先把另一个收起来）：叠着的两层对话框，
用户关掉上层之后常常不记得下面还有一层。

## 后果

- 新增 `core/health.ts`（约 220 行，含文件头把「为什么」讲清楚）+ 21 条单测。
- 新增 `ui/HealthDialog.tsx` + 10 条对话框用例；`styles.css` 加一组 `.health-*`。
- `App.tsx`：一份 `healthLog` 状态、两个 `syncFamily` effect、四处一次性上报、
  一对互相排斥的对话框状态；`UiActions` 加 `openHealth` / `closeHealth`。
- `UiActions` 是 `core/commands/types.ts` 上的契约，所以所有 `UiActions` 的实现
  （测试里的替身也在内）都要跟着补 —— 编译期会一个个点出来。
- i18n 新增 16 个 key × 两种语言。
- 外部层（`App.test.tsx`）7 条用例，钉的是「横幅说过的事清单里留得住」
  「按掉横幅不等于抹掉记录」「反复写不进去只记一次」「恢复会标成已恢复」。

## 重审条件

- **落盘那条**：「只活一次运行」是取舍不是定论。一旦真的出现
  「崩溃后要带走记录」这类需求（比如加一个「导出诊断」到文件），本 ADR 重审。
- **上限 60 是拍脑袋的**：真出现一次运行里 60 条以上（目前每族最多 6 条 id，
  所以这意味着内核数量涨了或者新增了族）时，要重审上限与分组。
- **写失败的闩**：将来如果出现「写失败 → 用户改了配置（比如清了配额限制）→ 又写失败」
  且两次**原因不同**的情形，闩会把第二次吞掉。要重审成「按原因闩」。
- **只有时刻、没有时间轴**：清单给出每条的时刻，但不给跨记录的间隔。
  排查「先坏的到底是哪一件」时，这一点会碍事 —— 那天就该考虑一个时间轴视图。
- **内核逐个记一条**：内核超过四五个时清单会变长，那时该考虑折成一条带 id 列表的。
