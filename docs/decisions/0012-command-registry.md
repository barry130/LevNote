# 0012 · 命令是能力的唯一清单：注册表 + 快捷键 + 命令面板

日期：2026-09-29
状态：已采纳
关联：0010（多标签工作区）

## 背景

P2 的快捷键是这样写的：

```ts
useEffect(() => {
  const onKeyDown = (event: KeyboardEvent) => {
    const mod = event.ctrlKey || event.metaKey;
    if (!mod) return;
    const key = event.key.toLowerCase();
    if (key === 's') { ... }
    else if (key === 'o') { ... }
  };
  window.addEventListener('keydown', onKeyDown);
}, [...]);
```

两个硬编码的分支。功能面一旦变宽（多标签、查找、大纲、主题、命令面板……），
这个写法会立刻显出三个问题：

1. **能力没有清单。** 想知道「这个软件能做什么」，得把整个 UI 目录翻一遍。
2. **入口之间会不一致。** 工具栏按钮、快捷键、将来的菜单各自写一遍动作，
   总有一个会漏掉某个分支（典型：按钮上做了「先确认未保存」，快捷键没做）。
3. **平台差异写死在判断里。** `ctrlKey || metaKey` 让 macOS 上 `Ctrl+S` 与 `Cmd+S`
   变成同一个键，两个绑定会同时命中。

## 决策

1. **引入 `Command` 抽象**（`core/commands/types.ts`）：id、标题、分组、
   快捷键声明、可用性判断、执行体。
2. **命令是能力的唯一清单。** 工具栏按钮、命令面板、快捷键全部从注册表派生；
   工具栏只是**精选子集**，但每个按钮的**行为**都走命令。
3. **快捷键写在命令自己身上**，不维护外部映射表。
4. **平台语义在解析期展开**（`Mod` → macOS 上是 Cmd，其余是 Ctrl），
   匹配期只做逐字段精确比对。
5. **`enabled` 是契约的一部分**：快捷键路径与命令面板路径都要检查它。

## 理由

- **第 2 条消除了一整类 bug。** 「按钮和命令面板里的同一个功能行为不一致」
  从此不可能发生，因为它们是同一个函数。
- **第 3 条防的是「幽灵绑定」。** 外部映射表一定会漂：命令改名或删掉后，
  表里的条目还在，表现为「按了某个键什么都不发生」，而且没人知道该去删哪一行。
- **第 4 条是必要的，不是洁癖。** 宽松匹配（只看按下了什么、不管多按了什么）
  会让 `Ctrl+Shift+Z`（重做）同时命中 `Ctrl+Z`（撤销）——
  这是这类实现最经典、也最难查的 bug。展开到解析期之后，
  匹配函数退化成纯比较，没有分支，也就没有边界争议。
- **第 5 条是实测出来的。** 最初 `enabled` 只在命令面板里生效，
  结果是「只读文件上按 Ctrl+S 仍会执行保存」。可用性判断必须两条路径共用。

## 后果

- 新增一个功能的成本变成「写一条命令 + 决定要不要放进工具栏」，
  而且**它自动获得快捷键能力、命令面板条目、以及可被测试的独立执行体**。
- 命令面板的列表**永远不会过期**：它直接由注册表生成，
  因此不可能出现「指向已删除功能的幽灵条目」，也不可能出现「注册了却搜不到的功能」。
- 模糊匹配自研（`core/commands/fuzzy.ts`，约 30 行）而不是引入 `fuse.js`：
  面板要搜的是几十条命令，不是几万行代码。可预测的排序规则比可调参数更有价值。
- **中文命令名靠 `keywords` 里的拼音命中**（`baocun` → 保存）。
  这不是权宜之计：拼音检索是中文桌面应用的常规期待，
  而「中文标题 + 英文 id」的子序列匹配对中文用户基本无效。

## 重审条件

- 若用户需要**自定义快捷键**（horseMD 有），注册表要支持「用户覆盖层」：
  用户绑定存在设置里，解析时优先于命令自带的声明，并做冲突检测与提示。
  当前架构已经留好了位置（`keybinding` 是命令的字段而不是全局表的键），
  但冲突检测与录制 UI 是独立工作量，不在本次范围内。
- 若命令数量超过 ~150 条，模糊匹配与分组需要重新设计（当前是扁平列表 + 分组标签）。
