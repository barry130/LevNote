# 0004 · 四类编辑器内核的选型与许可边界

日期：2026-09-28
状态：部分待定（见文末「待定项」）

## 背景

目标是对标 Typora（Markdown）、Notepad++（代码/文本）、思维导图工具、draw.io 四类工具。
自研四套编辑器内核不现实，必须站在成熟开源项目上。
约束是：**许可必须允许商业分发**，且不能有任何形式的「抄代码」。

## 决策

| 模块 | 选型 | 许可 | 状态 |
|---|---|---|---|
| Markdown | **Milkdown**（ProseMirror 之上的 WYSIWYG） | MIT | 待 P2 实测 |
| 代码/文本 | **CodeMirror 6** | MIT | 待 P2 实测 |
| 思维导图 | **mind-elixir** 或 **simple-mind-map** | MIT / BSD | **待定** |
| draw.io 图表 | 内嵌 **draw.io** 官方前端 | Apache-2.0（商标受限） | 待 P3，且需先过体积评估 |

## 明确排除

| 项目 | 原因 |
|---|---|
| **Typora** | 闭源商业软件。只做**功能对标**，不接触其代码、不逆向其实现。 |
| **Notepad++** | **GPLv3**。任何形式的代码复用都会把整个轻墨拖入 GPL —— 对一个要分发的桌面应用，这是不可接受的传染。功能对标可以，代码零接触。 |
| **tldraw** | 2025 年 9 月起商业生产环境需付费许可，不符合「免费可商用」的前提。 |

**这条边界必须写进团队约定，而不是存在某个人脑子里**：
新成员加入时最容易犯的错，就是"这个功能 Notepad++ 实现得挺好，我去看看它怎么写的"。
看 GPL 代码再写出功能相同的实现，在法律上是灰色地带，不值得为省几天时间冒这个风险。

## draw.io 的特殊性

draw.io 的**源码**是 Apache-2.0，但**商标**另有约定，且历次版本的使用条款有变化。
内嵌它做图表编辑，在许可上可行，但有两条硬约束：

1. 不得使用 draw.io 的名称与图标作为产品标识 —— 轻墨自有的品牌与图标（见 `outputs/brand/`）已经独立成型。
2. 需确认内嵌分发场景在所采用的版本条款下被允许，并保留其许可声明。

技术上的方案与风险在 `src-tauri/src/drawio/mod.rs` 里有完整记录：
用**独立 webview 窗口 + 127.0.0.1 随机端口**承载，
而不是主窗口里的 iframe —— 后者等于把主窗口的严格 CSP 撕开一个洞。

**未决风险 R1**：draw.io 静态资源体积在数十 MB 量级，与 Tauri「安装包小」的卖点直接冲突。
P0 必须先量出真实数字，再在三条路里选一条：

| 路线 | 代价 |
|---|---|
| 直接接受体积 | Tauri 的体积优势基本消失 |
| 按需下载 | 首次使用需联网，与"纯本地"定位有摩擦 |
| 基于 maxGraph 自建 | P5 从 2 周变成 1–3 人月 |

**在量出数字之前不写 draw.io 相关代码**，避免为一个可能被否的方案投入沉没成本。

## 待定项

1. **思维导图内核**：mind-elixir 与 simple-mind-map 都满足许可要求。
   判据是 P3 的压测结果 —— 大节点数（500+）下的渲染性能、导出保真度、
   以及各自的数据结构离 `docs/format-spec.md` §7.1 的最小骨架有多远。
   离得越远，将来换内核时用户的文件损失越大。
2. **Markdown 内核的 WYSIWYG 程度**：Milkdown 能做到接近 Typora 的即时渲染，
   但复杂表格与数学公式的编辑体验需要实测。备选是 CodeMirror + 预览分栏（更保守，也更不像 Typora）。

## 重审条件

- 任一内核出现许可变更或停止维护 → 立即重审。
- 若 P2 实测发现 Milkdown 在长文档（1 万字以上）下输入延迟超过 50ms，
  应换成分栏预览方案，而不是硬优化 —— 编辑器的输入延迟是体验的生死线。
