# 0004 · 四类编辑器内核的选型与许可边界

日期：2026-09-28
状态：**已定**（Markdown 内核维持 Milkdown 富文本 + 可选源码视图 + 分屏；
V3 长文档输入延迟已于 2026-09-30 实测、原文保真于 2026-10-02 收窄、
**2026-10-02 结论落地** —— 见文末「结论：维持 Milkdown…」）。
思维导图内核另见 [0007](0007-mindmap-core-choice.md)（也已复评维持）。

## 背景

目标是对标 Typora（Markdown）、Notepad++（代码/文本）、思维导图工具、draw.io 四类工具。
自研四套编辑器内核不现实，必须站在成熟开源项目上。
约束是：**许可必须允许商业分发**，且不能有任何形式的「抄代码」。

## 决策

| 模块 | 选型 | 许可 | 状态 |
|---|---|---|---|
| Markdown | **Milkdown**（ProseMirror 之上的 WYSIWYG） | MIT | ✅ **已定**（V3 实测 + 原文保真收窄后维持；可选源码视图与分屏是它的补充，不是替代） |
| 代码/文本 | **CodeMirror 6** | MIT | ✅ **已定**（M11 已落地） |
| 思维导图 | **mind-elixir 5.15.1** | MIT | ✅ **已定**（ADR 0007，2026-10-02 压测后复评维持） |
| draw.io 图表 | 内嵌 **draw.io** 官方前端 | Apache-2.0（商标受限） | ⏳ 待 V1（体积与独立渲染），P5 开工前置 |

## 明确排除

| 项目 | 原因 |
|---|---|
| **Typora** | 闭源商业软件。只做**功能对标**，不接触其代码、不逆向其实现。 |
| **Notepad++** | **GPLv3**。任何形式的代码复用都会把整个轻墨拖入 GPL —— 对一个要分发的桌面应用，这是不可接受的传染。功能对标可以，代码零接触。 |
| **tldraw** | 2025 年 9 月起商业生产环境需付费许可，不符合「免费可商用」的前提。 |

**这条边界必须写进团队约定，而不是存在某个人脑子里**：
新成员加入时最容易犯的错，就是"这个功能 Notepad++ 实现得挺好，我去看看它怎么写的"。
看 GPL 代码再写出功能相同的实现，在法律上是灰色地带，不值得为省几天时间冒这个风险。

## draw.io 的特殊性

draw.io 的**源码**是 Apache-2.0，但**商标**另有约定，且历次版本的使用条款有变化。
内嵌它做图表编辑，在许可上可行，但有两条硬约束：

1. 不得使用 draw.io 的名称与图标作为产品标识 —— 轻墨自有的品牌与图标（见 `outputs/brand/`）已经独立成型。
2. 需确认内嵌分发场景在所采用的版本条款下被允许，并保留其许可声明。

技术上的方案与风险在 `src-tauri/src/drawio/mod.rs` 里有完整记录：
用**独立 webview 窗口 + 127.0.0.1 随机端口**承载，
而不是主窗口里的 iframe —— 后者等于把主窗口的严格 CSP 撕开一个洞。

**未决风险 R1**：draw.io 静态资源体积在数十 MB 量级，与 Tauri「安装包小」的卖点直接冲突。
P0 必须先量出真实数字，再在三条路里选一条：

| 路线 | 代价 |
|---|---|
| 直接接受体积 | Tauri 的体积优势基本消失 |
| 按需下载 | 首次使用需联网，与"纯本地"定位有摩擦 |
| 基于 maxGraph 自建 | P5 从 2 周变成 1–3 人月 |

**在量出数字之前不写 draw.io 相关代码**，避免为一个可能被否的方案投入沉没成本。

## 待定项

1. **思维导图内核**：mind-elixir 与 simple-mind-map 都满足许可要求。
   判据是 P3 的压测结果 —— 大节点数（500+）下的渲染性能、导出保真度、
   以及各自的数据结构离 `docs/format-spec.md` §7.1 的最小骨架有多远。
   离得越远，将来换内核时用户的文件损失越大。
2. **Markdown 内核的 WYSIWYG 程度**：Milkdown 能做到接近 Typora 的即时渲染，
   但复杂表格与数学公式的编辑体验需要实测。备选是 CodeMirror + 预览分栏（更保守，也更不像 Typora）。

   > **2026-09-30 更新（V3 实测）：这一条不再只是「体验取舍」。**
   > 1 万字文档上，**源码内核（CodeMirror）比富文本内核（Milkdown）快 3 倍**
   > （`输入延迟` p50 **16ms** vs **48ms**，同为 120Hz、同批次）。而富文本档的 48ms
   > **正好压在 50ms 判据线上，且会随机器负载翻面**（轻载折算约 27ms）。
   > 也就是说：**富文本这条路的性能余量是零，源码那条路有 3 倍余量。**
   > 完整数据见 `../open-decisions.md` 的「V3 实测记录（第二轮）」。

## 重审条件

- 任一内核出现许可变更或停止维护 → 立即重审。
- 若 P2 实测发现 Milkdown 在长文档（1 万字以上）下输入延迟超过 50ms，
  应换成分栏预览方案，而不是硬优化 —— 编辑器的输入延迟是体验的生死线。

### V3 实测结论（2026-09-30，已跑）

**判据**：1 万字以上文档，输入延迟 ≤ 50ms。**主判据 = `beforeinput` → 出字那一帧**
（Event Timing API；修正前的 `paint` 口径只量了半条链路，会低估）。

**数据**（15426 字 / 23419 字符，120Hz，60 键/档，同批次，校准基准 32ms）：

| 视图 | 落点 | 输入延迟 p50/p95 | 判定 |
|---|---|---|---|
| 富文本 | 中部 / 结尾 | **48 / 56–64** | ❌ 压在线上，随负载翻面 |
| 富文本 | **开头** | **72 / 88** | ❌ 明显超出 |
| 源码 | 任意 | **16 / 16–32** | ✅ 顶到量程下限（真实值 ≤16ms） |
| 分屏 | 中部 | **16 / 24** | ✅ 同上 |

**三条与决策相关的判断：**

1. **富文本档没有余量，源码 / 分屏档有 3 倍余量。** 这是本轮最硬的数字。
2. **落点影响 1.5 倍**（开头 72 vs 中部 48）—— 唯一一档「明显不合格」的是「在文档最开头打字」。
3. **读数的绝对值随机器背景负载整体漂移约 1.8 倍**（同场景两批次实测）。
   所以**判据必须写明测量环境**，跨批次比较必须按校准基准归一化；
   在没写明环境时，「达标了吗」这个问题无解。

**据此重审本条条件**：「超过 50ms → 换分栏预览」**没有被触发成硬性要求，但也没被排除**：

- 富文本档的 `p50` 是 48ms（有效判据线也是 48ms）—— **不算通过**，因为它随时会因负载越线；
- **分屏（源码 + 预览）恰好就是本条预设的备选方案**，而它实测 16ms、长任务几乎为零
  —— 也就是说**这条退路已经存在且性能充裕**（M10 / ADR 0022 做的）；
- 但「换掉富文本」是大动作，**不构成充分理由**：还要看原文保真
  （源码优先架构天然不会用 serializer 改写未编辑的源码，正是 horseMD 的卖点）。
  **本条当时的重审结论是「性能上富文本已无余量」，而不是「立刻改架构」**
  —— 这个结论**后来被「V3 复测」推翻了**，见下。

**未定位的一条**：首块是 H1 时明显更贵（72 vs 段落首块 56）。中部放 H1 / H2 都不慢，
标题也没有特殊 CSS —— 机制不明，已记在 `../open-decisions.md`，不阻塞本结论。

### V3 复测（2026-10-02，修掉高亮之后）

上面那张表里富文本档「没有余量」的结论，**有一半以上来自一条可以修的开销**：
`codeHighlightPlugin` 每次 `docChanged` 都整篇重跑代码高亮，而 `mermaid` 不是
highlight.js 认识的语言 → 退回 `highlightAuto()`（约 35 种语言各试一遍），
5 个围栏共 605 字符就要 20.8ms。给 `highlightCode` 加 LRU 缓存后复测
（真实 Edge + CDP，校准基准 33.2–34.9ms，与上表的 32ms 同量级）：

| 视图 / 落点 | 输入延迟 p50 | p95 | `sync` p50 | 超过 50ms | 长任务 | 判定 |
|---|---|---|---|---|---|---|
| 富文本 / 中部（改前 → 改后） | 48 → **32** | 56 → **40** | 34.2 → **20.9** | → **0 / 40** | → **0 条** | ❌ → ✅ |
| 富文本 / 开头（改前 → 改后） | 72 → **40** | 88 → **48** | 63.4 → **30** | 60/60 → **0 / 40** | 56 → **0 条** | ❌ → ✅ |

**收益来自代码而不是负载**：本次校准基准（34ms）比上表那次（32ms）略慢，而读数更好。

**对决策的影响**：本条的「性能上富文本已无余量」**已被推翻** ——
富文本档现在两档都在判据内且有余量（中部 p50 32 / p95 40；开头 p50 40 / p95 48）。
所以**「超过 50ms → 换分栏预览」这条触发条件在性能维度上不成立**。
换不换架构，剩下的理由只有**原文保真**（源码优先天然不经过 serializer 改写未编辑的源码）
—— 与 horseMD 的方向一致，但不再是「因为富文本太慢」。

「开头比中部贵」仍在（40 vs 32，约 1.25 倍），已降级为**不阻塞的观察**。

### 原文保真的实测（2026-10-02）

**上面那句「剩下的理由只有原文保真」现在也有一半答案了。**
完整记录在 [`../open-decisions.md`](../open-decisions.md) 的「原文保真的实测与收窄」，摘要：

| 一份 23419 字符的真实文档，「改了一个字」之后被改写的行 | 改前 | 改后 |
|---|---|---|
| 合计 | **48 行（6.3%）** | **30 行** |
| ├ 列表符号 `-` → `*` | 18 行 | **0**（配置已关掉） |
| └ 表格按列宽重排 | 30 行 | 30 行（`remark-stringify` 的表格式化，无开关） |

**结论：原文保真是真的，但它不再是一个「必须现在换架构」的理由。**

- **确实存在损失**，而且其中 18 处（列表符号）是**纯损失** —— 用户没碰过、也不知情，
  且它**从来没进过「已知且已接受」清单**（`markdown-core.test.ts` 与 `plugin.ts` 都没提它）。
  这一半已由序列化配置关掉（`setup.ts` 的 `useDashSymbols`）。
- **剩下的一半是格式噪声**（表格对齐空格，语义不变、`git diff` 里一眼可辨），
  严重程度低于「列表符号被换掉」，而且是**架构级**的：要消掉它必须让
  **源码成为唯一数据模型**（horseMD 的「只写回改动发生的位置」）。
- **一个衡量口径的教训**：字符增量（+402 字符 / 1.7%）**照不出**列表符号被改写
  —— `-` 与 `*` 等长。只看字符数会得出「保真度只差 1.7%」的结论，而真实的受害面是
  **48/765 = 6.3% 的行**。**换一个指标就换一个结论**，与 V3 的三条方法论同类。

**所以本条的状态是**：性能维度**已经不再支持换架构**（V3 复测推翻了「没有余量」）；
原文保真维度**支持换架构但强度不足**（真实损失、可量化、随文档规模线性增长，
且是唯一还站着的理由）。

### 结论：维持 Milkdown 富文本 + 可选源码视图 + 分屏（2026-10-02）

**本条至此不再挂着待定状态。** 上面那三段（V3 复测、原文保真、V2）都跑完了，
结论是**不改变**「Milkdown 富文本 + 可选源码视图（+ M10 的分屏）」这条选型。

理由按强度排：

1. **性能维度已不成立**（V3 复测：富文本两档都进判据且有余量，见上）。
2. **原文保真维度真实但强度不足**：剩下改不掉的是 `remark-stringify` 的表格对齐重排
   （语义不变、`git diff` 里一眼可辨），而**纯损失的那一半（列表符号 `-` → `*`）
   已经关掉了**。为一个格式噪声去换架构不划算。
3. **换架构是大动作**，而它要解决的问题现在没有一个够硬。

**保留的重审触发条件**（比原「50ms」更贴近真实痛点）：

- 用户侧出现「保存后 `git diff` 满是噪声」的**实际投诉**（而不是我们自己测出来的百分比）；
- 或上游出现能**只写回改动位置**的序列化路径（horseMD 的
  `docs/markdown-source-preservation.md` 那条思路被验证可行）；
- 或 Milkdown / ProseMirror 出现许可变更或停止维护（原条件，不变）。
